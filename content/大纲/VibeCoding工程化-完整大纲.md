# 《Vibe Coding 工程化：从需求到可靠交付的通用流程》完整大纲

---

## 教程定位（给谁 / 不是什么 / 灵魂）

- **给谁**：已有一定 Vibe Coding 经验、能靠 AI 生成代码的人；面对复杂需求时缺乏结构化推进方法与判断力。适用于独立开发者、全栈工程师、技术团队中的多面手。
- **核心目标**：学完能对**任意**软件开发需求自主走完对应流程，而不是直接把需求丢给 AI 改代码，产出一份留痕判断的中间产物。
- **灵魂 = 判断力（载体是交付物，主次分明）**：每个方法核心回答三问——**何时用**、**怎么识别 AI 的坑**、**怎么剪裁到本轮够用**。交付物（产出物锚定/验收清单/模板）是**逼你在亲手产出中长出判断的练习册**，不是目的。
- **不是另一门"AI 启蒙课"（另攀一座山）**：多数教程（如 vibe-vibe）面向零基础大众、按"入门→进阶→实战"横切、承诺"做出第一个产品"，学完留下**知识**。本教程面向"已会写代码、想把 Vibe Coding 变成手艺"的人，走**执行视角的生产力工程**，学完带走**可再生的工作能力**。对比：**课程表 vs 工具箱**（按任务类型排、非学习阶段）、**做产品 vs 做手艺**（带走可复用流程而非单个产品）、**知识留痕 vs 判断训练**（交付判断而非理解）、**重量级平台 vs 轻量长青**（markdown 唯一真相源，十年不过时）。
- **一句话**：前者教人"做出东西"，本教程教人"做东西的一套手艺、每份中间产物该长什么样"，而这手艺的灵魂是**判断力**。

### S0 · 为什么需要流程？（三条轨道共同地基）

**目标**：建立工程化思维，理解"直接让 AI 改代码"的风险。

内容：

- 反面案例：一个模糊需求直接丢给 AI，结果改东坏西、无法验证、难以维护。
- 对应三轨道的反面案例：
  - 新功能：改东坏西、范围失控
  - Bug：没复现就瞎猜根因，越修越多
  - 重构：不动架构只堆补丁，代码更乱
- 流程的价值：降低不确定性、提高可验证性、保证质量、便于协作。
- 如何按需求类型选择轨道（分支选择地图）。
- 如何根据复杂度裁剪流程：简单脚本可跳过部分步骤，复杂功能必须完整执行。
- 新手可选：5 步最小闭环（一句话需求 → 三句设计 → 先列验收清单 → AI 写码 → 人工验收），"先跑通再规范"；明确标注"不是替代正式流程，跳过的正是返工回来补的"。

**练习**：回忆一次"直接丢需求"翻车的经历，判断它属于哪条轨道、缺了哪个阶段。

### S-对话 · 与 AI 高效多轮对话（三轨道通用元技能）

**目标**：让"多轮澄清"谈得懂、判得准、不崩——能判断 AI 的反问值不值得答、会不会被带偏，也知道何时继续、何时喊停。

内容（轻量共享单元，不产出阶段文档）：

- 核验 AI 反问的三问：①和产出物相关吗 ②答不上是"没定义"还是"不需要" ③追问事实还是替我做决定。
- 多轮对话四条纪律：定锚 / 反问不回 / 回喂迭代 / 防带节奏。
- 何时喊停或换问法：同一问题约 3 轮不收敛 → 换更窄提示词或单维深挖。
- 可选澄清记录「问题—结论表」：复盘反问题合理性的素材。

**配套引用**：B1-① 需求澄清、B2-② 定位根因、B3-② 识别坏味道等多轮对话密集环节，均会引用"对话纪律见 S-对话"。
**与选项式澄清分工**：那套管"答不上来"；S-对话管"判得准、谈不崩"。

### S-A · 现状探索：读懂现有代码库（三分支共同前置）

**目标**：在动手前读懂现有代码库，摸清架构、入口、关键依赖，避免盲人摸象。

**通用方法**：

- 让 AI 生成代码库地图：目录结构、模块职责、入口文件、核心数据流。
- 通过 AST / 搜索定位关键函数、调用链、数据模型。
- 让 AI 总结每个模块"是什么、干什么、被谁依赖"。
- 建立"关键文件速查表"：改这段功能要从哪下手、影响哪些模块。
- 项目过大 / 新手可走**狙击手模式**（S-1-Lite：只找 `[功能名]` 的入口 + 向下追最多 2 层调用），不必一次读懂全量地图。

**提示词模板**：

> 你是一名资深架构师。请分析以下代码库，输出一份代码库地图：
> [项目根目录 / 关键文件列表]
> 要求包含：整体架构与分层、各模块职责、入口与关键流程、核心数据模型、模块间依赖关系、可能需要修改的风险点。
> 输出 Markdown 格式。

**练习**：用本方法分析一个自己手头的项目，产出代码库地图。

### S-B · 测试与回归（三分支共用，各自侧重不同）

**目标**：用测试验证正确性，确保新修改不破坏已有功能。

**通用方法**：

- 根据需求文档 / 行为基线，生成测试用例（正常、异常、边界）。
- 生成单元测试、集成测试、端到端测试代码。
- 运行测试，分析失败原因，迭代修复。
- 回归测试：确保修改未影响已有功能。

**三条轨道各自的侧重**：

| 轨道 | 测试侧重 |
|------|----------|
| B1 通用需求 | 按需求/设计生成全量用例（正常+异常+边界） |
| B2 Bug 修复 | **回归优先**：先写失败用例锁住 Bug，修复后确认转绿且不破坏其他 |
| B3 重构 | **行为基线优先**：重构前建立 characterization tests，重构中保证测试全程绿 |

**提示词模板**：

> 请根据以下需求文档和行为，生成测试用例和测试代码。
> 需求：[简述]
> 代码位置：[文件/模块]
> 覆盖正常场景、异常场景、边界条件。
> 使用 [测试框架] 编写，并确保可运行。

### S-C · 文档同步与交付（三分支共用）

**目标**：保持文档与代码一致，形成可持续维护的交付物。

**通用方法**：

- 让 AI 根据最终代码更新设计文档、接口文档、README、CHANGELOG。
- 自动生成 API 参考、使用说明。
- 文档纳入版本控制。
- 交付物清单：代码、设计文档、测试报告、部署说明。

**提示词模板**：

> 请根据当前代码实现，更新相关设计文档、README 和 CHANGELOG。
> 确保文档与代码一致，描述清楚使用方法和注意事项。

### S-D · 流程自动化与工具链（三分支共用）

**目标**：将流程固化到工具中，减少重复劳动。

**通用方法**：

- 创建自定义提示词库（Cursor Rules、Claude Projects、文本模板）。
- 使用脚本或模板自动生成需求文档、任务列表、测试框架。
- 集成 CI/CD：提交前自动运行测试、AI 代码审查。
- 建立个人或团队流程规范。

**提示词模板**：不固定，鼓励学员根据自身需求定制。

**练习**：为自己配置一套提示词模板和自动化脚本。

### B1-① 需求澄清与分析（✅ 已完成）

> **前置**：通读 S0、S-A（新项目可简化 S-A）。
> **目标**：把"我想做个 X"变成结构化、可验证的需求文档。
> **预估时长**：30–60 分钟。

**通用方法（多轮澄清，每轮收敛一个维度，按章节生成模板的"五件套"展开，含贯穿案例点睛）**：

- 目标一 · 边界与约束 — 万能清单法 → 产出「五维清单」（角色 / 对象范围 / 触发状态 / 规则限制 / 环境前提）
- 目标二 · 验收标准 — 三情景法 → 产出「验收清单」（正常 + 边界 + 异常，可断言；含"目的宣言"+ 卡壳时"倒推法"）
- 目标三 · 范围外 — 逆向排除法 → 产出「范围外边界清单（含防偏离一句）」

> 多轮澄清谈不动 / 判不准反问题？对话纪律见 [S-对话]。

**沉淀产出物**：需求文档（六要素：背景 / 目标 / 功能 / 非功能 / 验收 / 范围外），作为 B1-② 的输入。
**提示词**：见 S-附录 B1-1a/b/c（三追问）+ B1-2（整合）+ B1-3（完整版）。
**练习**：对真实需求走完澄清流程，产出六要素需求文档。

> 下一步 → B1-② 技术方案设计。

### B1-② 技术方案设计（✅ 已完成）

> **前置**：B1-① 的需求文档。
> **目标**：产出技术方案设计文档，明确"怎么建"。
> **预估时长**：1–2 小时。

**通用方法（四件设计产物，各自按五件套展开）**：

- ① 整体架构（Mermaid 分层法）→ 分层架构草图
- ② 关键数据模型（名词实体法）→ 数据模型（实体 / 字段 / 状态机 / 幂等）
- ③ 接口定义（需求到接口映射法）→ 接口契约清单
- ④ 技术选型与风险（决策点拆解法）→ 技术决策表

**沉淀产出物**：技术方案文档（七段：概述 / 架构 / 模块职责 / 数据模型 / 接口 / 选型 / 风险规避），作为 B1-③ 评审对象、B1-④ 拆任务的唯一输入。
**提示词**：见 S-附录 B1-4a/b/c/d（四追问）+ B1-6（七段整合）+ B1-5（完整版）。
**练习**：拿需求文档生成方案并重点复核"范围外 / 状态+幂等 / 选型回应非功能"三点。

> 下一步 → B1-③ 方案评审与决策。

### B1-③ 方案评审与决策（✅ 已完成）

> **前置**：B1-② 的技术方案文档。
> **目标**：多备选 + 模拟评审 + 留决策记录（ADR）。
> **预估时长**：30–60 分钟。

**通用方法（三产物，各自按五件套展开）**：

- ① 多方案对比 → 横评表（方案 / 优缺点 / 风险 / 工作量）
- ② 模拟评审 → 隐患清单（漏网 / 失败 / 一致 / 维护）
- ③ 决策记录 ADR → 轻量版或正式版 ADR

### B3-② 识别坏味道与风险点（✅ 已完成）

**通用陷阱**

- 上下文超载：一次性给 AI 太多信息，导致输出混乱 → 用 S-A 拆解、每次聚焦一步。
- 跳过设计直接改代码 → 导致返工（B1 ② / B3 基线）。
- 不验证 AI 输出就接受 → 埋下隐患（S-B）。
- 任务粒度过大 → 难快速验证（B1 ④ / B3 ③）。
- Bug：没复现就瞎猜根因 → 越修越多（B2 ①）。
- 重构：不建基线就动手 → 无法判断是否改坏（B3 ①）。
- 忽视文档同步 → 后续维护困难（S-C）。

**最佳实践**

- 始终先产出文档，再写代码。
- 每次只让 AI 做一件事，并明确验收标准。
- 保留人工决策权：AI 提供建议，人做最终决定。
- 定期让 AI 总结当前项目状态，保持上下文。
- 将流程模板化，形成个人或团队规范。
