在 B2-② 我们找到了根因，但**你还没捞到"修对了没有"的标尺**。先把根因锁进一条测试：这条测试在 b2-bug 分支上跑会红（Bug 还在）、在 main 分支上跑会绿（Bug 不在）。有了它，B2-④ 每改一次就跑一次——红变绿的那一刻，根因才算真正消失，而且**以后任何人、任何改动再把它改坏，测试立刻报红**。

> 一句话：**回归测试 = 把"Bug 的复现路径"固定成代码，让 Bug 从"口头传说"变成"永远盯梢的哨兵"。**

> 这一章大量复用共享单元 [S-B · 测试与回归]（用例 / 写代码 / 跑 & 分析 / 回归报告四环节），本轨道**不重写**那套通用方法，只强调 B2 的侧重——**回归优先**：先写失败用例锁 Bug，修复后确认转绿。

用配套项目 `refund-shop` 的 **b2-bug 分支**继续举例（本章贯穿案例）：
- **Bug1 的红线段**：`internal/routes/orders_route_test.go` 已有 `TestCreateOrder_ZeroAmount_Returns400`——0 元订单应被拒 400。在 b2-bug 分支（`OrderMinAmount=0`）上跑它**会红**（实际返回 200），这正是"修复前红、修复后绿"的完美红线。
- **Bug2 的红线段**：`internal/domain/refund_rules_test.go` 已有 `TestCalcRemaining_Bug2ReverseRemaining_Apply5000After3000_Approved`——直接断言正确行为（已有 `3000` 后退再申请 `5000` 应被批准）。在 b2-bug 分支（`ReverseRefundRemaining=true`）上跑它**会红**（被误判"余额不足/已全退"）。同域另两条 `Apply8000OnFresh_Approved`、`Apply1After3000_Approved` 同理；routes 层还有 `TestCreateRefund_Bug2ReverseRemaining_ApproveFull_LeadsFully`、`TestOrderStatus_Bug2ReverseRemaining_Approve8k_LeadsPartial` 收口整条联动链路。

## 一、为什么"先写测试、让测试红"，而不是直接修？

| | 直接修 | 先写会红的回归测试再修 |
|---|---|---|
| 你怎么判断"修好了" | 靠"看起来不报错了" | 红变绿的那一刻 = 证据确凿 |
| 换个输入 | 可能又复现 | 测试覆盖的就是那次复现 |
| 日后被改坏 | 没人发现，Bug 悄悄回潮 | 测试立刻红灯报警 |
| B2-④ 改起来 | 心里没底、怕改A坏B | 每改一次跑一次，坏没坏一眼见 |
| 交给别人维护 | 说不清该守什么 | 测试就是一份"行为契约" |

> 一句话：**先让测试红，修代码才有"靶子"；修完测试转绿，改才算数。** 这也正是 TDD（测试驱动开发）的核心循环：红 → 绿 → 重构。

## 二、通用方法：把复现步骤固化成"先红后绿"的测试

复用 [S-B] 的用例/写码/跑&分析三环节，本轨道在这之上加一道 B2 特有的动作：**确认那条测试在修复前必然红**。三个目标：

### 🔴 目标一：选对测试类型，让断言锁住根因

**产出**：对某个 Bug 选定 1 个主测试类型（端到端 / 集成 / 单元），并确认它"隔着真实调用复现路径"。

**要确认的本质**：回归测试要**锁住复现路径本身**，而不是只测一下函数吐数值。选型思路 —— 能隔着接口复现就优先更外层；内层函数再补单元当作"放大镜"。

**可复制的拆分维度**（引用 S-B ·一② 的类型，B2 角度重申）：

| 维度 | 什么情况下 B2 该选 | 装进「Bug1：0 元下单」 |
|------|---------------------|--------------------------|
| **端到端** | Bug 在整条用户流程上暴露 | 发真实 `POST /api/orders` 带 amount=0，看是否 400 |
| **集成** | Bug 在模块协作间 | handler → 金额校验 → 插库的协作是否放行 |
| **单元** | 想精确锁定某一函数 | `CalcRemaining` 的 remaining 计算（Bug2 适用） |

**照抄即用的通用追问提示词**（即 S-附录 **B2-3** 的 ①）：

> 按这个根因报告，请先选测试类型：
> 复现路径是 `[入口接口 → 症状所在函数]`，选**端到端 / 集成**里能隔着真实调用锁住 Bug 的那一层；若关键逻辑在纯函数里，再补一个**单元**测试当放大镜。给我 1 个主类型，并说明为什么它是这层。

> 💡 **关键判断**：B2 的默认偏好 = **端到端 / 集成**（隔着真实调用锁 Bug），纯函数（如金额计算）才补单元。**别上来就只写单元测试**——那锁的是函数，可能漏掉"接口层根本没调用它"这类更漏的坑。

> 💡 **更省事的判断法：先看这个 Bug"藏在哪一层"，再定粒度。**
> ① Bug 在**单个纯函数**里（如 `CalcRemaining` 余量算错）→ **单元测试**锁定那个函数最直接；
> ② Bug 在**跨层协作**里（如 handler 没把 `amount=0` 传给校验、或二次退款在接口层漏了重验）→ 一定选**端到端 / 集成**，因为单测锁的是函数、盖不住"这层根本没调用它"的漏。
> 判断口诀：**纯函数 → 单测；跨层 / 接口 → 端到端**。配套两个真实 Bug 恰好各占一类——Bug2（`CalcRemaining` 算错）是纯函数，Bug1（0 元下单校验漏掉）是跨层，正好都对得上号。

> 🔴 **把"三层测试"看成"三层契约"，就知道该锁哪一层**：回归测试归到哪一层，本质是"你要确立哪一层的行为契约"。项目三层，各验一件事——
> | 层 | 它验收的契约 | 通常测法 | 退款项目对应 |
> |---|---|---|---|
> | **domain** | 业务逻辑**算得对不对**（金额、状态推导） | 单元测试 | `CalcRemaining` 余量、实付状态 `fully/partial/paid` 推导 |
> | **routes（HTTP 层）** | 链路**契约**（状态码、错误分流、固定文案） | httptest 打真实接口 | 超限回 `400` + 固定文案、`404`、500 不泄露 |
> | **integration** | 跨组件**协作对不对**（handler+校验+插库串起来） | 依赖真实入库的集成测试 | 申请退款 → 校验 → 落库 → 查状态整条 |
> **不是每层都重写一遍全量测试**——**按这次的 Bug 归属**，主要锁它藏的那一层，另外两层各补 1 条"别让它坏"的冒烟即可。判断口诀仍是**纯函数锁 domain、跨层锁 routes/integration**。
>
> 举个 routes 层"契约验收"的最小片段（目的就是锁"链接口该有的样子"）：
> ```go
> func TestPostRefunds_OverQuota_Returns400WithFixedMessage(t *testing.T) {
>     // 造一个已满额、再超退的请求
>     w := httptest.NewRecorder()
>     r := httptest.NewRequest(http.MethodPost, "/api/refunds", overQuotaBody())
>     ordersRoute().ServeHTTP(w, r)               // 走真实路由
>     if w.Code != http.StatusBadRequest {        // 契约①：状态码
>         t.Fatalf("want 400 but got %d", w.Code)
>     }
>     if got := w.Body.String(); got != "refund amount exceeds refundable quota" {
>         t.Fatalf("want fixed message, got %q", got) // 契约②：固定文案一字不改
>     }
> }
> ```
> 这条测试并不关心业务怎么算，它锁的是**"接口对外长什么样"**——这正是 D4 写进接口契约的那三点（固定文案 / 不外泄 / 三态分流）在这里落地成断言。**看测试名 `Returns400WithFixedMessage`，就一眼知道它在守哪根契约红线**。

> 🔴 **覆盖率怎么看（补完这层契约测试的实证）**：给配套项目补上这套 routes 契约测试后，实测 **domain 85.7%、routes 51.2%**（`go test -cover ./...` 直接打印这两个分包数字）；若用 `go test -coverprofile=cover.out ./...` + `go tool cover -func=cover.out` 把**全库**（含 `main.go` 的 0%）加权合计，总覆盖率约 46.2%。离 100% 还很远，但它已经把 **5 条资金红线链路**测穿（正常申请 / 超额拒绝 / 审批通过 / 审批超限 / 订单状态联动，只剩并发那类 `:memory:` 模拟不准的没铺）。判断力：**覆盖率高低不是目标，看它兜住了哪几条"判错就是钱错"的红线**——资金类把关键链路钉死，比堆到 90% 却漏掉超限分支强得多。你真正要带走的是"怎么给一段改造配上能证明它没改坏关键路的测试"，而不是把数字刷好看。

> ⚠️ **这条只适用于本项目这种"关键路径优先"的教学演示**——生产环境里，关键路径测穿后仍应逐步把覆盖率补上去，别把"覆盖率不重要"当成普遍原则带出本教程。

### 🔴 目标二：写"先红后绿"的回归测试，并起红线语义名

**产出**：一条**可运行**的测试代码——断言点对准根因报告"第一次变不对"的那一步；测试名自带"守哪根红线"的语义。

**要写对的本质**：这一条测试不是"随便测测"，它是**从复现步骤反推出来**的：把 B2-① 的 MRE（最小复现步骤）搬到测试里作为输入，把根因报告里"应该得到的正确值"作为断言目标。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug1」 |
|------|----------|--------------|
| **输入** | 用 B2-① MRE 的触发条件做测试输入 | amount=0（走真实 POST /api/orders） |
| **断言** | 用 B2-② 根因报告的"期望正确值"做断言 | 期望 400 + "amount must be"；实际 200 → 红 |
| **红线命名** | 测试名一眼说出"守什么行为" | `TestCreateOrder_ZeroAmount_Returns400` |
| **先红后绿** | 当前代码红、修复后绿 | b2-bug 红（200≠400）→ B2-④ 修后绿 |

**照抄即用的通用追问提示词**（即 S-附录 **B2-3** 的 ②③④）：

> 请把这条测试写成可运行代码：
> 测试框架 `[如 go test / pytest]`，代码位置 `[文件]`，测试名要能看出"守哪根红线"（如 `TestCreateOrder_ZeroAmount_Returns400`）。
> 断言对准根因报告里"第一次变不对"的那一步；保证修复前必然失败、修复后必然通过。
> 写完后说明：这条测试在当前代码上预期红（即复现 Bug）、修复后预期绿。

> 💡 **关键判断 · 怎么证明"这是复现 Bug 的红，不是写错的红"**：跑之前先想清楚——**红的原因必须与 Bug 症状吻合**。拿 Bug1：测试期望 400、实际得 200，这个"200"正好是 B2-① 复现说明里钉死的 Bug 症状。如果红的断言跟你复现说明对不上，那是测试写错了，先改测试再往下走（详见目标三）。

### 🔴 目标三：跑起来，确认"红"＝复现成功（区分测试写错 vs 代码缺陷）

**产出**：一次成功的**红线确认**——那条测试确实因为 Bug 而红，且失败信息与复现说明吻合（而非测试自己写错）。

**要确认的本质**：测试红了有两种可能：**a)** 真的复现了 Bug（理想情况，红得对）；**b)** 测试自己写错了（断言错、管道错、装配错）。B2-③ 的落点必须是 a——因为这条测试接下来要当守门员，测试若撒谎会误导 B2-④。

**可复制的拆分维度**：

| 维度 | 要判断的核心 | 装进「Bug1」 |
|------|--------------|--------------|
| **失败信息** | 报的错是不是 Bug 的症状？ | "want 400, got 200" ← 正是 0 元成功 |
| **断言正确性** | 期望值是否符合需求？ | 0 元应拒 400 → 断言没错 |
| **装配正确性** | 测试有没有测歪（测到别的模块）？ | 走真实 /api/orders → 正确命中 |
| **结论** | 红 = 复现成功，可进 B2-④ | ✅ 红得对 |

**照抄即用的通用追问提示词**（复用 S-B ·一③ 的失败分析）：

> 我运行测试得到以下输出：[粘贴失败输出]
> 请逐条判断：这条失败是"正确复现了 Bug（红得对）"，还是"测试自己写错（断言/装配错）"？
> 判定依据要贴上复现说明对照；若测试写错，给出修正。

> 💡 **关键判断 · 三个"确认真红"的节点**：
> ① **跑这条**：`go test -run TestCreateOrder_ZeroAmount_Returns400 ./internal/routes/` → 红；
> ② **对照复现说明**：失败信息与 B2-① 钉死的"实际↔期望"吻合；
> ③ **反向验证**：临时把 `OrderMinAmount` 改回 1 再跑 → 绿（说明测试确实锁住了这个开关）。验证完记得改回 b2-bug 状态。
> 三个都过，才敢说"红得对"。

> 测试跑不红 / 红得莫名其妙也别慌：把"这条测试红了，但我分不清是复现了 Bug 还是写错了，请对照复现说明把我的失败输出逐项拆开，告诉我哪一行断言在验证哪个事实，若断言错了该怎么改"原样甩给 AI——从"对着红圈发呆"变"逐条核对断言在守什么"；读不懂某节原文时，话术见导读「读不懂？用 AI 帮你读本教程」（卡壳救助已收拢于此）。

## 三、把回归测试沉淀成「红线测试 + 红绿记录」（本步的产出物锚定）

你这一章要"交出去"的，是**一条已确认红的回归测试** + 一段「红绿记录」。它既是 B2-④ 修复的靶子，也是日后所有回归的守门员。固定结构：

```markdown
# 回归测试记录：<Bug 一句话症状>

## 1. 测试文件与用例
- 测试文件：<文件:行号>
- 用例名：<TestXxx_Returns400OnZeroAmount——含红线语义>
- 覆盖点：<根因报告"第一次变不对"的那一步>

## 2. 当前状态（修复前 · 应红）
- 运行命令：<go test -run XXX ./...[路径]>
- 结果：FAIL，失败信息 <want 400, got 200>
- 红因判定：<复现了 Bug（红得对） / 测试写错（已改）>

## 3. 反向验证（可选佐证）
- 临时把根因开关改回默认再跑 → PASS（证明测试锁住了该开关）
- 验证后已恢复原状：<是 / 否>

## 4. 本测试守住的红线
<一条话：0 元订单永远不许创建成功>
```

**怎么写（从二、的三份产出拼）？**
- **"测试文件与用例"**：取 目标一 选定的类型 + 目标二 写出的测试名与断言点。
- **"当前状态"**：取 目标三 的运行结果，**最重要的就是"修复前应红"这个事实**——把它写成可复现命令，别人也能复跑。
- **"反向验证"**：取 目标三 ③ 的结果，作为"测试确实锁住了根因开关"的实证。
- **"守住的红线"**：一句话总结这条测试守护的不可违反约束。

**检查标准**：读这份记录的人，照着第 2 段的命令跑一遍能**得到同样的红色**；并且能回答"这条测试守住了什么红线"。**测试没确认红 = 别进 B2-④。** 一条"修完才想起来跑"的测试不是回归测试，是事后补作文。

**整合提示词**（把二、的三份产出收拢成回归测试记录）：

> 请把下面几份产出整理成一份「回归测试记录」：
> [粘贴：测试文件 + 用例名 + 断言覆盖点（目标一/二产出）]
> [粘贴：运行命令 + 当前 FAIL 输出 + 红因判定（目标三产出）]
> [粘贴：反向验证结果（可选）]
> 按 测试文件与用例 / 当前状态（应红）/ 反向验证 / 守住的红线 四段输出，命令要可复制。输出 Markdown。

> 📌 这份"已红的回归测试"正是 **B2-④ 前置里"以失败测试为输入"的那份**——B2-④ 修完后跑的就是它转绿。**每章的产出都成为下一章的输入，链条由此接上。**

## 四、提示词模板：写回归测试（S-附录 B2-3）

这是 S-附录 里的 `写回归测试提示词`（即 **S-附录 B2-3** 的完整版，B2 专用；你在本章「二、目标一 / 目标二」看到的 ①（选类型）、②③④（写测试）两条提示词，正是这条完整版的**拆段展示**，这里一次性给全量），直接复制填空即可：

> 有一个 Bug，根因报告如下：
> `[粘贴：B2-② 的根因报告]`
> 请帮我把它转成一条「回归测试」：
> ① 选类型：按复现路径选 端到端 / 集成（隔着真实调用锁 Bug 最好），不足再补单元；
> ② 写可运行测试：断言点对准根因报告里"第一次变不对"的那一步，保证修复前必然失败、修复后必然通过；
> ③ 起一个"红线"语义的测试名（如 `TestCreateOrder_ZeroAmount_Returns400`）；
> ④ 说明这条测试在当前代码上预期红（即复现 Bug）、修复后预期绿。
> 请先列出将要创建的测试文件与覆盖点，再写代码。

**逐字段解析（方便你按需增删）**：

- **`[粘贴：根因报告]`**：整份贴 B2-② 的根因报告——**断言点就取自它的"第一次变不对"那一步**，不是自己拍一个。
- **① 选类型**：B2 偏好端到端 / 集成（隔着真实调用锁 Bug），纯函数才补单元。**让 AI 只给一个主类型 + 理由**，别一次摊三种。
- **② 写可运行测试**：核心是"修复前必红、修复后必绿"——请 AI 把断言对准根因行为，而非症状周边。
- **③ 红线语义名**：测试名一眼说出"守什么"，如 `TestCreateOrder_ZeroAmount_Returns400`。**这是可持续维护的关键习惯。**
- **④ 预期红/绿说明**：逼 AI 明确这条测试"现在红、修后绿"，**防止写出一条在 b2-bug 分支上本来就绿的无效测试**。

> 💡 **递归用法**：AI 第一版测试往往断言太松（只查状态码、不查错误文本），或没对准根因。**把它回喂，追加"放宽到把断言钉在根因报告里'第一次变不对'的数据上，例如期望的返回码 + 错误信息原文 + 不发生 insert"，** 迭代 1–2 轮直到这条测试"在 Bug 代码上必然红、在正确代码上必然绿"。

> 测试类型一时拿不准？追加"给 2–3 个可选测试类型（端到端 / 集成 / 单元）各自的取舍与后果，我懂了再挑"——从"逼你拍板"变"菜单里点菜"，只降门槛不替你决定；这条已在 S-附录·进阶操作速记「选填」下备案，照抄即用。

## 五、练习：确认两条回归测试在 b2-bug 分支上"红了"

**任务**：为 Bug1、Bug2 各确认一条回归测试，当场跑出"红"，并产出两份回归测试记录。

**推荐步骤（以 Bug1 为例）**：

1. 在 `refund-shop` 的 **b2-bug** 分支上，定位 `internal/routes/orders_route_test.go` 里的 `TestCreateOrder_ZeroAmount_Returns400`（它就是 Bug1 的红线段）。
2. 用它作为"回归测试的生产示例"，跑通：`go test -run TestCreateOrder_ZeroAmount_Returns400 ./internal/routes/` → 期望 **FAIL**（want 400, got 200）。
3. 用 B2-3 提示词重新从根因报告"生成"这条测试，对照 AI 给的测试名与断言点，看它是否和你手头这条红线一致——**体会"从复现步骤反推测试"的路径。**
4. 用目标三的"三节点确认红"：对照复现说明 + 反向验证（临时把 `OrderMinAmount` 改回 1 再跑 → 绿，验证后改回 b2-bug 状态）。
5. 用整合提示词产出「回归测试记录」，存为 `docs/regression-test-<bug-id>.md`。
6. **（Bug2 同样流程）**：定位 `internal/domain/refund_rules_test.go` 的 `TestCalcRemaining_Bug2ReverseRemaining_Apply5000After3000_Approved`，跑出红（直接断言正确行为，却在 b2-bug 上因减法倒置被误判"余额不足/已全退"）。

**对答案**：两份记录都应含"测试文件与用例 / 当前状态（应红）/ 反向验证 / 守住的红线"四段，并且**第 2 段命令跑出来都是 FAIL、失败信息与复现说明吻合**。

- **Bug1**：`TestCreateOrder_ZeroAmount_Returns400` 在 b2-bug 分支红（实际 200 → 期望 400）。守住红线：**0 元订单永远不许创建成功。**
- **Bug2**：`TestCalcRemaining_Bug2ReverseRemaining_Apply5000After3000_Approved` 在 b2-bug 分支红（正确行为应是批准退 `5000`，却因 `ReverseRefundRemaining=true` 被误判"余额不足/已全退"）。守住红线：**退款申请（含首次）不该因减法倒置被误判为余额不足/已全退。**
- **两条测试的共同点**：它们都写在 `main` 分支是**绿**的（正确行为）、在 `b2-bug` 分支是**红**的（Bug 复现）——这就是"回归测试 = 复现步骤的自动化"，也是 B2-④ 修复后它们必须在同一次代码上转绿的判据。

> 📌 **预期红提示（Bug 现场正常现象）**：b2-bug 分支因注入，`go test ./...` 下 domain 的多条用例会**一并变红**（不止上面这 1 条）——这是 Bug 现场注入全局开关后的**正常现象**，不是测试写错；B2-④ 修好减法方向后它们会**全部转绿**。

> 🔎 **（可选进阶）给自己的 Bug 从零写一条**：若你手里的 Bug 没有现成红线测试，用 B2-3 提示词从你的根因报告生成一条，跑出红。判断标准：**红的原因必须与复现说明吻合，否则是测试写错。**
