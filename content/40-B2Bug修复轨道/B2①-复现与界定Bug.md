在 S0 里，我们看过 B2 轨道的反面案例：**没复现就瞎猜根因，越修越多**。B2 和 B1 最大的不同就在这——B1 是"从无到有做新功能"，B2 是"已有功能行为不对，把它修对"。而修对的第一个动作不是改代码，是**先把"它到底怎么坏的"钉死**。

用配套项目 `refund-shop` 的 **b2-bug 分支**举例（本章贯穿案例，两个预埋 Bug）：
- **Bug1（0 元订单能创建）**：往 `POST /api/orders` 发 `amount: 0`，居然下单成功（应该被拒 400）。
- **Bug2（可退余额减法方向倒置）**：可退余额计算用的减法方向被倒置——任何退款申请（含第一次）都会被误判为可退余额不足/已全退而拒。

> 🔍 **这些 Bug 从哪来？（blank import 注入载体）** 两个 Bug 不是手写进业务逻辑的，而是靠一个**教学注入包** `internal/b2bug` 注入的——b2-bug 分支的 `main.go` 里用**空导入** `_ "refund-shop/internal/b2bug"` 引入它（空导入不绑定名字，但会触发该包的 `init()`）；`inject.go` 的 `init()` 只干两件事：把 `OrderMinAmount` 改成 `0`（Bug1）、把 `ReverseRefundRemaining` 置 `true`（Bug2）。**main 分支的 `main.go` 不导入这个包**，所以行为正确。认清这层载体，你复现的目标是"让 Bug 从根上消失"（修业务代码、让判定不再依赖被改写项），**不要改注入包本身**。

如果直接猜"可能是金额校验写错了"就动手，你很可能改错地方、或改了 A 又弄坏 B。**先把 Bug1 稳定复现出来，你才拥有判断"修没修好"的标尺。**

## 一、为什么修 Bug 前必须先"复现"？

很多人拿到 bug 的第一反应是"赶紧改"，但"赶紧"恰恰是最贵的：

| | 没复现就动手 | 先复现再动手 |
|---|---|---|
| 你掌握的 | 一句模糊的"好像出错了" | 一份"照做必现"的步骤 |
| 改的时候 | 靠猜，改哪算哪 | 对着触发条件精准定位 |
| 判断修好没 | 说不清（可能只是碰巧不报错） | 复现步骤跑一遍，不现 = 修好 |
| 返工风险 | 高（改了 A 坏 B，越修越多） | 低（每次改动都能验证） |
| 协作 | 别人复现不了，无法一起查 | 把复现说明丢给队友/AI 就能查 |

> 一句话：**复现的 20 分钟，通常能省掉后面 2 小时的瞎猜和无数次"我这边没问题啊"。**

## 二、通用方法：把"症状"逼成"可复现的事实"

### 🔴 目标一：构造最小复现步骤（MRE）

**产出**：一份最小复现步骤（MRE）——别人照做也能复现的最短操作路径。

**要复现的本质**：把"好像出错了"拆成四个问不烂的维度，逼 AI 和你一起把 Bug 钉死。这套维度是**跨 Bug 通用的**，任何 Bug 都能套。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug1：0 元下单」 |
|------|----------|------------------------|
| **触发条件** | 什么输入 / 操作 / 环境下必然触发？ | 下单接口 amount=0（其余字段正常） |
| **实际输出** | 复现时实际得到什么？ | 200 OK，订单创建成功，status=paid |
| **期望输出** | 按需求应该得到什么？ | 400 Bad Request，amount must be > 0 |
| **影响范围** | 波及哪些功能 / 数据 / 用户？ | 0 元订单入库；后续退款、状态联动全被污染 |

**照抄即用的通用追问提示词**（即 S-附录 **B2-1**）：

> 我遇到一个 Bug：`[一句话症状]`。请帮我把它稳定复现并界定清楚：
> ① 触发条件：什么输入 / 操作 / 环境下必然触发？列出最关键的 1–3 个触发因子；
> ② 实际输出：复现时实际得到什么（报错 / 返回值 / 界面表现），贴出证据；
> ③ 期望输出：按需求 / 业务直觉应该得到什么；
> ④ 影响范围：波及哪些功能 / 数据 / 用户，严重程度如何；
> ⑤ 最小复现步骤（MRE）：给出能复现它的最短操作路径，越短越好。
> 若某个触发因子我不确定，先按最可能的情况给一版，标注"待验证"，我再实测确认。

> 💡 **关键判断**：MRE 的合格线 = **别人照做 3 步以内能复现**。步骤超过 5 步，多半混进了无关变量，要砍。**复现不了 = 还没界定清楚，别急着进 B2-②。**

---

### 🔴 目标二：二分法缩小触发条件

**产出**：一份「触发因子清单」——哪个条件才是关键触发因子（一改 Bug 就消失的那个）。

**要复现的本质**：Bug 往往不止一个触发条件，直接全量排查等于大海捞针。二分法的思路是**设计对照实验，一次只改一个变量**，逐步排除无关变量。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug1」 |
|------|----------|--------------|
| **变量** | 有哪些可能影响复现的变量？ | amount 值、product_name 是否为空、shipping/coupon 值、是否走 API |
| **对照** | 每次只改一个变量、固定其余？ | 只把 amount 从 0 改成 1，其余不变 → 是否就不复现 |
| **关键因子** | 哪个变量一改 Bug 就消失？ | amount=0 是关键因子（amount=1 时正常） |

**照抄即用的通用追问提示词**（即 S-附录 **B2-1a**）：

> 我按上面的步骤复现了，但触发条件还不确定是哪一个。请帮我用二分法缩小：
> ① 列出所有可能影响复现的变量（输入 / 环境 / 数据状态）；
> ② 每次只改一个变量、固定其余，给出"改哪个、预期会怎样"的对照实验；
> ③ 根据我回报的结果，逐步排除无关变量，直到锁定最关键的触发因子。

> 💡 **关键判断**：二分法不是让 AI 猜，是**设计对照实验**——改完必须实测回报，让 AI 据此排除。**锁定"关键因子"后，B2-② 定位根因就有靶子了。**

> 复现不出来也别慌：把"我复现不出来，请按[这类功能]最常见的故障形态给我 2–3 个可能方向，我挑最像的那个再展开"原样甩给 AI——从"被 Bug 卡住"变"在 AI 给的菜单里点菜"；读不懂某节原文时，话术见导读「读不懂？用 AI 帮你读本教程」（卡壳救助已收拢于此）。

## 三、把复现结果沉淀成「复现说明」（本步的产出物锚定）

你这一章要"交出去"的，是一份**复现说明**——B2-② 定位根因的唯一输入，也是 B2-③ 写回归测试的依据。它有固定**四要素**结构：

```markdown
# 复现说明：<Bug 一句话症状>

## 1. 触发条件
什么输入 / 操作 / 环境下必然触发（最关键 1–3 个触发因子）

## 2. 实际 vs 期望输出
- 实际：复现时得到什么（贴报错 / 返回值 / 界面表现）
- 期望：按需求应该得到什么

## 3. 影响范围
波及哪些功能 / 数据 / 用户，严重程度

## 4. 最小复现步骤（MRE）
最短操作路径，别人照做也能复现
```

**怎么写（从二、的两份产出拼）？**
- **"触发条件"**：取 二、目标二 二分法锁定的关键因子（1–3 个），不是全部变量。
- **"实际 vs 期望输出"**：取 二、目标一 的 ②③，实际输出要贴证据（报错原文 / 返回 JSON）。
- **"影响范围"**：取 二、目标一 的 ④，判断严重程度（涉及金额 / 数据 → 高优先）。
- **"最小复现步骤"**：取 二、目标一 的 ⑤，砍到最短、别人照做能复现。

**检查标准**：读这份说明的人，能照着第 4 步**亲手复现**，并对照第 2 步判断"这就是那个 Bug"。**复现说明不合格 = 别进 B2-②。**

**整合提示词**（把二、的两份产出收拢成复现说明）：

> 请把下面几份产出整理成一份「复现说明」（四要素：触发条件 / 实际 vs 期望输出 / 影响范围 / 最小复现步骤）。
> [粘贴：MRE 最小复现步骤]
> [粘贴：触发因子清单（二分法结果）]
> [粘贴：实际输出证据 / 期望输出]
> 要求：触发条件只留最关键 1–3 个；MRE 保持最短路径、别人照做能复现；输出 Markdown。

> 📌 这份复现说明正是 **B2-② 前置里"以复现说明为输入"的那份**，也是 B2-③ 把"复现步骤转成自动化测试"的直接来源——**每章的产出都成为下一章的输入，链条由此接上。**

## 四、提示词模板：复现与界定 Bug（S-附录 B2-1）

这是 S-附录 里的 `复现与界定 Bug 提示词`（即 **S-附录 B2-1**，B2 专用），直接复制填空即可：

> 我遇到一个 Bug：`[一句话症状]`。请帮我把它稳定复现并界定清楚：
> ① 触发条件：什么输入 / 操作 / 环境下必然触发？列出最关键的 1–3 个触发因子；
> ② 实际输出：复现时实际得到什么（报错 / 返回值 / 界面表现），贴出证据；
> ③ 期望输出：按需求 / 业务直觉应该得到什么；
> ④ 影响范围：波及哪些功能 / 数据 / 用户，严重程度如何；
> ⑤ 最小复现步骤（MRE）：给出能复现它的最短操作路径，越短越好。
> 若某个触发因子我不确定，先按最可能的情况给一版，标注"待验证"，我再实测确认。

**逐字段解析（方便你按需增删）**：

- **`[一句话症状]`**：把用户那句"好像出错了"原样贴进去即可，越原始越好——模糊反而能激发 AI 反问，帮你把没说清的条件逼出来。
- **① 触发条件**：**最重要**——它决定"在什么情况下才要查"，也是 B2-② 定位根因的入口。
- **② 实际输出**：必须贴**证据**（报错原文 / 返回 JSON / 界面表现），不能写"反正不对"。
- **③ 期望输出**：按需求 / 业务直觉写"应该是什么"。**实际 vs 期望的差，就是 Bug 的定义。**
- **④ 影响范围**：判断严重程度——涉及金额 / 数据 / 多用户的高优先，先修。
- **⑤ MRE**：最短复现路径，别人照做能复现。**这是 B2-③ 写回归测试的原料。**
- **"待验证"标注**：AI 不确定的触发因子先标"待验证"，你实测后回报，别让 AI 替你拍板。

> 💡 **递归用法**：AI 给的第一版复现步骤往往太长或漏条件。**把它回喂，追加"请把复现步骤砍到最短，并标出哪些条件是我必须实测确认的"**，迭代 1–2 轮，直到"照做必现"。

> 连"一句话症状"也说不清？追加"请先按[行业]常见故障形态给我 2–3 个可能方向，我挑最像的那个再展开"——从"描述 Bug"变"挑方向"，门槛低一半；这条已在 S-附录·进阶操作速记「选填」下备案，照抄即用。

## 五、练习：复现 b2-bug 分支的 Bug1，产出复现说明

**任务**：在配套项目 `refund-shop` 的 **b2-bug 分支**上，复现 Bug1（0 元订单能创建），产出四要素复现说明。

**推荐步骤**：

1. 切到 b2-bug 分支：`git checkout b2-bug`，然后 `go run .` 起服务。（若提示 `bind: address already in use`，说明 3000 端口已被之前残留的服务占用——先 `Ctrl+C` 停掉旧进程或结束相应进程，再重新 `go run .`；启动成功后日志打印 `listen tcp :3000` 即端口就绪）
2. 用 B2-1 提示词，把症状"0 元订单居然能创建成功"丢给 AI，让它给出触发条件 / 实际 vs 期望 / 影响范围 / MRE 的初稿。
3. 亲手复现：`curl -X POST http://localhost:3000/api/orders -H "Content-Type: application/json" -d '{"product_name":"Free","amount":0,"shipping":0,"coupon_used":0}'`，记录实际返回（200 还是 400）。
4. 用二分法确认关键因子：把 amount 改成 1 再发一次，确认"amount=0 是关键因子"。
5. 用整合提示词把结果整理成四要素复现说明，存进项目 `docs` 目录。

> 📌 **B2 轨道的通用产出命名规范（统一口径）**：为了让 B2 各章的产出能像 B1 那样串成一条可查档的链，B2 每一步的沉淀文件统一按 `docs/<类型>-<bug-id>.md` 命名——复现说明 `reproduce-<bug-id>.md`、根因报告 `root-cause-<bug-id>.md`、修复说明 `fix-<bug-id>.md`、回归结论 `regression-conclusion-<bug-id>.md`。`<bug-id>` 就是你正在处理的 bug 标识（本项目里是 `Bug1` / `Bug2`，如 `docs/reproduce-Bug1.md`）；其他项目里替换成你自己的 bug 号即可。后续各章会各自回指这份命名。

**对答案**：你的复现说明应能回答"什么条件触发、实际得到什么、应该得到什么、影响多大"四个问题，并且第 4 步 MRE 别人照做能复现。**对照：Bug1 实际返回 200（订单创建成功），期望返回 400（amount must be > 0）。** 症状所在文件：`internal/routes/orders.go` 的下单校验处（`createOrder`，约第 55 行）——但**先别急着改**，那是 B2-② 定位根因的活。

> ⚠️ **对答案前，先预告一个可能的"假 Bug"**：Bug1 复现时，这段 0 元订单创建成功后，返回的订单 `status` 可能是 **`fully_refunded`**（因为订单状态由聚合 `SUM(approvedRefund) >= amount` 推导，`0>=0` 成立所以显示"已退完"）。**这是 Bug1 的结果的一部分，不是另一处 Bug**——别把它当成第二个问题去追。

> 🔎 **（可选进阶）再复现 Bug2**：下单 `amount: 10000` 后，第一次申请退 `3000` → 即被 400 拒（文案 `refund amount exceeds refundable quota`），期望应批准 `3000`。命令：`curl -X POST http://localhost:3000/api/refunds -H "Content-Type: application/json" -d '{"order_id":N,"amount":3000,"reason":"..."}'`（N 为上一步下单返回的订单 id）。症状所在文件：`internal/domain/refund_rules.go` 的可退余额计算（`CalcRemaining`，约第 43–46 行）。同样只复现、不深挖。
