用配套项目 `refund-shop` 的 **b2-bug 分支**继续举例（本章贯穿案例，两个预埋 Bug 的根因）：
- **Bug1 的根因**：`orders.go` 第 17 行有个**包级变量** `OrderMinAmount = 1`（订单金额下限）；第 54 行校验 `if req.Amount < OrderMinAmount` 原本能挡住 0 元。但 b2-bug 分支的 `internal/b2bug/inject.go` 在 `init()` 里把它改成了 `0` → 于是 `0 < 0` 为假，0 元就放行了。
- **Bug2 的根因**：`refund_rules.go` 第 13 行有个**全局开关** `ReverseRefundRemaining = false`，`CalcRemaining` 第 44 行本应 `remaining = orderAmount - totalRefunded`；b2-bug 分支的 `inject.go` 把它置 `true`，第 45–47 行就改用 `remaining = totalRefunded - orderAmount` → 剩余变成负数 → 被判成"已全退"。

> 📌 **行号以当前提交为准**（本教程项目处持续演进）：正文行号仅供快速定位参考，若你现在打开文件对不上，按**文件名 / 函数名 / 变量名**定位（如 `refund_rules.go` 里的 `ReverseRefundRemaining` 全局开关、`orders.go` 里的 `OrderMinAmount`），不要依赖绝对行号。

看清楚了吗？**两个 Bug 的代码"写法"没变，变的是被注入包改写了一个全局值**。这就是"症状 vs 根因"的绝佳教材——你以为根因在 `orders.go` 的校验写错，其实根因是"校验**依赖了一个可被外部改写的全局下限**"；这才是 B2-④ 真正要修的方向。

## 一、为什么必须先"定位根因"、而不是直接改？

| | 只改症状 | 先定位根因再改 |
|---|---|---|
| 你改的 | 表面不报错的那一行 | 数据真正变不对的那一行 |
| 换个输入 | 又复现（换汤不换药） | 不再复现（根子断了） |
| 改 A 坏 B | 常见（补丁盖帽） | 少见（改动有依据） |
| B2-③ 写测试 | 不知道该为哪个行为写 | 知道要锁哪个行为 |
| 判断"修好了没" | 说不清 | 对"根因行为"验证 |

> 一句话：**在根因上改一行，好过在症状上改十行。** 定位花的时间，几乎总能被 B2-④ 的"一次改对"赚回来。

## 二、通用方法：从"症状"走到"根因"

定位根因不是玄学，是两步可复制的动作：**先沿调用链把数据每一步看一遍，找到第一次变不对的那一跳；再对每个嫌疑点分清"症状 / 根因"，反向推断出真正的成因。**

### 🔴 目标一：沿调用链追溯，锁定"数据第一次变不对"的那一跳

**产出**：一条从"入口请求"到"症状出现"的**调用链**——每一跳都标出"文件:行号 + 这一跳数据变成什么"，并圈出数据**第一次变不对**的那一跳（嫌疑点）。

**要定位的本质**：一个请求从入口到出错，中间要过很多行代码。**根因必在"数据第一次偏离期望值"的位置**——在这之前数据都对，从这一跳开始就不对，后面全是连锁反应。沿调用链逐跳核对数据，就是给 Bug 画一条"价值流"，你会一眼看到它在哪里"跑偏"。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug2：减法方向倒置」 |
|------|----------|------------------------------|
| **入口** | 请求从哪进来？ | `POST /api/refunds` → `createRefund` |
| **参数** | 进函数时数据是什么？ | orderAmount=10000，totalRefunded=3000，applyAmount=3000 |
| **逐跳变换** | 每一跳数据变成什么？ | `CalcRemaining` 算 remaining |
| **第一次变不对** | 哪一跳数据开始偏离期望？ | `remaining` 算成了 -7000（期望 7000）← **嫌疑点** |

> ⚠️ **实例前提说明**：表中 `totalRefunded=3000` 的"先退过 3000 再退 3000"是**函数级推导示例**（用于演示减法倒置如何把 remaining 算成 -7000）。在 API 层因 Bug2 首次即拒，**累计场景实际无法经 API 触达**——真正让 Bug2 显形，是由 B2-③ 以单元红线测试用**函数参数直接复现**（不走 API）。

**照抄即用的通用追问提示词**（即 S-附录 **B2-2** 的 ①）：

> 从入口请求到症状出现，请逐跳列出调用链：每一跳给"文件:行号 + 这一跳数据变成什么"。
> 重点标出**数据第一次变不对**的那一跳（嫌疑点）；若中途有分支，把分出去的每条路各标一次。
> 任一步你拿不准就标"待验证"，别替我猜。

> 💡 **关键判断**：调用链画完后，**嫌疑点应该能收敛到 1–2 处**，而不是十处。如果 AI 列了一长串"可疑"，多半是还没切到"数据视角"，追问它"哪一跳的值偏离了期望值 7000"。**锁定嫌疑点，目标二才有对象。**（调用链分析本身可复用 S-A 第 2 步的"谁依赖谁"证据追问，这里只是把视角换成"数据怎么变的"。）

### 🔴 目标二：区分"症状"与"根因"，反向推断原委

**产出**：一份**根因论断**——用一句话说清"根因是什么、推导依据是什么、证据链长什么样"，并列出 1–2 个**待确认怀疑点**（值得实测/加日志验证的地方）。

**要定位的本质**：症状 = 用户看到的现象；根因 = 造成现象的代码与数据逻辑。**同一个症状可以由不同根因引起，同一个根因也会造成不同症状**（本案例 Bug2 的症状是"误报已全退"，但根因在减法方向被倒置）。所以拿到嫌疑点后，要**反向推断**：为什么这一行会算出这个错值？是条件写错、变量被改、还是数据状态不对？

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug2」 |
|------|----------|--------------|
| **症状** | 用户/表面看到什么？ | （含首次）申请退款就被报"余额不足/已全退"而不予批准 |
| **表面原因** | 一眼看到的可疑代码？ | `CalcRemaining` 里 `remaining <= 0` 触发了拒绝 |
| **真正根因** | 为什么这行会错？ | `ReverseRefundRemaining` 被置 true，减法方向倒置 |
| **证据链** | 从哪一行开始能证明？ | inject.go init() 改写全局开关 → remaining 变负 |

**照抄即用的通用追问提示词**（即 S-附录 **B2-2** 的 ②③④）：

> 基于上面这条调用链，请帮我：
> ② 对每个嫌疑点说明"这是症状（表象），还是根因（成因）"——凡是"改了症状仍复现"的，都标回表象，继续往下追；
> ③ 反向推断：结合代码 + 数据变化，推断根因到底是什么，给出一条可核对的推导链路；
> ④ 列出 1–2 个我还需要实测 / 加日志确认的怀疑点，别替我拍板。
> 要区分清楚："修复后 Bug 消失" ≠ "改对了根因"，我要的是那条能让旧复现步骤彻底不现的根因。

> 💡 **关键判断 · 怎么证明"这就是根因"**：反问 AI 一句话——**"如果我把这里改成 XXX，原来的复现步骤还会复现吗？"** 只有"改到这里后复现彻底消失"，才算碰到根因；若只是"这次不报错了"，那是补丁不是根因。（呼应 S-对话 的"证据追问"，别接受 AI 的猜测式结论。）

> 根因揪不出来也别慌：把"嫌疑点太多了看不完，请只给我 2–3 个'最可能是数据来源被改坏'的方向，我挑最像的展开"原样甩给 AI——从"被调用链淹没"变"在 AI 给的菜单里点菜"；读不懂某节原文时，话术见导读「读不懂？用 AI 帮你读本教程」（卡壳救助已收拢于此）。

## 三、把定位结果沉淀成「根因报告」（本步的产出物锚定）

你这一章要"交出去"的，是一份**根因报告**——B2-③ 写回归测试的依据（测什么行为才算锁住），也是 B2-④ 修复"到底改哪一行"的指路牌。它有固定结构：

```markdown
# 根因报告：<Bug 一句话症状>

## 1. 根因（一句话）
< 数据 / 代码在哪一行开始变不对，为什么 >

## 2. 推导链路（证据链）
- 入口：<文件:行号>，数据 = <期望值>
- 逐跳：<文件:行号>，数据变成 <实际值>
- 第一次变不对：<文件:行号> ← 根因所在
- 后续连锁：<受影响的表现>

## 3. 症状 vs 根因（刻意区分）
- 症状（表面）：<用户看到的现象>
- 根因（成因）：<造成现象的那一行 / 那个值>
- 若只改症状会出现：<换输入又复现 / 改A坏B>

## 4. 待确认怀疑点（1–2 个）
- [ ] <还需实测 / 加日志证实的点 1>
- [ ] <点 2，可能没有>
```

**怎么写（从二、的三份产出拼）？**
- **"根因一句话"**：取 目标一 锁定的嫌疑点 + 目标二 反向推断的结论，压缩成一句"哪一行 + 为什么错"。
- **"推导链路"**：取 目标一 的调用链，标注每一跳的数据值，把"第一次变不对"那一跳高亮。
- **"症状 vs 根因"**：取 目标二 的②③，明确区分；尤其写清"只改症状会怎样"的后果，防止 B2-④ 打补丁。
- **"待确认怀疑点"**：取 目标二 的④，**必须实测/加日志确认后才算数**，这是根因报告的"可信度声明"。

**检查标准**：读这份报告的人，能指着"根因一句话"说"哦，原来是这里改了 `XXX`"；并且"待确认点"要么已确认、要么明确标注未验证。**根因没确认 = 别进 B2-③。** 一个待确认点都没列出的根因报告，大概率是 AI 在替你拍板。

**整合提示词**（把二、的三份产出收拢成根因报告）：

> 请把下面几份产出整理成一份「根因报告」（四段：根因一句话 / 推导链路 / 症状 vs 根因 / 待确认怀疑点）。
> [粘贴：调用链 + 嫌疑点（目标一产出）]
> [粘贴：根因论断 + 证据追问结论（目标二产出）]
> [粘贴：待确认点清单]
> 要求：根因一句话不超过 40 字、能被第三个人看懂；推导链路标注文件:行号；症状 vs 根因必须各写一行；待确认点保持可勾选。输出 Markdown。

> 📌 这份根因报告正是 **B2-③ 前置里"以根因为输入"的那份**——B2-③ 要写的回归测试，就是"能不能把这个根因指认的行为锁死"。**每章的产出都成为下一章的输入，链条由此接上。**

## 四、提示词模板：定位根因（S-附录 B2-2）

这是 S-附录 里的 `定位根因提示词`（即 **S-附录 B2-2**，B2 专用），直接复制填空即可：

> 我已复现一个 Bug，复现说明如下：
> `[粘贴：B2-① 的四要素复现说明]`
> 我怀疑跟 `[疑似文件/函数，可空]` 有关。请帮我定位根因：
> ① 画调用链：从入口请求到症状出现，逐跳列出"文件:行号 + 这一跳数据变成什么"，标出数据**第一次变不对**的那一跳（嫌疑点）；
> ② 区分症状与根因：对每个嫌疑点说明"这是表象，还是真正根因"，防止只打补丁；
> ③ 反向推断：**先反证我的怀疑**——如果我怀疑的根因是错的，还有哪 2 个更可能的根因？各给一条反证路径；在能推翻我的怀疑之前，别顺着我的假设收敛。之后再基于代码 + 数据变化推断根因到底是谁，给出推导链路；
> ④ 待确认点：列出 1–2 个我还需要实测 / 加日志确认的怀疑点，别替我拍板。
> 任一步你拿不准就标"待验证"，我实测回报后再收敛。

**逐字段解析（方便你按需增删）**：

- **`[粘贴：四要素复现说明]`**：把 B2-① 的复现说明整份贴进去——尤其是"触发条件"和"实际 vs 期望输出"。**复现说明越准，根因定位靶子越清楚。**
- **`[疑似文件/函数，可空]`**：有怀疑就先填，没有就留空让 AI 从调用链入口自己找。**别因为猜了就不核对，AI 很可能顺着你的假设备错方向。**
- **① 画调用链**：定位的"骨架"——本质是把"数据一路怎么看"显性化，**焦点是"第一次变不对"，不是"最终报错"**。
- **② 区分症状与根因**：**本章的灵魂**。逼 AI 给每个嫌疑点定性"表象 / 成因"，把"改了仍复现"的统统打回。**防止只给一条"改这行就不报错"的补丁建议。**
- **③ 反向推断**：要求 AI 给出"为什么这里会错"的可核对链路，而不是一句结论。**没有链条的根因 = 猜测。** 本步刻意把"反证你的怀疑"放前面——**AI 是附和机，你猜哪它就容易顺着哪**；让它先提出 2 个能推翻你怀疑的候选并给反证路径，能逼它"唱反调"，避免一份"基于你错误假设的漂亮根因报告"。
- **④ 待确认点**：**守门员**。让 AI 交出"需要你实测/加日志"的地方，把"AI 拍板"的权力交回你手上——**你确认过的根因才算数。**

> 💡 **递归用法**：AI 第一版根因往往给得太糙（一句"校验写错了"就走人）。**把它回喂，追加"把每个结论钉到具体一行代码，并说明'为什么这行在数据上必然产生这个错值'；没有依据的结论删掉"**，迭代 1–2 轮直到每条都有证据链。

> 追到一半发现调用链太长、根本看不完？追加"先只追 [入口] → [症状所在函数] 这一段，命中就停"——聚焦到一小段，根的定位快一倍；这条已在 S-附录·进阶操作速记「选填」下备案，照抄即用。

## 五、练习：定位 b2-bug 分支两个 Bug 的根因

**任务**：基于 B2-① 的**两份**复现说明（Bug1 0 元下单 / Bug2 首次退款即被拒），各产出一份根因报告。

> ⚠️ **先补齐 Bug2 复现**：若你跳过了 B2-① 的「可选进阶 · 再复现 Bug2」，手里只有 Bug1 一份复现说明——请先回 B2-① 照该节命令补出 Bug2 的四要素复现说明（下单 `amount:10000` → 首次申请退 `3000` → 被 400 拒），再回来继续本章。

**推荐步骤（以 Bug2 为例）**：

1. 用 B2-2 提示词，把 Bug2 的复现说明贴给 AI，加上 `[疑似文件/函数] = internal/domain/refund_rules.go`。
2. 让 AI 画调用链：`POST /api/refunds`（`internal/routes/refunds.go`）→ `createRefund` → 读 orderAmount、totalRefunded（SUM approved）→ `domain.CalcRemaining` → 返回。标出"哪一跳 remaining 变负"。
3. 用 ②③ 逼 AI 区分症状与根因、给出推导链路。**重点追问**："为什么 remaining 会算出负数？是不是有个全局开关在起作用？"
4. 用 ④ 让它列出待确认点；**亲手验证至少一个**——在 `b2-bug` 分支上直接申请退 `3000`（首次即被 400 拒）跑一遍复现，或加一行日志打印 `ReverseRefundRemaining`，确认它确实是 `true`。
