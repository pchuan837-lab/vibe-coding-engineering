# B2-⑤ 验证与收尾

> **轨道**：B2 Bug 修复（已有功能行为不符合预期）第五步，也是 B2 轨道收尾。
> **前置**：B2-①~④ 完成，手里有**复现说明 / 根因报告 / 已红转绿的回归测试 / 修复说明**；配套项目 `refund-shop` 切到 **b2-bug** 分支。
> **目标**：做**全量回归**确认修复没弄坏任何已有功能，**同步文档与 CHANGELOG**（记清"修了什么、复现路径"），收尾交付。
> **预估时长**：20–40 分钟。

> 🧭 **本章自包含**：不需提前通读其他任何编号章节；要用到某个 `S-附录` 提示词时，我会在正文当处（章末的 📌）明确指出，你用到再看即可。（"前置"里的 B2-①~④ 产出的复现说明 / 根因报告 / 已红转绿测试 / 修复说明，都是**输入材料**，不是要你回头通读那几章）

> 🧭 **本章怎么读**：主线走完全程（约 20–40 分钟）；只想先跑通？→ 本章最少做：①跑一次全量测试，见"全绿、无回归" ②CHANGELOG 记一条"修了什么 + 复现路径"（交付物清单核对返工再补）；详见导读「三条路线图」·新手极简·B2⑤ 行。只想看核心方法？→ 见导读 ·老手精华。省步骤 ≠ 省产出物，跳过的正是返工回来补的。

```text
①复现界定→②定位根因→③回归测试→④修复
                              ↓
[⑤验证收尾]→⑥回归强化→⑦文档交付→⑧工具固化
```

> 📍 **当前位置：B2 轨道 · 第 5 / 8 步**（上图 `[⑤]` 即你所在步骤）。①~⑤ 即本轨道五章；⑥~⑧ 复用共享单元 S-B/S-C/S-D 做强化。

前面四步，我们把一个 Bug 从"一句症状"钉成了"已转绿的最小修复"。但**一单修复到手，不代表可以收工**——你只证明了"那条测试绿了"，还没证明"别的功能没被它弄坏"。B2-⑤ 就是给整条链路收个结实的尾：**全量回归确认无破坏 + 把"修了什么、怎么复现"写进文档，让这次修复可追溯、防再犯。**

> 一句话：**验证与收尾 = 向全项目证明"这次修复是安全的可合并"，并把教训固化下来。**
>
> 这章大量复用 [S-B · 测试与回归]（全量回归 S-6、测试报告 S-7）和 [S-C · 文档同步与交付]（API/文档同步 S-8、CHANGELOG S-10），本轨道不重写通用方法，只强调最后两个动作——**复现路径必须记进 CHANGELOG** 和 **区分"修复引入的失败"与"本来就有"的失败**。

用配套项目 `refund-shop` 的 **b2-bug 分支**继续举例（本章贯穿案例，两个 Bug 的收尾）：
- **Bug1 + Bug2 修复后的全量回归**：跑 `go test ./...` 应全绿——因为修复让 b2-bug 分支重新对齐了 main 的正确行为，`orders_route_test.go` 与 `refund_rules_test.go` 里那些"在 b2-bug 上原本红"的测试现在全部转绿，且其它用例不被破坏。
- **CHANGELOG 要写的两行**：Bug1"下单金额下限于 0 元不再放行（复现：amount=0 传 /api/orders 应 400）"；Bug2"可退余额减法方向倒置致退款被误拒（复现：订单金额 10000，申请退 3000 返 400，期望批准 3000）"。
- **收尾的意义**：这两行 CHANGELOG + 那条转绿的测试，就是"这个 Bug 修好了、且以后不会再悄悄回来"的双保险。

## 一、为什么"修好了"还要单独做一章"验证与收尾"？

| | 只修不验 | 修复 + 验证与收尾 |
|---|---|---|
| 你掌握的 | "那条测试绿了" | "全项目没被弄坏" |
| 别处被误伤 | 发现不了，走人后炸 | 全量回归当场抓出 |
| 日后追溯 | 几个月后"这是改哪了？" | CHANGELOG + 测试留痕清晰 |
| 防再犯 | 没人记得那复现路径 | 测试 + CHANGELOG 双重锁死 |
| 合并判断 | 拍脑袋 | 用证据说"可合并" |

> 一句话：**"修好一个 Bug"和"安全地交付这次修复"是两件事。** B2-⑤ 把后者也钉死。

## 二、通用方法：让"修复"变成"安全可合并的交付"

### 🔴 目标一：全量回归——证明"没弄坏别处"

**产出**：一份**全量回归结论**——`go test ./...` 全绿、受影响模块的既有用例未被破坏，且能区分"这次修复引入的失败"与"本来就有的失败"。

**要回归的本质**：你只动了根因一两行，但这一两行可能被别的调用者依赖。全量回归 = 把"没弄坏别处"从口头保证变成测试输出。关键是**别把回归失败一股脑算到这次修复头上**——要判断它是不是"本来就在红"的存量问题。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug1 + Bug2 修复后」 |
|------|----------|------------------------------|
| **全量命令** | 怎么跑全部测试？ | `go test ./...` |
| **受影响模块** | 这次改动连带会碰哪？ | routes（orders/refunds）+ domain（金额计算） |
| **失败归类** | 失败是新引入还是存量？ | 高亮本次修复相关用例，区分存量红 |
| **结论** | 全绿可合并？ | 全绿 → 可合并 |

**照抄即用的通用追问提示词**（即 S-附录 **B2-5** 的 ①）：

> 我已完成修复，请帮我做全量回归：
> ① 列出应跑的回归命令（全量 + 关键定向）与受影响模块；
> ② 若跑出失败，逐条判断是"这次修复引入"还是"本来就在红"（对照修复前基线）；
> ③ 给我一份"是否可合并"的结论。

> 💡 **关键判断**：全量回归的合格线 = **全绿，或失败全部判为存量**。**只要有"说不清是不是这次改的"红灯，就先别合并**——回到 B2-④ 检查是不是真的没蔓延。

---

### 🔴 目标二：复现闭环——把原复现步骤再走一遍，确认"彻底不现"

**产出**：一次**复现闭环确认**——B2-① 的原始复现步骤（人工 + 那条已红测试）在修复后都不再复现。

**要闭环的本质**：测试转绿是自动化证据，人工把原始步骤再点一遍是"眼见为实"。两者都过，才敢说"这个 Bug 确实没了"。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug1」 |
|------|----------|--------------|
| **自动化** | 那条已红测试现在绿？ | `TestCreateOrder_ZeroAmount_Returns400` 绿 |
| **人工** | 原 MRE 再跑还复现吗？ | `curl … -d 'amount:0'` → 400，不成功 |
| **等价输入** | 同类触发点还复现吗？ | amount=-1 也 400 |
| **结论** | 彻底不现？ | ✅ 闭环 |

**照抄即用的通用追问提示词**（即 S-附录 **B2-5** 的 ②）：

> 请给我一份"复现闭环"核对清单：
> · 哪条已红测试现在绿了？哪条命令？
> · 原复现步骤（B2-① MRE）人工再走一遍结果如何？
> · 同类触发点（等价输入）还复现吗？
> 逐项勾选，缺一项都不算闭环。

> 💡 **关键判断**：闭环 ≠ "那条测试绿了"那么简单。**要回到 B2-① 的原始 MRE 亲自再走一遍**——因为测试可能没覆盖到所有等价输入。原步骤 + 测试都"不现"，才算封死。

### 🔴 目标三：同步文档与 CHANGELOG——把"修了什么 + 怎么复现"写进历史

**产出**：一条** CHANGELOG 条目**（修什么 + 复现路径）+ 受影响接口/设计文档已同步（以代码为准）。

**要同步的本质**：修完一个 Bug，文档里的"正确行为描述"可能已不再是修复前那句。用 S-C 的"以代码为准"原则，把 CHANGELOG、接口说明、设计文档刷新一遍——**重点是把"复现路径"记进去**，这是 B2 轨道防再犯的独有动作。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug1」 |
|------|----------|--------------|
| **CHANGELOG** | 修了什么 + 复现路径？ | "修复：amount<=0 订单被放行；复现：POST /api/orders amount=0" |
| **接口文档** | 行为描述还对得上代码？ | 下单接口"0 元应拒 400"是否已写明 |
| **设计文档** | 全局下限的依赖关系是否记录？ | 应注明"校验不依赖可改全局下限" |
| **以代码为准** | 改完是否回扫了一遍？ | 用 S-8 按最终代码核对 |

**照抄即用的通用追问提示词**（即 S-附录 **B2-5** 的 ③）：

> 修复已就位，请帮我同步文档：
> · 更新 CHANGELOG：写一行"修复什么 + 复现路径"（别人照能复现）；
> · 检查受影响接口/设计文档是否与最终代码一致（以代码为准）；
> · 指出哪些文档描述已过时，给出修正。
> 复用 S-C 的同步方法，别只改 CHANGELOG 就交差。

> 💡 **关键判断**：CHANGELOG 里那句话必须是**可复现**的（带触发方式），而不是"修复了某个 bug"这种空话——否则它就是"防再犯"的失效哨兵。对照 S-C（S-8/S-10）的写法。

> 回归红了 / 文档对不上也别慌：把"①这条回归红是这次修复引入的还是本来就有（给基线证据）②只列确实被这次改动影响的文档，别让我从头翻全库"丢给 AI——从"被回归和文档淹没"变"只盯两件最要命的事"；读不懂某节原文时，话术见导读「读不懂？用 AI 帮你读本教程」（卡壳救助已收拢于此）。

## 三、把验证结果沉淀成「回归结论 + CHANGELOG 条目」（本步的产出物锚定）

你这一章要"交出去"的，是**回归结论**（全绿 + 无回归）和** CHANGELOG 条目**（修什么 + 复现路径）。它是 B2 轨道"修好了、可合并"的盖章，也是日后防再犯与追溯的档案。固定结构：

```markdown
# 回归结论：<Bug 一句话症状>

## 1. 全量回归
- 命令：<go test ./...>
- 结果：全绿（或列出存量失败并说明与本次无关）
- 受影响模块：<routes: orders/refunds；domain: 金额计算>

## 2. 复现闭环
- [x] 已红测试转绿：<TestCreateOrder_ZeroAmount_Returns400> → PASS
- [x] 原 MRE 人工复跑：<curl amount=0 → 400，不成功>
- [x] 等价输入不现：<amount=-1 也 400>

## 3. CHANGELOG 条目（可复现）
- Fixed: <amount<=0 订单被放行>（复现：POST /api/orders 传 amount=0 应 400）

## 4. 收尾判断
- 交付物完整：<修复说明 / 回归测试 / 本结论>
- 结论：<可合并 / 待修复及原因>
```

**怎么写（从二、的三份产出拼）？**
- **"全量回归"**：取 目标一 的命令 + 结果 + 失败归类。
- **"复现闭环"**：取 目标二 的勾选清单，逐项打勾。
- **"CHANGELOG 条目"**：取 目标三 写的可复现那句话。
- **"收尾判断"**：汇总三份产出，给出**明确的可合并结论**——这是 B2 轨道最后的"交付感"。

**检查标准**：读这份结论的人，能回答"全量绿没绿、原复现还现不现、CHANGELOG 记的复现路径别人照做能不能复现、能不能合并"。**回归不绿 / 复现仍现 = 收尾未完成。** 一条没写"复现路径"的 CHANGELOG 不算数。

**整合提示词**（把二、的三份产出收拢成回归结论 + CHANGELOG）：

> 请把下面几份产出整理成一份「回归结论」：
> [粘贴：全量回归结果][粘贴：复现闭环勾选清单][粘贴：CHANGELOG 条目]
> 按 全量回归 / 复现闭环 / CHANGELOG 条目 / 收尾判断 四段输出，收尾判断给明确"可合并 / 待修复"。输出 Markdown。

> 📌 这份"回归结论"让 **B2 轨道 ①~⑤ 闭环**——从"症状"走到"可合并的修复"，每一步的产出都成为下一步输入，链条完整闭合。步入 **⑥ S-B 回归强化**后，你的回归测试会进入 CI/测试体系，固化成长期守门员。

## 四、提示词模板：验证与收尾（S-附录 B2-5）

这是 S-附录 里的 `验证与收尾 提示词`（即 **S-附录 B2-5**，B2 专用），直接复制填空即可：

> 我已完成一个 Bug 的最小修复，修复说明如下：
> `[粘贴：B2-④ 的修复说明]`
> 请帮我做「验证与收尾」：
> ① 全量回归：列出应跑的回归命令与受限影响的模块，断言修复没弄坏已有功能；
> ② 复现闭环：重跑原复现步骤 + 那条已红转绿的测试，确认彻底不再复现；
> ③ 文档同步：更新 CHANGELOG（修了什么 + 复现路径）与受影响接口/设计文档（复用 S-C，以代码为准）；
> ④ 收尾清单：核对 交付物 / 测试报告 / 提交信息，给我一条"可合并"的最终判断。
> 若回归有失败，先区分"修复引入"还是"本来就有"，别急着认定是这次改的。

**逐字段解析（方便你按需增删）**：

- **`[粘贴：修复说明]`**：贴 B2-④ 的修复说明——它定义了回归的边界（改了什么 = 该验什么）。
- **① 全量回归**：要命令 + 受影响模块 + **失败归类**。"受限影响模块"这半句，防止拿全库当靶子。
- **② 复现闭环**：**自动化（转绿测试）+ 人工（原 MRE 复跑）+ 等价输入**三关都过才算闭环。
- **③ 文档同步**：**"复现路径必须进 CHANGELOG"** 是 B2 专属动作，别只写"Fixed 某 bug"。复用 S-C 的以代码为准。
- **④ 收尾清单**：拿"可合并 / 待修复"的最终判断——**这是 B2 轨道的盖章，要有明确结论**。
- **"若回归有失败…"**：防止把存量红误嫁给这次修复，也防止这次引入的红被掩盖。

> 💡 **递归用法**：AI 第一版 CHANGELOG 常写成"修复了 0 元下单"这种不可复现空话。**把它回喂，追加"把复现路径补成别人照做能复现的一两步（含触发输入与期望输出），并核对这条是不是'可复现'而非笼统描述'"**，迭代 1–2 轮直到可复现。

> 回归范围一时列不全？追加"按我这次改动的调用链，只列出确实会被波及的模块与用例，别让我从全库一个个看"——从"全库覆盖"变"改动链定向"，快得多；这条已在 S-附录·进阶操作速记「选填」下备案，照抄即用。

## 五、练习：对 b2-bug 分支的两条修复做全量回归 + 收尾

**任务**：在 `refund-shop` 的 **b2-bug 分支**上，对 B2-④ 修好的两个 Bug 做验证与收尾，各产出一份回归结论 + 一条 CHANGELOG 条目。

**推荐步骤（以 Bug1 为例）**：

1. 用 B2-5 提示词，把 Bug1 的修复说明给 AI。
2. 全量回归：`go test ./...` → 期望**全绿**（修复让 b2-bug 分支对齐 main 正确行为，原本红的测试全部转绿）。
3. 复现闭环：自动（重跑 `TestCreateOrder_ZeroAmount_Returns400` → 绿）+ 人工（`curl -X POST http://localhost:3000/api/orders -H "Content-Type: application/json" -d '{"product_name":"Free","amount":0}'` → 400）+ 等价输入（amount=-1 → 400）三关全过。
4. 文档同步：往 `CHANGELOG.md` 补一条可复现的 Fixed 条目；检查 `docs/api-reference.md` 里下单接口"0 元应拒"是否与代码一致。
5. 用整合提示词产出「回归结论」，存为 `docs/regression-conclusion-<bug-id>.md`。
6. **（Bug2 同样流程）**：全量回归确认绿；复现闭环（`TestCalcRemaining_Bug2ReverseRemaining_Apply5000After3000_Approved` 绿 + 订单 10000 首次申请退 3000 不再返 400、正常批准 3000）；CHANGELOG 补"可退余额减法方向倒置致退款被误拒"条目。

**对答案**：两份回归结论都应含"全量回归 / 复现闭环 / CHANGELOG 条目 / 收尾判断"四段，收尾判断为"可合并"，且 CHANGELOG 里的复现路径别人照做能复现。

- **Bug1**：`go test ./...` 全绿；`TestCreateOrder_ZeroAmount_Returns400` PASS；人工 curl amount=0 → 400；CHANGELOG 写法示例：`Fixed: 0 元订单被错误创建（复现：POST /api/orders 传 amount=0 应返回 400）`。
- **Bug2**：`go test ./...` 全绿；`TestCalcRemaining_Bug2ReverseRemaining_Apply5000After3000_Approved` PASS（同域 `Apply8000OnFresh_Approved`、`Apply1After3000_Approved` 亦绿）；订单 10000 首次申请退 3000 不再返 400、正常批准 3000；CHANGELOG 写法示例：`Fixed: 可退余额减法方向倒置致退款被误拒（复现：订单金额10000，申请退3000 返400，期望批准 3000）`。
- **收尾判断依据**：全绿 + 复现彻底不现 + CHANGELOG 可复现 → 可合并。

> 🔎 **（可选进阶）切回 main 对照**：把两个 Bug 的修复提交到本地分支后，`git checkout main` 对比确认 main 的正确实现与你删掉 `inject.go` 依赖后一致——体会"真正的修复 = 让 b2-bug 分支的行为回归 main 的正确行为"。
