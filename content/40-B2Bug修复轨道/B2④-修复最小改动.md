## 一、为什么"最小改动"这么重要？

| | 大改动/顺手重构 | 最小改动 |
|---|---|---|
| 引入新 Bug 的风险 | 高（改了 A 弄坏 B） | 低（边界极小） |
| 回归测试能不能兜住 | 难判断"哪处弄坏的" | 改一处盯一处 |
| 回滚/审查 | 难（一堆无关 diff） | 容易（一两个文件几行） |
| 语义 | 把 Bug 修复混进了重构 | 只表达"把这个 Bug 修掉" |

> 一句话：**最小改动 = 最小爆炸半径。** 修复还混着重构，等于给审查人和你自己埋雷。

## 二、通用方法：把已红的测试改成绿，且只动根因那一两行

### 🔴 目标一：对照根因报告，圈出"要改的那一点"（最小 diff 圈定）

**产出**：一份「改动圈」——只含根因报告"第一次变不对"那一步依赖的**文件 + 具体行**，明确"其余一律不碰"。

**要圈定的本质**：改动范围 = 根因的**边界**。根因报告已经告诉你"数据在哪一行开始变不对"，改动就落在那一行及其直接依赖上。**别顺着报错栈往下蔓延，也别顺手清理"看着不爽"的代码。**

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug1」 |
|------|----------|--------------|
| **根因行** | 数据/判定在哪一行开始错？ | `orders.go` L54 `if req.Amount < OrderMinAmount` |
| **直接依赖** | 这一行依赖哪个可改状态？ | `OrderMinAmount`（L17 全局可写） |
| **只动这里** | 改动是否唯一、不蔓延？ | 只改校验判定，不碰插库/返回/其它路由 |
| **不动什么** | 明确"红线内不得碰"？ | 不动 `inject.go`、不动 6 个端点的其它逻辑 |

**照抄即用的通用追问提示词**（即 S-附录 **B2-4** 的 ①④）：

> 按这份根因报告，请圈出"最小改动"范围：
> · 只看"第一次变不对"那一步依赖的代码，列出将改的**文件 + 具体行**；
> · 明确**不碰**哪些（无关模块 / 接口 / 可以后说的重构点）；
> · 若你建议顺手改别的文件，先说明为何**必要**，我确认后再动。

> 💡 **关键判断**：改动圈的判定标准 = **"删掉这次改动，Bug 又在"**。多改一行是浪费，少改一行是补丁。拿 Bug1：真正的改动方向是让校验不再依赖可改的下限（比如直接 `if req.Amount <= 0 { 400 }`），而不是新增一个"仅挡 0 元"的 if——后者是盖帽。

---

### 🔴 目标二：修根因而非打补丁，让旧复现"彻底消失"而非"这次不报错"

**产出**：一条**修复方向评判**——改完后，原复现步骤换任何等价输入都不再复现（而非仅当前那一次不报错）。

**要判断的本质**：补丁 vs 修复的差别一眼可见——**补丁堵的是触发点，修复祛的是病灶**。判定方法就是 B2-② 那句反问：**"改完后，原复现步骤还会复现吗？"** 若换个输入仍复现，说明只盖了帽。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug1」 |
|------|----------|--------------|
| **触发点** | 该堵住"这一次"，还是消除"这一类"？ | 0 元一次 / 凡 `amount <= 0` 均拒 |
| **全局依赖** | 判定是否还在依赖可改状态？ | 是 = 补丁；否（独立判负）= 修复 |
| **旧复现** | 改成后旧步骤还能复现吗？ | 修好 → amount=0 永远 400，不可复现 |
| **变体输入** | 同根因其它输入会不会再炸？ | `amount=-1` 也一并被拒 → 说明修到根上 |

**照抄即用的通用追问提示词**（即 S-附录 **B2-4** 的 ②）：

> 请对这份改动做"修根因 vs 打补丁"自检：
> · 反问：改完后，原复现步骤**还会复现吗**？若只需换一个等价输入（如把 0 换成 -1）就又能触发，说明还在打补丁，退回继续改；
> · 说明你改的是"消除这一类"（根因）还是"堵住这一次"（触发点）。

> 💡 **关键判断 · 本案例的经典陷阱**：有人修 Bug1 时会顺手改 `inject.go` 把 `OrderMinAmount` 改回 1——**那是改错对象**。因为 `inject.go` 是刻意让行为"能被打乱"的注入点，把它修好等于"让 Bug 从根上随时能被重新注入"。真正的修复方向是**让业务代码不依赖这个可写开关**——`inject.go` 再怎么改，`amount<=0` 也进不来。**病灶的判断标准：删掉这个可改状态，代码是否依然正确。**

### 🔴 目标三：先转绿——只跑那条已红测试，确认红变绿

**产出**：一次**定向转绿**——那条已红回归测试从 FAIL 变 PASS，且未跑无关全量（先聚焦，别混入其它失败）。

**要转绿的本质**：修复完成的"硬证据"是那条测试由红变绿，而不是"我肉眼看逻辑对了"。先定向跑它，绿了再谈全量回归（那是 B2-⑤）。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「Bug1」 |
|------|----------|--------------|
| **定向命令** | 只跑那一条怎么跑？ | `go test -run TestCreateOrder_ZeroAmount_Returns400 ./internal/routes/` |
| **改前状态** | 修复前它是红吗？ | 是（want 400, got 200） |
| **改后状态** | 修复后变绿吗？ | 绿（400）|
| **别混跑** | 先不跑全量，避免干扰？ | 定向跑，全量留给 B2-⑤ |

**照抄即用的通用追问提示词**（即 S-附录 **B2-4** 的 ③）：

> 改动已就位，请给出**定向转绿**验证：
> · 只跑那一条已红测试的命令（含路径）；
> · 提交前贴出"修复前红 / 修复后绿"两次输出，确认转绿原因正是这次改动。

> 💡 **关键判断**：转绿的条件 = **改动前后的唯一变量是这次 diff**。如果转绿的同时你还改了其它逻辑，这条测试"变绿"就不足以证明修复有效——你可能在掩盖。所以**先只做最小 diff，再跑那一条**。

> 改着改着越改越多也别慌：把"停一下：我现在的目标是最小修复这个 Bug 不是重构，请把这次改动的文件收敛到根因报告圈定的范围，把顺手想改的地方单独列到待办重构清单，这次别动"给 AI——从"修复滑向重构"回到"最小 diff 正道"；读不懂某节原文时，话术见导读「读不懂？用 AI 帮你读本教程」（卡壳救助已收拢于此）。

## 三、把修复沉淀成「修复说明」（本步的产出物锚定）

你这一章要"交出去"的，是一份**修复说明** + 那条测试**已转绿**的事实。它是 B2-⑤ 全量回归的对象，也是日后追溯"这个 Bug 当年怎么修的"的存档。固定结构：

```markdown
# 修复说明：<Bug 一句话症状>

## 1. 改动清单（最小 diff）
- 文件：<文件:行号>
- 改动：<把什么改成什么，一两行>
- 改动量：<+N/-N 行>

## 2. 为什么这样改（指向根因）
- 根因：<B2-② 根因一句话>
- 改后根因行为是否消失：<是——amount<=0 一律 400，不再依赖可改下限>

## 3. 定向转绿证据
- 命令：<go test -run XXX ./...>
- 修复前：FAIL（<want 400, got 200>）
- 修复后：PASS
- 唯一变量：<只做了上面这些 diff>

## 4. 明确不碰
- 未改：<inject.go / 其它 5 个端点 / 排序分页等无关逻辑>
```

**怎么写（从二、的三份产出拼）？**
- **"改动清单"**：取 目标一 的改动圈，落到具体行 + 改动量。
- **"为什么这样改"**：取 目标二 的修根因判断，写明"改后根因行为消失、未依赖可改状态"。
- **"定向转绿证据"**：取 目标三 的红→绿输出，**务必写"唯一变量"** 证明是这次 diff 生效。
- **"明确不碰"**：取 目标一 的红线，列清没动哪些，防止误伤。

**检查标准**：读这份说明的人，能复现命令重现"改前红、改后绿"，且相信"只动了几行、没碰别的"。**测试没转绿 = 修复未完成，别进 B2-⑤。**

**整合提示词**（把二、的三份产出收拢成修复说明）：

> 请把下面几份产出整理成一份「修复说明」：
> [粘贴：改动圈（文件+行+diff）][粘贴：修根因判断][粘贴：定向转绿红绿证据][粘贴：不碰清单]
> 按 改动清单 / 为什么这样改 / 定向转绿证据 / 明确不碰 四段输出，命令可复制。输出 Markdown。

> 📌 这份"已转绿的修复"正是 **B2-⑤ 前置里"以修复为输入"的那份**——B2-⑤ 要做全量回归，确认它没弄坏任何其它功能。**每章的产出都成为下一章的输入，链条由此接上。**

## 四、提示词模板：修复（最小改动）（S-附录 B2-4）

这是 S-附录 里的 `修复 提示词`（即 **S-附录 B2-4**，B2 专用），直接复制填空即可：

> 我有一条已红的回归测试，根因报告如下：
> `[粘贴：B2-② 的根因报告]`
> `[粘贴：那条已红测试 + 当前 FAIL 输出]`
> 请帮我做「最小改动」修复：
> ① 最小 diff：只看根因报告"第一次变不对"那一步依赖的代码，列出将改的文件 + 具体改动行，不做无关重构；
> ② 修根因而非补丁：反问"改完后原复现步骤还会复现吗"——若只是"这次不报错"而旧复现仍会被其他输入触发，退回继续改；
> ③ 先转绿：给出跑那条已红测试的命令，确认修复前红、修复后绿；
> ④ 不蔓延：确认改动没有波及无关模块 / 接口。
> 若你建议顺手重构或改多余文件，先说明为何必要，我确认后再改。

**逐字段解析（方便你按需增删）**：

- **`[粘贴：根因报告]` + `[粘贴：已红测试 + FAIL 输出]`**：把 B2-②、B2-③ 两份输入并排贴上——一起给出的效果是"AI 既知道改哪、也知道怎么验"。
- **① 最小 diff**：核心约束——**只动根因那一步，不做无关重构**。让 AI 先列文件 + 行，你确认范围再动手。
- **② 修根因 vs 补丁**：**本章的灵魂**。"改完还会复现吗"这句反问，专门掐掉"盖帽修复"。**强调"换等价输入也应被挡"才算祛病灶。**
- **③ 先转绿**：要"修复前红 / 修复后绿"两次输出，**并要它确认转绿的唯一变量就是这次 diff**。
- **④ 不蔓延**：收口的约束——**连带改动必须说明"为什么必要"**，防止修复边上悄悄夹带重构。

> 💡 **递归用法**：AI 第一版修复常常给"看起来对、但偷偷动了别处"的方案。**把它回喂，追加"把这次改动压到最小之外的所有建议列成单独的'待办'，不混进本次修复；并逐行说明为什么这一行是非改不可的根因行"**，迭代 1–2 轮直到 diff 收敛到根因几行。

> 该改这一处还是那一处拿不准？追加"把这两种做法的行为差异用大白话讲给我听，并说明各改一处后旧复现会怎样，我懂了再挑"——只降门槛不替你拍板；这条已在 S-附录·进阶操作速记「选填」下备案，照抄即用。

## 五、练习：最小改动修复 b2-bug 分支的两个 Bug

**任务**：在 `refund-shop` 的 **b2-bug 分支**上，各做一次最小改动修复，让两条已红测试转绿，各产出修复说明。

**对答案**：两份修复说明都应含"改动清单 / 为什么这样改 / 定向转绿证据 / 明确不碰"四段，命令可复现"改前红、改后绿"。

- **Bug1 最小 diff（示意）**：`orders.go` 校验从 `if req.Amount < OrderMinAmount` 改为 `if req.Amount <= 0`（或用不可改写的常量下限）。**改动后 `TestCreateOrder_ZeroAmount_Returns400` 绿**；且 `amount=-1` 同样被拒，说明祛的是"非法金额"这一根因，不止挡 0 元。

- **共同铁律**：两个 Bug 都没改 `inject.go`——因为注入点是"能让行为打乱"的教学装置，病灶是"业务判定依赖了可被外部改写的全局状态"。改法让 `inject.go` 再怎么注入也无法让 0 元下单 / 倒置减法生效，才是真·根因修复。

> 🔎 **（可选进阶）验证"病灶=全局依赖"**：修好后，把 `inject.go` 的注入暂时加回去（不改它，只是验证）再跑那两条测试——**应当仍绿**。绿色说明你的修复不再被注入点影响；若变红，说明你还在依赖开关，病没断根。
