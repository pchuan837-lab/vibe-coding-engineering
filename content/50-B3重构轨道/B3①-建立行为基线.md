> 📍 **当前位置：B3 轨道 · 第 1 / 5 步**（上图 `[①]` 即你所在步骤）。

B3 和 B2、B1 最大的不同在这里——**B1 从无到有、B2 把错的改对，而 B3 是"行为完全不变、只把内部结构改好"**。正因"不该有任何可见变化"，你改的时候最容易翻车的就是：**改着改着，把行为也悄悄改了**。所以 B3 动手第一件事不是改，而是**先给"现在长什么样"拍一张照片**——这张照片就是行为基线。

> 一句话：**重构的安全带，是重构前先给自己套上的行为基线。没基线就重构，等于蒙眼换零件。**

用配套项目 `refund-shop` 的 **main 分支**举例（本章贯穿案例，三处待重构的坏味道，节奏铺垫到 B3-② 才正式点名）：

- **待重构点二（schema 混写）**：`db/schema.sql` 单文件混写 orders / refunds 两表 + 3 个索引，无版本管理。
- **待重构点三（规则堆 if-else）**：`domain/refund_rules.go` 的 `CalcRemaining` 有一大串边界 if-else。

注意：**本章先不对这三处下任何"好坏"判断**（那是 B3-② 的事）。本章只做一件事——**把它们当前的行为用测试锁死、跑绿**。改完它们，重跑这些基线测试，绿 = 没变味，红 = 你改坏了行为。

## 一、为什么重构前必须先拍"行为基线"这张照片？

| | 直接动手重构 | 先建行为基线再重构 |
|---|---|---|
| 你怎么知道"行为没变" | 靠"看起来还能跑" | 基线全绿 = 铁证 |
| 改到一半出事 | 不知道哪步弄坏的 | 每步跑基线，当场定位 |
| 隐性错误 | 边改边"顺手修掉"，越俎代庖 | 基线上标注"这只是现状"，交给 B2/需求处理 |
| 交给别人改 | 说不清"原来怎样" | 基线 = 一份"现状契约" |

> 一句话：**行为基线的价值 = 给"行为不变"一个可核验的定义。** 它不是普通测试——它**不判断你现在这样对不对**，只负责记住"你现在就是这样"。

**关键：characterization test 和你在 B2 / S-B 见过的测试不是一回事**：

| 测试类型 | 有没有"应该"的预期 | 用途 | 你会在哪见过 |
|---|---|---|---|
| 需求测试 | 有，应如何 | 验"做了要的功能" | B1 / S-B 正常用例 |
| 回归测试 | 有，防再犯 | 锁 Bug 修好不再冒 | B2-③ 红线测试 |
| **行为基线（characterization）** | **无，锁现状** | 重构安全网 | **本章 B3-①** |

**决定这个区别的一句话**：行为基线测试的断言写的是**"现在跑出来就这样"**，而不是"就应该这样"。这样即使当前代码有隐性 bug，你也**不替它做主**——你在基线上标一句"此断言仅为现状"，改坏与否只和"现状"比，不和"理想"比。（隐性错误该不该修、怎么修，是 B2 轨道的事，别在重构时夹带。）

## 二、通用方法：把"重构前的现状"钉成可跑的全绿基线

复用 [S-B] 的测试用例 / 生成 / 失败分析三环节，本轨道在这之上加一道 B3 特有的动作：**先界定重构范围，只对将被重构的那段建基线**。三个目标：

### 🔴 目标一：界定重构范围，只给"要动的那几处"建基线

**产出**：一份**范围清单**——明确"本次只重构这几处代码"，行为基线只覆盖它们（及其直接调用链），不铺满全库。

**要界定的本质**：基线不是越全越好——**全库铺基线会拖慢节奏、制造噪音**。B3 的纪律是"小步重构"，基线跟着"这一步要动的那一段"走，先建、改完、再进下一步。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「main 分支」 |
|------|----------|------------------|
| **对象** | 这次重构成什么？（函数/文件/路由） | 3 处坏味道：handler 样板 / schema / CalcRemaining |
| **调用链** | 它被谁调用，动它会影响谁？ | createOrder 被 RegisterOrders 与 /api 路由挂载调用 |
| **边界** | 明确"这次不碰的" | 其它后端逻辑、重构期间的数据库 schema 变更 |
| **范围** | 基线只覆盖上面这些？ | 只给 3 处坏味道建基线，不铺全库 |

**照抄即用的通用追问提示词**（即 S-附录 **B3-1** 的 ①）：

> 我准备重构 `[粘贴：代码文件 + 要动的函数/路由]`，请先帮我界定行为基线的范围：
> · 只覆盖我将重构的这段代码及其直接调用链；
> · 明确这次**不碰**的部分，基线不用覆盖；
> · 给出每处要建的基线测试文件与覆盖点清单。

> 💡 **关键判断**：范围的合格线 = **"这次 B3-④ 每改一步，都能用对应基线验证"**。范围太大 → 一步改一堆、错了难定位；范围太小 → 漏了调用方，改断连接没人发现。**先窄后宽，宁可多建两轮。**

---

### 🔴 目标二：从调用点提取输入输出样本，生成"锁现状"的基线测试

**产出**：一批 **characterization tests**——对当前代码的"输入→输出"逐条记录，**不判断对错、只锁现状**，含正常 / 边界 / 报错三分支。

**要生成的本质**：行为基线的断言来源不是"需求文档"，而是**你亲手从调用点采到的真实输入输出样本**。拿 `CalcRemaining` 来说——它现在对 "orderAmount=0" 返回啥？对 "申请超额" 返回啥？把这些**实跑结果**写进断言，就是基线。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「CalcRemaining」 |
|------|----------|------------------------|
| **正常样本** | 常规输入输出？ | `CalcRemaining(1,10000,3000,5000)` 当前返回什么 |
| **边界样本** | 临界值（0/负/相等）？ | `orderAmount<=0`、`applyAmount<=0`、`totalRefunded<0` 报错 |
| **报错样本** | 非法输入时输出？ | `fmt.Errorf("order %d invalid amount=%d",…)` 之类 |
| **申请超额** | 超剩余时怎么截断？ | `applyAmount>=remaining` → 返回 remaining |

**照抄即用的通用追问提示词**（即 S-附录 **B3-1** 的 ②）：

> 请基于这些调用点 / 输入输出样本，为 `[函数/路由]` 生成 characterization tests：
> · 逐条记录"当前输入 → 实际输出"（含正常 / 边界 / 报错），**断言写的是现状、不是理想**；
> · 标识哪些是"正常路径"、哪些是"我现在只是如实记录、不判断对错"的样本。
> 复用 S-B 的测试生成方法。

> 💡 **关键判断**：抓样本的诀窍是**"喂边界、别喂花哨"**——把 `0`、`-1`、`等于剩余`、`超过剩余` 这些临界值都喂一遍。样本够边界，基线才够硬；只有正常值，重构漏了边界也不会被抓住。

---

### 🔴 目标三：跑绿归档，并标出"哪些分支被覆盖、哪些是盲区"

**产出**：一次**全绿归档**——行为基线测试全部通过（当前代码上全绿），附一份"覆盖点 + 盲区"清单，并在断言旁标注"仅为现状、非应当如此"。

**要确认的本质**：基线必须在重构前**全绿**——它是"改前现状"的基准值。同时要**诚实标出盲区**：哪条分支没测到（比如 `CalcRemaining` 的 TODO 模糊点 ③"申请超额"策略），因为盲区意味着"重构后此处若变味，基线兜不住"。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「handler 样板」 |
|------|----------|----------------------|
| **全绿** | 当前代码上全部通过？ | `go test ./internal/routes/` 全绿 |
| **覆盖点** | 哪些分支被钉住了？ | createOrder / createRefund / approveRefund 的成功与 400 分支 |
| **盲区** | 哪些分支没测到？ | 数据库故障 500 分支未覆盖（较难模拟） |
| **现状标注** | 哪些只是"现状"？ | 如报错文案拼写错误属现状，不判断 |

**照抄即用的通用追问提示词**（即 S-附录 **B3-1** 的 ③④）：

> 基线已生成，请帮我跑绿并存档：
> · 给出每份基线的运行命令，确认当前代码上**全绿**；
> · 列出"已覆盖的分支"和"未覆盖的盲区"，盲区要标"重构后此处变味基线兜不住"；
> · 在断言旁标注哪些**仅为现状**、哪些是业务上应当如此的——把隐性错误钉成"待 B2 / 需求处理"而非"重构别动它"。

> 💡 **关键判断 · 三个"确认真全绿"的节点**：
> ① **重构前**跑基线 → 全绿（这是"改前现状"的基准照）；
> ② 记录盲区 → 知道"哪块没安全带"；
> ③ 把"仅为现状"的断言和"应当如此"的断言分开标注 → 防止重构时把隐性 bug 当需求做成"顺手修正"。
> 三者就位，B3-④ 每改一步后重跑这张基线照，变没变味一眼见。

> 📌 **基线命名约定（统一口径，RO-4）**：新增基线测试文件一律命名为 `<原文件>_baseline_test.go`、与被测文件**同包同目录**（如 `refund_rules.go` → 同包下 `refund_rules_baseline_test.go`）；其中**测试函数一律以 `TestBaseline_` 开头**（如 `TestBaseline_CalcRemaining_Normal`）。这样「`go test -run TestBaseline ./...`」可一次命中全部基线、与既有 `Test_*` 旧测试清晰分开。**这是归档行为的一部分，不是练习区的补充**：无论你走哪条路线（主线 / 新手极简 / 老手精华），建基线的命名都按此口径，`go test -run TestBaseline` 跑基线在哪都一样。

> 不知道从哪采样本 / 采不全也别慌：把"我不确定 [函数] 的行为细节，请先帮我把它现在接受的输入范围、返回的所有分支（正常/边界/报错）用大白话列成一张表，我核对后再让基线断言跟这张表一致"给 AI——从"凭感觉写断言"变"照着现状清单勾对"；读不懂某节原文时，话术见导读「读不懂？用 AI 帮你读本教程」（卡壳救助已收拢于此）。

## 三、把基线沉淀成「行为基线测试 + 基线说明」（本步的产出物锚定）

你这一章要"交出去"的，是一份**全绿的行为基线测试** + 一份**基线说明**。它是 B3-② 识别坏味道时"哪些地方最不能乱动"的依据，也是 B3-④ 每步保真的判据。固定结构：

```markdown
# 行为基线说明：<待重构对象，如 CalcRemaining>

## 1. 范围
- 本次重构对象：<文件:函数/路由>
- 覆盖的调用链：<直接调用点>
- 不碰（基线不覆盖）：<其它模块>

## 2. 基线测试
- 测试文件：<文件>
- 运行命令：<go test -run XXX ./...>
- 当前状态：全绿 ✅

## 3. 覆盖点 vs 盲区
| 分支 | 是否已基线覆盖 |
|------|---------------|
| < orderAmount<=0 报错 > | ✅ |
| < 申请超额截断 > | ✅ |
| < 数据库故障 500 > | ⚠️ 盲区 |

## 4. 现状标注
- <这条/这类断言仅为现状，非应当如此（隐性错误交给 B2/需求处理）>
```

**怎么写（从二、的三份产出拼）？**
- **"范围"**：取 目标一 的范围清单。
- **"基线测试"**：取 目标二 的测试文件 + 目标三 的全绿结果。
- **"覆盖点 vs 盲区"**：取 目标三 的覆盖点清单，**盲区用 ⚠️ 标出并写清后果**。
- **"现状标注"**：取 目标三 的"仅为现状"断言清单——**这是 characterization test 区别于普通测试的灵魂**。

**检查标准**：读这份说明的人，能跑命令重现"当前全绿"，且知道哪块分支没安全带、哪些断言只是现状不算"应该这样"。**基线没全绿 = 别进 B3-②**——一张泛红的重构前照片，没法当"改前基准"。

**整合提示词**（把二、的三份产出收拢成行为基线说明）：

> 请把下面几份产出整理成一份「行为基线说明」：
> [粘贴：范围清单][粘贴：基线测试文件 + 全绿结果][粘贴：覆盖点/盲区清单][粘贴：现状标注]
> 按 范围 / 基线测试 / 覆盖点 vs 盲区 / 现状标注 四段输出，命令可复制。输出 Markdown。

> 📌 这份"全绿的行为基线"正是 **B3-② 前置里"以行为基线为输入"的那份**——B3-② 会对照它识别"哪些地方动不得、哪些可放手"。**每章的产出都成为下一章的输入，链条由此接上。**

## 四、提示词模板：建立行为基线（S-附录 B3-1）

这是 S-附录 里的 `建立行为基线 提示词`（即 **S-附录 B3-1**，B3 专用），直接复制填空即可：

> 我准备重构下面的代码，重构前需要一份「行为基线」来防止改坏行为：
> `[粘贴：将被重构的代码 + 它的调用点 / 输入输出样本]`
> 请帮我建 characterization tests（行为基线测试）：
> ① 范围界定：只对将被重构的这段代码建基线，不扩大到无关模块；
> ② 锁定现状：对当前代码的输入→输出逐条记录，**无需判断"对不对"，只需锁定"现状如此"**（含正常 / 边界 / 报错分支）；
> ③ 全绿归档：让这些基线测试在当前代码上全部通过（全绿），并说明覆盖了哪些分支、哪些是盲区；
> ④ 标注：哪些断言只是"现状"而不是"就应该这样"，避免把隐性错误也一并固化。
> 复用 S-B 的测试用例 / 生成 / 失败分析方法。

**逐字段解析（方便你按需增删）**：

- **`[粘贴：将被重构的代码 + 调用点/输入输出样本]`**：整段贴上要动的代码 + 它的真实调用样本——**基线断言就来自这些样本，不是你来编**。
- **① 范围界定**：**B3 的关键纪律**——只给将要动的那一处建基线，别铺全库。
- **② 锁定现状**：characterization test 的灵魂句——**"无需判断对不对，只需锁现状"**。这是它和需求/回归测试的分水岭。
- **③ 全绿归档**：基线必须"当前全绿"才有基准意义；**把盲区显式列出来**，因为盲区=重构时不受保护的地带。
- **④ 标注现状 vs 应当**：防止把当前代码里的隐性 bug 固化成交付契约——**隐性错误标"待 B2/需求处理"，不混进重构。**

> 💡 **递归用法**：AI 第一版基线常会"手滑"写成带理想预期的需求测试（比如把 `CalcRemaining` 里报错文案当 bug 改掉）。**把它回喂，追加"把每条断言标成 S(现状) / E(应当如此) 两类，并出现第 ④ 类时暂停、单独列给我，别让它混进本次基线"**，迭代 1–2 轮直到基线只锁现状、无夹带判断。

> 不确定这段代码现在到底有哪些分支？追加"先别写断言：把这段代码现在的输入范围、所有返回分支（正常/边界/报错）用大白话列成表，我核对后再让基线表一致"——从"逼你凭记忆写断言"变"照着现状清单对"；这条已在 S-附录·进阶操作速记「选填」下备案，照抄即用。

## 五、练习：给 main 分支的三处坏味道建行为基线

**任务**：在 `refund-shop` 的 **main 分支**，为三处待重构对象各建一份全绿的行为基线 + 基线说明。

**推荐步骤（以 CalcRemaining 为例）**：

1. 切到 main 分支，确认 `refund_rules.go` 的 `CalcRemaining` 当前行为（可先 `go test ./internal/domain/` 看现有测试）。
2. 用 B3-1 提示词，把 `CalcRemaining` + 它的几个输入样本（orderAmount<=0 / applyAmount<=0 / totalRefunded<0 / 申请超额 / 正常申请）给 AI。
3. 让 AI 生成 characterization tests（当前全绿、断言锁现状、覆盖正常/边界/报错），并标出 TODO 模糊点③"申请超额"当前是策略 A（截断）。
