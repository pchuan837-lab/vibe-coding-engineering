B3-① 我们用行为基线把"现状"钉住了。现在可以放心看了——看代码里有没有"坏味道"。但有个关键心态要摆正：**坏味道 ≠ 必须马上重构成某模样**。它只是"代码在发出'这里将来改动会疼'的信号"。要不要动、先动哪个，要看两件事：**改了会不会把行为搞翻（风险）**、**改了对后续维护帮助多大（价值）**。

> 一句话：**识别坏味道是"看菜"，排序才是"点菜"——先挑低风险高价值的下锅。**

| 坏味道 | 在哪 | 一句话"为什么疼" | 初步风险 |
|--------|------|------------------|-----------|
| **① 重复样板** | `routes/orders.go`（`createOrder`）+ `routes/refunds.go`（`createRefund` / `approveRefund`）共 3 个 handler | 改一处 JSON 约定要跟着改 3 处，易漏 | 低（复制粘贴改，且端点可测） |
| **② schema 混写** | `db/schema.sql` 单文件 | 加表/改列没有版本演进，上线混乱 | 中（涉及数据库变更，行为面广） |
| **③ 规则堆 if-else** | `domain/refund_rules.go` | 边界判定堆成串，改一条怕碰其它 | **高（金额核心，改坏影响退款）** |

注意**"初步风险"和"坏味道严重度"是两回事**——`CalcRemaining` 的 if-else 看着最"乱"，但它恰恰是**重构风险最高**的一处（动金额规则 = 撞核心逻辑）。这就是本章要教你的：**别只看坏味道顺不顺眼，要看你动它时行为翻车的概率。**

## 一、为什么"识别坏味道"不等于"马上全修"？

| | 见到坏味道就改 | 识别 + 按风险/价值排序 |
|---|---|---|
| 付出 | 处处点火，处处返工 | 先改确定能保真的，建立信心 |
| 风险 | 高风险处先动，一改就翻 | 低风险高价值先行，安全垫厚 |
| 判断 | 凭"看着乱" | 凭"改了行为会不会翻天 + 测试够不够" |
| 结果 | 重构变成第二种灾难 | 每一步都在基线下安全推进 |

> 一句话：**重构最大的坑不是"不敢改"，而是"什么都想改、从最险的下手"。** 识别完必须排序。

## 二、通用方法：对照基线与受影响面，给坏味道排个"安全的下锅顺序"

### 🔴 目标一：识别坏味道——逐个讲清"为什么是问题"

**产出**：一份**坏味道清单**——列出重复代码 / 过长函数 / 过度耦合 / 命名 / 可读性等问题，**每个都用大白话讲清"为什么是坏味道、不修会怎样"**。

**要识别的本质**：坏味道不是看"代码丑不丑"，而是看"将来有没有人因此踩坑"。识别时让 AI 逐个回答"它阻塞了什么改动"—是新需求难落地？是易改 A 坏 B？还是新人看不懂？

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「handler 样板」 |
|------|----------|----------------------|
| **现象** | 代码长什么样？ | 3 个 handler 重复"绑定/解析→err→JSON→return" |
| **根由** | 为什么会有这味道？ | 从最早的单端点复制粘贴出来的 |
| **后果** | 不修会怎样？ | 改错误文案/返回结构要跟着改 3 处，漏一处接口不一致 |
| **归属** | 属于哪类坏味道？ | 重复代码 / DRY 破缺 |

**照抄即用的通用追问提示词**（即 S-附录 **B3-2** 的 ①）：

> 在 `[范围]` 里识别坏味道，逐处给我：
> · 现象（代码长什么样）+ 属于哪类（重复 / 过长函数 / 过度耦合 / 命名 / 可读性）；
> · 根由（为什么会变成这样）；
> · 后果（不修会怎样，具体到"将来哪类改动会疼"）。
> 用大白话讲，别只贴代码不解释。

> 💡 **关键判断**：一处地方值不值得重构 = **"盯着它，某个真实需求将来会不会被拖累"**。能答上"会" = 有改的价值；答不上 = 只是"看着不顺眼"，别为了凑清单硬列进 B3-③。

---

### 🔴 目标二：评估改动风险——对照基线，标出"动不得 / 测试薄弱"的点

**产出**：每处坏味道的**风险标注**——改动是否触碰行为基线覆盖薄弱处、是否牵连核心逻辑、是否影响面相广。

**要评估的本质**：风险 = "改了行为翻车的概率 × 翻车后果"。两个放大因素：**测试覆盖薄弱**（基线没兜住，翻车发现不了）和 **逻辑核心**（金额/状态这类，翻车后果严重）。复用 S-A 的受影响面视角。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「CalcRemaining if-else」 |
|------|----------|--------------------------------|
| **基线索住否** | 基线覆盖了它的关键分支？ | 正常/边界/报错都有基线，但基准线略"薄" |
| **核心逻辑** | 是业务决定成败的规则？ | 是——退款金额规则 |
| **影响面** | 被谁调用、波及多大？ | 被 approve 端点与 audit 逻辑引用 |
| **风险级** | 综合定级？ | 高（动核心且有盲区，最需谨慎） |

**照抄即用的通用追问提示词**（即 S-附录 **B3-2** 的 ②③）：

> 对上面每处坏味道，标出改动风险与测试缺口：
> · 基线覆盖了哪些分支、哪些是盲区（重构后变味兜不住）；
> · 是不是业务核心逻辑、被多少调用点依赖（配合 S-A 受影响面）；
> · 重构前还**缺**哪些行为基线 / 测试用例。
> 给出每处的风险级：低 / 中 / 高。

> 💡 **关键判断**：**别被"坏味道难看"带偏风险判断**。`CalcRemaining` 的 if-else 最丑，但它风险最高——因为它是金额核心。判断标准永远回到"**动它时，基线够不够硬 + 坏了的后果多大**"。

---

### 🔴 目标三：排推荐顺序——低风险高价值优先

**产出**：一份**推荐重构顺序**——按"低风险高价值"优先、"高风险"靠后（除非价值极高且基线硬）排序，每处附理由；被判定"不值得改"的明确说出来。

**要排序的本质**：先做**确定能保真**的（低风险高价值），攒一次全绿的心理与验证信心；把**高风险**的留到基础稳了、基线补硬了再碰。排序是对"该先干什么"的表达，不是"都要干"的清单。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进 main 分支三处 |
|------|----------|--------------------|
| **低风险高价值** | 先改哪？ | ① 去重 handler 样板（低险高值）→ 先行 |
| **中风险中价值** | 其次？ | ② schema 演进（中险中值）→ 其次 |
| **高风险** | 何时碰？ | ③ CalcRemaining（高险核心）→ 补硬基线后再动 |
| **不值得改** | 哪处可放？ | 若无真实需求拖累的，明确"不做" |

**照抄即用的通用追问提示词**（即 S-附录 **B3-2** 的 ④）：

> 请给推荐重构顺序：
> · 按"低风险高价值"优先、"高风险靠后"排序，每处附一句理由；
> · 明确标出哪几处你判断"不值得改"，并说清不做的理由（别硬凑清单）。
> 最后给一句总览："先做 A，再补硬 B 的基线后做 B，C 暂缓"。

> 💡 **关键判断 · 排序的"安全下锅"标准**：低风险高价值 = **改了行为几乎不可能翻 + 对后续改动帮助大**，先做攒信心；高风险 = 必须**先把基线补硬（回 B3-①）再碰**。**宁可在安全区多做几步，也不要一上来就撞核心。**

> 坏味道一堆、看不动也别慌：把"先别列全部，把 [范围] 里最影响我接下来要做的 [某需求/改动] 的那 2–3 处坏味道挑出来，其余的先不展开"给 AI——从"面对清单发怵"变"只盯拖累真实目标的那几处"；读不懂某节原文时，话术见导读「读不懂？用 AI 帮你读本教程」（卡壳救助已收拢于此）。

## 三、把识别结果沉淀成「重构清单」（本步的产出物锚定）

你这一章要"交出去"的，是一份**重构清单**——坏味道 / 改动风险 / 测试缺口 / 推荐顺序齐全。它是 B3-③ 设计重构方案的直接输入。固定结构：

```markdown
# 重构清单：<范围>

## 1. 坏味道
| 位置 | 现象 | 根由 | 后果（不修会怎样） | 归属类型 |
|------|------|------|-------------------|----------|
| `orders.go` + `refunds.go`（3 个 JSON 绑定点） | 3 处重复样板 | 复制粘贴 | 改约定要改 3 处易漏 | 重复代码 |

## 2. 改动风险与测试缺口
| 位置 | 基线覆盖 | 盲区 | 核心逻辑? | 影响面 | 风险级 |
|------|----------|------|-----------|--------|--------|
| <defAmount> | 有，稍薄 | 数据库 500 分支 | 是 | 退款相关 | 高 |

## 3. 推荐顺序
1. <低风险高价值>：handler 去重 —— 行为易保真，先行
2. <中风险>：schema 演进 —— 补基线后做
3. <高风险>：CalcRemaining —— 先把基线补硬再碰
4. <不值得改>：<若有> —— 理由：无真实需求拖累

## 4. 总览
先做 A，再补硬 B 的基线后做 B，C 暂缓。
```

**怎么写（从二、的三份产出拼）？**
- **"坏味道"**：取 目标一 的清单（现象/根由/后果/归属）。
- **"改动风险与测试缺口"**：取 目标二 的风险标注（基线条/盲区/核心/影响面/定级）。
- **"推荐顺序" + "总览"**：取 目标三 的排序与结论，含"不值得改"的明确说明。

**检查标准**：读这份清单的人，能一眼看清"改了每处会发生什么风险、测试够不够、该先动哪"，并清楚哪几处被判定不值得改。**没排顺序 / 没标风险的清单，B3-③ 无从下手。** 一份"只有坏味道、没有风险级"的重构清单不算数。

**整合提示词**（把二、的三份产出收拢成重构清单）：

> 请把下面几份产出整理成一份「重构清单」：
> [粘贴：坏味道清单][粘贴：风险与测试缺口表][粘贴：推荐顺序]
> 按 坏味道 / 改动风险与测试缺口 / 推荐顺序 / 总览 四段输出，风险需三级标注，顺序需"低风险高价值优先"并附理由。输出 Markdown。

> 📌 这份"重构清单"正是 **B3-③ 前置里"以重构清单为输入"的那份**——B3-③ 会对优先项设计具体重构方案。**每章的产出都成为下一章的输入，链条由此接上。**

## 五、练习：为 main 分支三处坏味道出重构清单 + 排顺序

**任务**：基于 B3-① 建好的行为基线，对 main 分支三处坏味道产出重构清单并给推荐顺序。

**推荐步骤**：

1. 用 B3-2 提示词，粘贴"行为基线说明 + 相关代码（orders.go / schema.sql / refund_rules.go）"，`[范围]` 填"main 分支的 handler / schema / CalcRemaining"。
2. 让 AI 逐处给坏味道（现象/根由/后果/归属），并**对照基线标风险级**。
3. 核对风险：确认 AI 是否把 `CalcRemaining`（if-else 最丑）正确标为**高风险**而非"最该先改"，把 handler 去重标为**低风险高价值**。
4. 让 AI 给推荐顺序 + "不值得改"项。
5. 用整合提示词产出「重构清单」。

**对答案**：一份合格的重构清单应含四段，顺序"低风险高价值优先、高风险靠后"，且有明确"不值得改"说明。

- **坏味道① handler 样板**：重复代码，风险**低**，价值**高**（行为边界在基线下易保真）→ **推荐先做**。
- **坏味道② schema 混写**：可读性/演进缺失，风险**中**（数据库变更影响面广），价值**中** → **补基线后做**。
- **坏味道③ CalcRemaining if-else**：过度耦合/复杂分支，风险**高**（金额核心 + 基线略薄 + 3 处 B1① 模糊点），价值高但**必须先补硬基线再碰** → **最后做**。
- **不值得改**：若某处只是"命名不够好"且无真实需求拖累，应明确说"不做"，不硬凑进 B3-③。

> 🔎 **（可选进阶）体会"风险≠难看"**：让 AI 分别按"坏味道严重度"和"改动风险"排两版序，对比差异——你会发现 `CalcRemaining` 在"严重度"排前、却应在"重构顺序"排后。**重构顺序看风险，不看难看程度。**
