# B3-③ 设计重构方案

> **轨道**：B3 重构（保持行为不变、内部结构变好）第三步。
> **前置**：B3-② 完成，手里有一份**重构清单**（坏味道 + 风险 + 测试缺口 + 推荐顺序）；配套项目 `refund-shop` 切到 **main** 分支。
> **目标**：为每个要改的坏味道，设计一份**重构方案**——明确"改哪里、怎么改、改完怎么验证没改坏"，还要先补 B3-② 标出的基线缺口。
> **预估时长**：20–40 分钟。

> 🧭 **本章自包含**：不需提前通读其他任何编号章节；要用到某个 `S-附录` 提示词时，我会在正文当处（章末的 📌）明确指出，你用到再看即可。（"前置"里的 B3-② 产出的重构清单是**输入材料**，不是要你回头通读那章）

> 🧭 **本章怎么读**：主线走完全程（约 20–40 分钟）；只想先跑通？→ 本章最少做：①对一个坏味道给出"改法 + 波及面 + 保真验证" ②对照风险，确认该先补的基线缺口（给三处都出完整方案返工再补）；详见导读「三条路线图」·新手极简·B3③ 行。只想看核心方法？→ 见导读 ·老手精华。省步骤 ≠ 省产出物，跳过的正是返工回来补的。

```text
①建立行为基线→②识别坏味道→[③设计重构方案]→④小步重构→⑤确认保真收尾
```

> 📍 **当前位置：B3 轨道 · 第 3 / 5 步**（上图 `[③]` 即你所在步骤）。

到这一步，你已经知道"哪些地方值得改、哪个先改"。但**"知道改哪"还不等于"能安全改完"**——B3 的关键纪律是：**动手前先把每个重构点怎么改、改完怎么验证想清楚**。方案是 B3-④ 小步重构的"作战地图"：没有它，你就会在重构时边改边犹豫"这里是不是该拆一下？这个测试还够不够？"，一犹豫就容易顺手把行为也变了。

> 一句话：**重构方案 = 把"我要把它改成更好"变成"我明确知道改成什么样、且改完能证明没变样"。**
>
> 这章复用 [S-B · 测试与回归]（S-3/S-6）和 B3-① 的行为基线来定"保真验证方式"，本轨道不重写通用方法，只强调件事——**每个重构点必须配一句"改完用哪条基线 / 哪个样本证明没改坏"**。

用配套项目 `refund-shop` 的 **main 分支**继续举例（本章贯穿案例，给三处坏味道出方案的节奏）：

| 坏味道 | 改法方向 | 波及面 | 保真验证方式 |
|--------|----------|--------|--------------|
| **① handler 样板** | 提取公共绑定/响应 helper（去重复） | 3 个 handler 调用点 | 跑 3 个已有 handler 基线测试，返回体对比 |
| **② schema 混写** | 拆成 migrations/001+002 + 版本表（拆文件） | 首次建库 → 上线迁移逻辑 | 基线里"表/列/约束/索引存在"断言仍过 |
| **③ 规则堆 if-else** | 拆分支为策略/守卫函数 + 先补基线（拆层） | 金额核心，被退款端点调用 | 先补 B3-② 标的缺口，跑 8 条金额基线（示例建议条数） |

注意 **③ 的方案里先有"补基线"这一步**——因为 B3-② 判定它"基线略薄 + 高风险"，B3-③ 就必须先把安全带补硬再谈改法。这就是"方案要尊重风险排序"的体现。

## 一、为什么"设计好方案再动手"，才能保证重构不改坏行为？

| | 边改边想 | 先出重构方案再执行 |
|---|---|---|
| 你知道目标 | "改得更漂亮"（模糊） | "改成这样 + 用这个验证"（明确） |
| 验证 | 忘了底线测 | 每个点配好保真基线 |
| 波及面 | 改着发现牵连一堆 | 事前列清调用点 |
| 高风险处 | 一上来就撞 | 先补基线、控住风险 |
| B3-④ 执行 | 边犹豫边改 | 照图施工，一步一验 |

> 一句话：**方案是"不改变行为的施工图"。** 它把"感觉能改"变成"确定能改、且能证明没改坏"。

---

## 二、通用方法：给每个坏味道写"改法 + 波及面 + 保真验证"

### 🔴 目标一：给坏味道定改法与波及面

**产出**：每个坏味道的**改法方案**——具体重构手法（提取函数 / 改名 / 去重复 / 拆层 / 拆文件）落到"改哪里、改成什么样"，并讲清**波及面**（牵连哪些调用点、会不会改变对外行为）。

**要设计的本质**：重构手法很多，选哪个取决于"这个坏味道怎么来的"。炸代码去了重复、拆层降耦合、拆文件理清演进。关键是**每个改法都要答"会不会改变对外行为"**——会 = 那不是重构了，是改需求。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「handler 样板」 |
|------|----------|----------------------|
| **手法** | 选哪种重构？ | 提取公用 helper（绑定 + 错误响应） |
| **改哪里** | 落到哪个文件/函数？ | `routes/orders.go` → 新增 helper + 3 handler 复用 |
| **改成什么样** | 目标形态？ | handler 只剩"业务逻辑三五行" |
| **波及面** | 牵连哪些调用点？对外行为变吗？ | 3 个 handler + 挂载不变，返回体不变 |

**照抄即用的通用追问提示词**（即 S-附录 **B3-3** 的 ①②）：

> 请为 `[坏味道]` 设计改法：
> · 手法：选 提取函数 / 改名 / 去重复 / 拆层 / 拆文件 之一，落到"改哪里、改成什么样"；
> · 波及面：列出会牵连的调用点 / 其它代码，并明确"会不会改变对外行为"；
> · 若会改变对外行为，单独标出（那通常不是重构，是需求变更，别做）。

> 💡 **关键判断**：重构的边界 = **"对外行为零变化"**。任何"让接口返回体/REST 语义改变"的改法都不是重构，是需求变更——别混进 B3。

---

### 🔴 目标二：为每个重构点配套"保真验证方式"

**产出**：每个重构点的**保真验证方式**——跑**哪条行为基线** / 对比**哪个输入输出样本**，证明"改完后行为没变"。

**要配套的本质**：B3 能不能安全推进，靠"改一步、验一步"。这个"验"不能临时拍脑袋，要在方案阶段就定好——**哪个函数改完，用哪条基线测试守着**。凡标了"测试缺口"的，先补基线再谈改。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「CalcRemaining」 |
|------|----------|------------------------|
| **基线守哪个** | 改这函数跑哪条？ | 8 条金额基线（正常/边界/报错/截断，示例建议条数） |
| **缺口** | B3-② 标的缺口补什么？ | 先补"策略 A 截断 + 3 处模糊点现状"基线 |
| **对比样本** | 额外对比哪个输入输出？ | `CalcRemaining(1,10000,3000,5000)` 前后一致 |
| **验证节奏** | 改完哪步验？ | 每拆一个分支跑一次定向基线 |

**照抄即用的通用追问提示词**（即 S-附录 **B3-3** 的 ③④）：

> 为上面每个重构点配「保真验证方式」：
> · 改完跑哪条行为基线 / 对比哪个输入输出样本，能证明行为没变；
> · 若 B3-② 标了测试缺口，先把该补的行为基线 / 用例列出来（重构前先补），再谈改法。

> 💡 **关键判断 · 保真验证的合格线**：**"改完后，重构前的行为基线全部仍绿 + 关键输入输出样本前后一致"**。凡是"我肉眼看逻辑没变"都是假验证——必须跑基线。缺口未补的高风险处（如 `CalcRemaining`），**先补基线再动**。

> 不知道选哪个改法 / 保真验证悬空也别慌：把"先别给整套方案，就回答我两件事：①这根线值不值得动？如果值得，最保守的一种改法是什么（先提最稳的，别一上来就大重构）？②改完我用哪条基线能立刻判断改没改坏？"给 AI——从"纠结一堆方案"变"只确认最稳改法 + 一条验证基线"；读不懂某节原文时，话术见导读「读不懂？用 AI 帮你读本教程」（卡壳救助已收拢于此）。

## 三、把方案沉淀成「重构方案」（本步的产出物锚定）

你这一章要"交出去"的，是一份**重构方案**——每个坏味道对应"改法 / 波及面 / 保真验证方式"，外加"前置补基线清单"。它是 B3-④ 小步重构的直接执行依据。固定结构：

```markdown
# 重构方案：<范围>

## 0. 前置补基线
- <处1>先补：<该补的基线/用例（来自 B3-② 缺口）>
- <处2>先补：<…>

## 1. <坏味道①：名字>
- 手法：<提取函数 / 去重复 …>
- 改哪里 & 改成什么样：<文件、函数、目标形态>
- 波及面：<调用点清单、是否改变对外行为>
- 保真验证：跑 <基线条目> / 对比 <样本>，缺口已补并全绿

## 2. <坏味道②：…>
…

## N. 不值得改项（如有）
- <处>：不做，理由：<…>
```

**怎么写（从二、的两份产出 + B3-② 拼）？**
- **"前置补基线"**：取 B3-② 的"测试缺口"，列在前面——**先补安全带再动改**，尤其高风险处。
- **每处四要素**：改法（目标一 ①）、改成什么样（目标一 ②）、波及面（目标一 ②）、保真验证（目标二）。
- **"不值得改项"**：取 B3-② / B3-③ 里 "不做" 的判断，留档说明。

**检查标准**：读这份方案的人，能照它进入 B3-④"一步一改一验"，且每处都答得到"怎么证明没改坏"。**没有配套保真验证的重构方案 = 无效方案**——它降级成了"我想改成这样"的愿望清单。高风险处没先补基线，也不能进 B3-④。

**整合提示词**（把二、的两份产出收拢成重构方案）：

> 请把下面几份产出整理成一份「重构方案」：
> [粘贴：各处改法 + 波及面][粘贴：各处保真验证方式][粘贴：B3-② 的测试缺口]
> 按 前置补基线 / 每处（手法-改哪里-波及面-保真验证）/ 不值得改项 组织，每处必带"保真验证"。输出 Markdown。

> 📌 这份"重构方案"正是 **B3-④ 前置里"以重构方案为输入"的那份**——B3-④ 会照它一步步改、一步一验。**每章的产出都成为下一章的输入，链条由此接上。**

## 四、提示词模板：设计重构方案（S-附录 B3-3）

这是 S-附录 里的 `设计重构方案 提示词`（即 **S-附录 B3-3**，B3 专用），直接复制填空即可：

> 这是我要重构的目标与「重构清单」：
> `[粘贴：重构清单（坏味道 + 风险 + 测试缺口 + 推荐顺序）]`
> `[粘贴：B3-① 的行为基线说明]`
> 请对每个要改的坏味道给一份「重构方案」：
> ① 改法：给出具体重构手法（提取函数 / 改名 / 去重复 / 拆层 / 拆文件），落到"改哪里、改成什么样"；
> ② 波及面：说明这处改动会牵连哪些调用点 / 其它代码，会不会改变对外行为；
> ③ 保真验证：配套"跑哪条行为基线 / 对比哪个输入输出样本"来证明没改坏；
> ④ 先补基线：若 B3-② 标了"测试缺口"，先把该补的行为基线 / 用例列出来（重构前先补）。
> 若某处不值得改，直接说"不做"，别为凑数出方案。

**逐字段解析（方便你按需增删）**：

- **`[粘贴：重构清单]` + `[粘贴：行为基线说明]`**：两份一起贴，让 AI 既知道"改哪些、什么风险"，也知道"现在行为怎样、用什么守"。
- **① 改法**：**手法 + 落点**——不只说"提取函数"，要说清改哪里、改成什么样。
- **② 波及面**：**必答"会不会改变对外行为"**——会 = 需求变更，不是重构，别做。
- **③ 保真验证**：**每个重构点必须配验证基线/样本**——这是方案区别于"愿望清单"的关键。
- **④ 先补基线**：尊重 B3-② 的"测试缺口"，**高风险处先补基线再动**。

> 💡 **递归用法**：AI 第一版方案常"手法空泛 + 保真验证悬空"（只说"重构会更清晰"）。**把它回喂，追加"每一处都必须落到'改哪个文件的哪几行'，并给一句可执行的验证命令（跑哪条基线 / 对比哪个样本）；没有验证线的，退回重写"**，迭代 1–2 轮直到方案"逐条可执行、条条有验证"。

> 某处改法选不出？追加"给 2–3 个可选改法（保守 / 中等 / 彻底）各自的取舍与后续影响，我懂了再挑"——从"逼你定手法"变"菜单里点菜"；这条已在 S-附录·进阶操作速记「选填」下备案，照抄即用。

## 五、练习：为推荐顺序的前两项出重构方案

**任务**：在 main 分支，为 B3-② 推荐顺序里的 handler 去重（低险高值）和 schema 演进（中险）各出一份重构方案；高风险处先做"前置补基线"清单。

**推荐步骤**：

1. 用 B3-3 提示词，粘贴重构清单 + 行为基线，`[范围]` 写"三处坏味道"。
2. 先看"前置补基线"——确认 `CalcRemaining` 处被要求先补的策略 A 截断基线。
3. 让 AI 为 **handler 去重**出完整方案：改法（提取 helper / 去重复）、波及面（3 个 handler + 挂载）、保真验证（跑哪条 handler 基线）。
4. 让 AI 为 **schema 演进**出方案：改法（拆 migrations/001+002 + 版本表 / 拆文件）、波及面（首次建库 vs 上线迁移）、保真验证（基线里的表/列/约束/索引断言）。
5. 用整合提示词产出「重构方案」，确认每处都有可执行的验证命令。

**对答案**：一份合格的重构方案应含"前置补基线 + 每处（手法-改哪里-波及面-保真验证）+ 不值得改项"，每处验证命令可执行。

- **handler 去重方案**：手法提取公共 `bindJSON` / `respondError` helper；波及面 = 3 个 handler 调用点 + 路由挂载不变，**对外行为零变化**；保真验证 = 跑 3 个 handler 基线测试（成功/400/404），返回体对比。
- **schema 演进方案**：手法拆 `migrations/001_orders.sql` + `002_refunds.sql` + 版本表（`schema_version`）；波及面 = 首次建库改为按版本迁移脚本执行，**表结构/约束/索引不变**；保真验证 = 基线里 orders/refunds 两表 + 3 索引存在断言仍过。
- **CalcRemaining（高风险）**：本步只出"前置补基线"清单（补策略 A 截断 + 3 处模糊点现状基线 + 报错文案），**不急着给大改法**——先补硬安全带，B3-④ 再谈拆分支。

> 🔎 **（可选进阶）反向验证"对外行为不变"**：对 handler 去重方案，让 AI 标一句"这个 helper 的引入，会不会让某个端点的成功返回体的字段顺序 / 内容变化？"——你能借此体会到**重构方案里"对外行为零变化"这条红线要逐点核对**。
