## 一、为什么"小步改 + 一步一验"才能保住行为不变？

| | 憋大招一把重构 | 小步重构、频繁验证 |
|---|---|---|
| diff 大小 | 一大坨，看不清 | 每步很小，diff 清楚 |
| 出错定位 | 不知道哪步改坏的 | 当步就能定位回退 |
| 验证 | 最后一起验，红了一片 | 每步绿了才前进 |
| 行为失控 | 风险高 | ⚠️ 有基线兜底 |
| 信心 | 提心吊胆提交 | 全程绿，心里有底 |

> 一句话：**小步 + 频繁验证，是给重构上"刹车"，防止它滑向"改着改着变味"。**

## 二、通用方法：把每一处重构切成"可验证的小步"

### 🔴 目标一：把重构方案拆成"可独立验证的小步"

**产出**：一份**小步拆分**——把 B3-③ 的每个重构点切成"每步一个完整改动、能独立验证 / 可独立回滚"的小步，并排好顺序（先补基线，再动代码）。

**要拆分的本质**：步子的合格线 = **"能独立验证、且万一不对能独立回滚的最小完整改动"**。它不是按"时间长短"划的——同一处改动，对高手可能 3 分钟、对生手可能半小时，关键不在这；关键是**这一小步"自给自足"**：改完单独跑测试 / 编译就能验，出问题单独回退这一小步、不影响其他步。步太大 = 报错了难定位；步太小 = 没必要地碎。顺序上**先做"前置补基线"**，再动结构。

**拆细 vs 合并，怎么判断**：拿不准一口气改多少，用三条线量——
- **能独立验证吗**：这一步改完，能否单独跑出一条绿 / 红的明确结论？不能 → 拆更细。
- **能独立回滚吗**：这一步万一不对，能不能单抽出回退、不动别的步？不能 → 拆更细。
- **值得单独成步吗**：这一下改得太碎（改个变量名都要单独一步），反而拖慢节奏 → 那就把几处真正耦合在一起的改动合并成**一个完整改动**，但合并后仍要满足前两条。
口诀：**拆到"能独立验证、能独立回滚"为止；在此前提下，能合并的耦合改动合一步走。**

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「handler 样板」 |
|------|----------|----------------------|
| **粒度** | 每步做几件"完整改动"？ | 每步一个完整改动（加 helper / 替换一个 handler / 删一段冗余） |
| **可验证** | 改完这步能单独验？ | 每步后 `go test ./internal/routes/` 绿 → 下一步 |
| **顺序** | 先补基线再动结构？ | ① 先确认 handler 基线在 → ② 加 helper → ③ 逐个替换 → ④ 删冗余 |
| **节奏** | 一步多大？ | 满足"能独立验证 / 可独立回滚"，时长浮动、别用"几分钟"硬卡 |

**照抄即用的通用追问提示词**（即 S-附录 **B3-4** 的 ①②）：

> 请把 `[重构点]` 拆成小步，每步只做一件事、能独立编译 / 过测试：
> · 先把前置补基线（若有）排在最前并补齐全绿；
> · 给出每一步：做什么 / 改哪个文件哪几行 / 跑哪条基线验证。

> 💡 **关键判断**：步子的合格线 = **"每步改完都能独立跑绿，红一眼看出是哪步"**。参考节奏：新建 helper 可作一步、替换一个 handler 可作一步、删一段冗余可作一步——难点不在"几分钟一步"，而在**别把"加 helper + 替换全部 + 删冗余"塞成一步**（塞大了既不独立验证、也难以单独回滚）。

**拆细 vs 合并，再补一刀：** 框架搭好了想让每步"改少点"，但也别矫枉过正——**纯机械的同构改动**（如 3 个 handler 套同一个 helper、字段名统一）可以合并成一步跑通，不必逐个**单独**提交；**有行为差异的改动**（涉及边界、取值变化）一定要单独成步、单独验证。

### 🔴 目标二：一步一验——每完成一小步就验证，绿了才前进

**产出**：一份**逐步重构记录**——每步含"改了什么 / diff 摘要 / 验证结果"；**不绿的步骤当场停下**，分清"改坏了行为"还是"测试写错"再决定回退还是修测试。

**要执行的本质**：这是 B3 的信条——**"一步一验"不是可选项**。每小步后跑方案里配好的那条基线，绿 → 继续，不绿 → 停。关键是**分清红因**：红可能是"重构真改坏了行为"，也可能是"基线 / 测试本身写错"（比如断言了不该断言的现状、或样本采错）。每小步的"保真"应看作**三件套**：`go test` 跑通你方案配的行为基线（绿）＋ `go vet ./...` 无新增告警（净）＋ 核对对外契约无 diff（空，`docs/api-reference.md` 的 diff 为 0）——行为、静态质量、对外契约三者都保住，这步才算过。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「CalcRemaining 第2步」 |
|------|----------|------------------------------|
| **本质** | 每步验证跑什么？ | ≥8 条金额基线样本、且覆盖 正常/边界/报错/截断 四类（示例建议，数字不必逐字对齐）+ 关键样本对比 |
| **不绿处理** | 红 = 改坏 or 测试错？ | 先看 diff 是否触及行为 → 回溯 vs 修基线 |
| **回退线** | 回退到哪？ | 回退到"上一小步绿"的状态再重来 |
| **记录** | 每步留什么？ | diff 摘要 + 验证命令 + 结果（绿/红） |

**照抄即用的通用追问提示词**（即 S-附录 **B3-4** 的 ③④）：

> 每完成一小步，给我这一步的 diff 摘要 + 验证结果，绿了才进下一步：
> · 输出「逐步重构记录」，每步含 改了什么 / diff 摘要 / 跑哪条基线 / 结果；
> · **每步三件套**：`go test`（行为基线）绿 ＋ `go vet ./...`（静态）净 ＋ 契约（api-reference）diff 空，三者齐过才算过；
> · 哪一步验证失败，当场停下，帮我区分"重构改坏了行为"还是"基线/测试写错"，再决定回退到哪一步重来或修测试。

> 💡 **关键判断 · 三个"必须停"的时刻**：①任何一步**基线不绿** → 停下，别带病往下走；②diff 碰了**方案之外的部分** → 停下，回到方案范围；③**越改越加功能** → 停下，你是重构不是加需求。三条踩中任何一条都先把当下收敛，别恋战。

> 一步红了一脸懵也别慌：把"这一步红了，帮我先别改任何东西：①只看上一步到我这一步的 diff，列出所有行为可能受影响的行；②第一优先判断是'改坏'还是'测试写错'；③如果是改坏，告诉我回退到哪一步最小。我没确认前不要再往下改"给 AI——从"手忙脚乱乱改"变"先诊断、再决定回退/修测试"；读不懂某节原文时，话术见导读「读不懂？用 AI 帮你读本教程」（卡壳救助已收拢于此）。

## 三、把执行过程沉淀成「逐步重构记录」（本步的产出物锚定）

你这一章要"交出去"的，是一份**逐步重构记录**——每步"改了什么 / diff 摘要 / 验证结果"，全绿推进。它是 B3-⑤ 确认行为保真的依据：B3-⑤ 会重跑全量基线做最后兜底，这份记录说明"每步是怎么保真的"。固定结构：

```markdown
# 逐步重构记录：<范围>

## 0. 前置补基线
- [x] 补 <处> 的策略 A 基线，全绿
- [x] 补 <处> 的报错文案基线，全绿

## 小步 1：<加 helper / 拆守卫>
- 改：<文件:行，改了啥>
- diff 摘要：< +N / -M，动了哪几行 >
- 验证：`go test ./internal/routes/`  ✅ 绿；`go vet ./...`  ✅ 净；契约 diff  ✅ 空

## 小步 2：<替换 createOrder>
- 改：<…>
- diff 摘要：<…>
- 验证：`go test ./internal/routes/`  ✅ 绿

## 小步 3：…
…

## 每步结论
- 全部小步在基线保护下次第全绿推进，无"带病往下带"
```

**怎么写（从二、的两份产出拼）？**
- **"前置补基线"**：取 目标一 排在最前的补基线小步，打勾。
- **小步 N**：取 目标一 的小步拆分 + 目标二 每步的"改了什么 / diff 摘要 / 验证结果"。
- **"每步结论"**：一句总括——是否全程全绿、有无回退、有无红过又怎么处理。

**检查标准**：读这份记录的人，能顺着它重演每步"改了什么 → diff 多大 → 验了什么 → 绿没绿"，且能看出"每步都独立可验证、没有一步塞了一大坨"。**一份"一个巨型 diff + 最后一次全绿"的记录，不算逐步重构记录**——它丢了"小步可定位"的核心价值。

**整合提示词**（把二、的两份产出收拢成逐步重构记录）：

> 请把下面几份小步记录整理成一份「逐步重构记录」：
> [粘贴：各小步的 改了什么 / diff 摘要 / 验证结果]
> 按 前置补基线 / 小步 N / 每步结论 组织，每步 diff 要能看出"改小、可定位"，验证要标绿/红及处理。输出 Markdown。

> 📌 这份"逐步重构记录"正是 **B3-⑤ 前置里"以逐步重构记录为输入"的那份**——B3-⑤ 会重跑全量基线做最后保真兜底，并用这份记录交叉核对。**每章的产出都成为下一章的输入，链条由此接上。**

> 若某步验证失败，帮我区分是"重构改坏了行为"还是"基线/测试本身写错"，再决定回退还是修测试。

**逐字段解析（方便你按需增删）**：

- **`[粘贴：重构方案]`**：把 B3-③ 的方案贴进——**每步的验证基线就来自方案的"保真验证方式"，不是临场编**。
- **① 拆分**："每步只做一件事 + 能独立编译/过测试 + 能独立回滚"——这是步子的合格线，防止憋大招（"1–3 分钟"只是一个参考节奏，别把"用了几分钟"当步子的对错标准）。
- **② 补基线**：严格按方案的"前置补基线"先补齐全绿，**高风险处（如 `CalcRemaining`）没补硬基线不先动**。
- **③ 一步一验**：每步给 diff 摘要 + 验证，绿了才继续；**不绿当场停，别带病往下带**。
- **④ 记录** + **失败区分**：把过程留下 + 红了先判断"改坏 vs 测试错"，再回退或修测试。

> 💡 **递归用法**：AI 常"一上来就想一个大 diff 搞定 + 最后才统一跑测试"。**把它回馈，追加"强制把每个坏味道拆成互不依赖的小步，每步独立给出 改哪里 + diff 摘要 + 验证命令；某步不绿就停，别一次给我一坨改完后再说全绿"**，迭代 1–2 轮直到"小步 + 一步一验"。

> 步子大小拿不准？追加"优先用最保守的小步（每步只动一处），宁可多几步也别一步改一片"——从"判断步子大小"变"先保守走几步"；这条已在 S-附录·进阶操作速记「选填」下备案，照抄即用。

## 五、练习：把 handler 去重切成小步、一步一验地走完

**任务**：在 main 分支，按 B3-③ 的 handler 去重方案，把它拆成小步并在每步验证下走完。

**推荐步骤**：

1. 用 B3-4 提示词，粘贴 handler 去重方案，`[重构点]` 填"handler 样板去重"。
2. 让 AI 先确认 handler 基线存在（B3-① 建的）并全绿，作为前置。
3. 让它拆成小步：加 helper → 改 createOrder → 改 createRefund → 改 approveRefund → 删冗余，每步给 diff 摘要 + `go test ./internal/routes/` 验证。
4. **亲手跑**：跟着每步跑一次基线，确认绿了再让它走下一步（练习的核心是"你真的一步一验，不是只看 AI 说绿"）。
5. 最后用整合提示词产出「逐步重构记录」。

**对答案**：一份合格的逐步重构记录应含"前置补基线 + 小步 N（改了什么/diff 摘要/验证结果）+ 每步结论"，且**步进 diff 越小越好**、全程基线绿推进。

- **前置**：确认 3 个 JSON 绑定站点的基线测试在且绿（B3-① 建的）。
- **小步 1**：新增 `bindJSON` / `respondError` helper（纯新增，不替换），`go test` 绿。

- **每步结论**：5 小步各独立可验证、全绿推进，无一步塞大坨。

> 🔎 **（可选进阶）体验"不绿该怎么处理"**：故意在**小步 2** 让 AI 不小心把某条 handler 的返回体改了一个字段（比如把 `status` 字段漏了），跑基线会红——你能借此体会"一步一验"的价值：**红立刻定位到小步 2，回退再改，不用翻首尾十几行 diff。**
