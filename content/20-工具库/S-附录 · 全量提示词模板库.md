# S-附录 · 全量提示词模板库

> **定位**：整套《Vibe Coding 工程化》教程所有"填空式提示词"的**集中速查库**。
> **目标**：正文各章教"怎么用、为什么、怎么判断"，这里一句话不落地把它们收全。走到任何一步要"照抄即用"的提示词，来这张表复制填空即可，不用回头翻正文。
> **适用**：B1 通用需求 / B2 Bug 修复 / B3 重构 三条轨道的全部环节（含共享单元 S-A / S-B / S-C / S-D）。
> **预估时长**：不需要专门学——它是工具箱，用时来取。

> ⚠️ **怎么读这张表**：这是一份"速查索引"，不是"教学正文"。每条提示词的**逐字段解析、追加追问、递归用法**都在**正文出处**里讲透了，这里只负责"把完整可复制的提示词放在一处 + 一条一句告诉你它用在哪"。需要弄懂原理时，回看正文对应小节。

## 一、怎么用（三句话）

1. **先对阶段**：看第二节「速查总览」，按你当前所处的**轨道 + 环节**（如 B1-② 技术方案）定位该用哪几条。
2. **再复制填空**：跳到对应条目，复制引用块里的编号提示词，把 `[占位符]` 换成你的需求名词即可丢给 AI。
3. **要理解或加戏**：回"正文出处"看逐字段解析与递归用法；S-附录 不重复这些，只在每条下留一行指引。

> 💡 **裁剪原则**：提示词按"完整流程"写的，简单任务可只取其中几条。拿不准要不要省略时，参考 S0 的"复杂度三问"（影响面 / 依赖者 / 坏了后果）。

> 🗣️ **多轮谈不动 / 判不准反问题？** 这是一条元技能，不占提示词——去 [S-对话] 看"核验三问 + 对话纪律"（本附录管"给什么提示词"，S-对话管"怎么谈不崩"）。

> 🧭 **进阶操作速记（四条通用迭代手法，全程复用；下面各条目里出现的内容归到这里一次讲透）**：
> - **追问**：某条提示词结果太粗 → 追加"请补齐 [边界 / 失败 / 一致性] 上的表现"。
> - **递归**：第一版不满足 → 把结果回喂 AI，追加"请对每条功能需求补齐验收标准和边界条件"，迭代 2–3 轮。
> - **整合**：多条碎片产出 → 用对应的整合提示词（B1-2 需求 / B1-6 方案 / S-2b 现状 / S-7 测试 / S-12 交付）收拢成规范交付物。
> - **选填（选项式澄清）**：某条追问/选择你要是没想清楚 → 追加"请按[行业]通用做法给我 2–3 个常见默认选项，让我挑，别让我凭空创造"。适用于"需要你产出一个答案或拍一个选择"的提示词；每条下方标了 🔽：就是高发的那几条。
>   - **看不懂选项时先别硬挑** → 追加"先别急着要我选：先用大白话讲清这 2–3 个选项各自是什么、差别在哪、各自取舍和后果，我懂了再选"。**你只有在懂了差别之后点的头才算数**（守住人类决策权）。

## 🧭 给纯新手：先认术语、认编号（任一条读懵先来这）

> 如果你读正文或这张表时，被某些"单词/编号"卡住（术语恐慌），先别慌——它们大多有句大白话。这里一次性给你一张速查：**记住它们不是本事，会用才是**，看不懂不扣分。

**① 高频术语大白话速查**

| 术语 | 一句大白话 | 你会在哪遇到 |
|---|---|---|
| **幂等** | 同一操作做两遍，结果 = 做一遍（如退款接口重试不会重复扣两笔钱） | B1-①⑤、S-B |
| **状态机 / 状态流转** | 一个对象只会按"画好的线路"变状态（如 待处理→已退款→已关闭），不能乱跳 | B1-②④、S-A |
| **回归测试** | 改完新功能后，把"旧的没坏"也验证一遍（确认没把别处搞坏） | S-B |
| **AST** | 把代码按"语法结构"拆成一棵树，程序据此理解/改写代码 | S-A 练习 |
| **行为基线 / characterization tests** | 重构前先把"当前实际行为"用测试钉住，之后照着比对，防止改着改着变了味 | B3-① |
| **WBS** | 把大任务逐层拆成小任务（Work Breakdown Structure，工作分解结构） | B3 |
| **Mermaid** | 一种用文本画流程图/时序图的语法（```mermaid 围栏块） | 多处"架构图" |
| **ADR** | 记"当初为什么这么选"的决策记录（Architecture Decision Record）；一句话＝"选了 X，因为 Y；没选 Z" | B1-③ |
| **坏味道（code smell）** | 代码里"闻起来不对劲"但能跑的结构问题（如重复样板、超长函数），是重构的候选 | B3-② |
| **golden 测试 / 快照测试** | 把"输入→预期输出"写进测试做表驱动断言，跑 `go test` 自动比对，行为一改就红 | B3-⑤ |

**② Mermaid 你看到的是源码、不是图？**
- 这不是你错了，而是**这个查看器没渲染 Mermaid**。它需要支持渲染的 Markdown 环境：**GitHub 网页原生渲染**；Trae / VS Code 需装 Mermaid 插件；装好后上面的 ```mermaid 块会自动变成流程图。

> 🔎 **怎么认出"该渲染的代码块"**：看到 ```mermaid 开头（注意是反引号+ mermaid），就是流程图所在；在你的支持引擎里它应显示成图。

**③ 编号怎么认（别被 S-1-Lite / B1-7b 吓到）**
- `S-` 开头 = 三轨道通用的共享工具；`B1-` / `B2-` / `B3-` = 对应轨道的环节；`-a / -b / -Lite` 这类后缀 = 同一大编号下的细分或轻量变体。
- **判断哪条该记、哪条可忽略**：**凡条目下方"附了完整可复制提示词"的编号，是用给你照抄的**；只在正文里被提及、没有附提示词的编号，只是**章节内的小节索引/交叉引用，读过去就够，不用单独记**。拿这条一眼分清，整张表就不再有"噪音"。

## 三、S 区（三轨道通用）

> 这三条的读者覆盖 B1 / B2 / B3 全部轨道。改动代码前、之后、要交付文档时，都回到这一区。

### S-1 · 代码库探索（生成代码库地图）

> 你是一名资深架构师。请分析以下代码库，输出一份代码库地图：
> [项目根目录 / 关键文件列表]
>
> 要求包含：
> 1. **整体架构与分层**（这是什么架构、分几层）；
> 2. **各模块职责**（每个目录/包是干什么的）；
> 3. **入口与关键流程**（程序从哪启动、一次典型请求怎么流转）；
> 4. **核心数据模型**（关键实体/表及关联）；
> 5. **模块间依赖关系**（谁依赖谁、有没有环、最底层是哪些）；
> 6. **可能需要修改的风险点**（耦合重、缺测试、易炸的地方）。
>
> 输出 Markdown 格式。

**何时用**：在已有代码库上动手前；**出处**：S-A · 三。
**进阶追问**（需要时追加）："请具体描述一次 [某典型请求] 从入口到数据库的完整调用链"；"请明确指出哪些模块是最底层、改动成本最高、最不该碰"。
**递归用法**：第一版先只要求第 1/2/3 点快速上手，要动某一块时再对该块单独深挖。
**🔽 选填**：不确定该贴哪些目录/文件 → 追加"请基于当前代码库自行挑选核心入口 + 关键文件开始分析"。

### S-1-Lite · 狙击手模式（新手 / 大项目轻量进场）

> 我是新手，先不看全量架构。请只针对我要改的 `[功能名]`：
> ① 它在哪个文件是**入口**（如 Controller / 路由 / 事件监听）；
> ② 从这个入口向下追**最多 2 层**调用，分别依赖了哪几个关键文件/函数；
> ③ 只用几句话说明这 3–5 个文件各自是干什么的，**超过 2 层的先忽略**。
> 输出：入口文件 → 调用到 2 层的文件职责清单。

**何时用**：代码库很大 / 新手不想一上来啃全量地图时；**出处**：S-A · 新手免责声明。
**为什么"只追 2 层"**：先在你改动的局部建立最小认知，够动手就行；等要深挖某处时，再对应 S-A 第 2/3 步或全量 S-1 补深。

### S-2 · 验证"被谁依赖"（证据追问）

> 请为你上面的每一条"被谁依赖"，给出证据——具体是哪个文件的哪一行 import / 调用，
> 把相关代码贴出来，不要给泛泛的模块名。

**何时用**：S-A 第 3 步让 AI 逐模块说完"是什么 / 干什么 / 被谁依赖"之后，抽查它的"被谁依赖"是否属实；**出处**：S-A · 二 第 3 步。
**为何必须做**：AI 的地图可能过时/编造，而"被谁依赖"决定你的爆炸半径——判断错了，后面所有影响面评估都跟着错。抽查 1–2 处即可确认它这块可靠。

---

### S-2a · 评估受影响面（定义/直接/隐藏/影响）

> 我要改动 `[函数/字段名]`，请帮我精确评估受影响面：
> ①它在哪个文件定义；②列出全部直接调用点（含文件+行号）；
> ③找出可能存在的隐藏调用点（事件名 / 依赖注入别名 / 字符串 key），逐一贴出调用证据；
> ④给出改它之后需要回归测试的模块清单。

**何时用**：改动某个函数/字段前，估算波及面；**出处**：S-A · 二 第 2 步。
**为什么有 ③**：文本搜索对"事件/依赖注入/字符串"的调用是盲区——漏掉隐藏调用点，改完线上才炸。

### S-2b · 现状探索产出物整合（四段）

> 请把我这次现状探索的产出整理成一份「现状探索产出物」（四段）：
> [粘贴：代码库地图] [粘贴：受影响面清单] [粘贴：模块三句话] [粘贴：速查表草稿]
> 按 1.代码库地图 / 2.受影响面清单 / 3.模块三句话 / 4.关键文件速查表 输出；速查表合并重复文件、只留"要动手"的关键文件。输出 Markdown。

**何时用**：S-A 走完四步后，把碎片收拢成规范交付物（导航底图）；**出处**：S-A · 二「沉淀成产出物」。

### B1-1a · 需求澄清：五维清单追问

**何时用**：B1-① 澄清"边界与约束"；**出处**：B1-① · 二 目标一。产出 = 五维清单（角色/对象范围/触发状态/规则限制/环境前提）。
**卡壳应对**：答不上某维 → 直接回 AI"这部分我没想好，按行业最佳实践给我推荐 3 种选择+利弊，我来挑"（见 B1-①"卡壳救助站"）。

**何时用**：B1-① 澄清"验收标准"；**出处**：B1-① · 二 目标二。产出 = 验收清单（正常+边界+异常）。

### B2-1 · 复现与界定 Bug（构造最小复现步骤 MRE）

> 我遇到一个 Bug：`[一句话症状]`。请帮我把它稳定复现并界定清楚：
> ① 触发条件：什么输入 / 操作 / 环境下必然触发？列出最关键的 1–3 个触发因子；
> ② 实际输出：复现时实际得到什么（报错 / 返回值 / 界面表现），贴出证据；
> ③ 期望输出：按需求 / 业务直觉应该得到什么；
> ④ 影响范围：波及哪些功能 / 数据 / 用户，严重程度如何；
> ⑤ 最小复现步骤（MRE）：给出能复现它的最短操作路径，越短越好。
> 若某个触发因子我不确定，先按最可能的情况给一版，标注"待验证"，我再实测确认。

**何时用**：B2-① 复现与界定 Bug；**出处**：B2-① · 二 目标一。产出 = 复现说明（四要素：触发条件 / 实际 vs 期望输出 / 影响范围 / 最小复现步骤）。
**🔽 选填**：说不清"一句话症状" → 追加"请先按[行业]常见故障形态给我 2–3 个可能方向，我挑最像的那个再展开"。

### B2-1a · 二分法缩小触发条件

> 我按上面的步骤复现了，但触发条件还不确定是哪一个。请帮我用二分法缩小：
> ① 列出所有可能影响复现的变量（输入 / 环境 / 数据状态）；
> ② 每次只改一个变量、固定其余，给出"改哪个、预期会怎样"的对照实验；
> ③ 根据我回报的结果，逐步排除无关变量，直到锁定最关键的触发因子。

**何时用**：B2-① 复现后锁定关键触发因子；**出处**：B2-① · 二 目标二。产出 = 触发因子清单（哪个条件一改 Bug 就消失）。
**为何必须做**：触发条件不止一个时，不缩小就进 B2-②，等于带着"多个嫌疑犯"去定位根因，容易误判。

> ③ 反向推断：基于代码 + 数据变化推断根因到底是什么，给出推导链路；
> ④ 待确认点：列出 1–2 个我还需要实测 / 加日志确认的怀疑点，别替我拍板。

**何时用**：B2-② 定位根因；**出处**：B2-② · 二 目标一 / 二。产出 = 根因报告（根因一句话 + 推导链路 + 1–2 个待确认怀疑点）。

**🔽 选填**：调用链太长看不完 → 追加"先只追 `[入口]` → `[症状所在函数]` 这一段，命中就停"。

### B2-4 · 修复（做最小改动让测试转绿）

### B3-2 · 识别坏味道与风险点

### B3-3 · 设计重构方案

> 这是我要重构的目标与「重构清单」：

### B3-4 · 小步重构、频繁验证

> 按下面这份重构方案，帮我一步步小步重构（每步改完就验证、不憋大招）：

> ② 补基线：先按方案"前置补基线"补齐全并全绿，再开始改；
> ③ 一步一验：每完成一小步，给出这一步的 diff 摘要 + 跑哪条基线/哪些用例，确认绿了再进下一步——每步同时把 `go test`（行为基线）、`go vet ./...`（静态）都跑绿、并核对对外契约（api-reference）diff 空，三者齐净才算过；**不绿的步骤立刻停下说明原因，别往下带**；
> ④ 记录：输出「逐步重构记录」，每步含 改了什么 / diff 摘要 / 验证结果。

**何时用**：B3-④ 小步重构、频繁验证；**出处**：B3-④ · 二 目标一 / 二。产出 = 逐步重构记录（每步 改了什么 / diff 摘要 / 验证结果，全绿推进）。
**💡 复用关系**：验证复用 **S-B**（S-5 改成 / S-6 回归）与 B3-① 行为基线；本轨道强调"一步一验、不绿的步骤停顿"，避免憋大招越改越歪。
**🔽 选填**：步子大小拿不准 → 追加"优先用最保守的小步（每步只动一处），宁可多几步也别一步改一片"。
