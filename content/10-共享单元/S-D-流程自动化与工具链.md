# S-D · 流程自动化与工具链（三分支共用）

> **轨道**：共享单元（B1 / B2 / B3 共用，整条流程的收尾固化）。
> **前置**：已经历一遍 S0→S-C 的完整流程，体会到各阶段的产出。
> **目标**：把前面所有流程**固化到工具中**，减少重复劳动——让"该做的检查"变成"自动就跑"，而不是靠人记得。
> **预估时长**：1–2 小时。

你已走完整条流程（工具链是教程里唯一"自带变数"的阶段：每个人的工具栈不一样，所以**没有放之四海的模板**，有的是**一套定制方法**）。S-D 的价值：把 S0–S-C 积累的"每次都要手动做"的动作（喂提示词、搭骨架、跑测试、盯文档）变成**一份配置 + 几条脚本**，以后一键复用。

> 一句话：**把方法论变成你的"工具箱"——好流程用一次只能帮一次，固化成工具能帮一辈子。**

---

## 一、通用方法：四个固化动作

### 🔴 ① 建自定义提示词库

**产出**：一份**存成文件、随时唤起**的自定义提示词库（Cursor Rules / Claude Projects / 文本模板皆可）。

**可复制的拆分维度**：

| 维度 | 要确认的核心 | 装进「退款」 |
|------|--------------|--------------|
| 承载 | 提示词存在哪、怎么被触发？ | Cursor Rules / Projects / Markdown 模板 |
| 来源 | 从哪收集这些提示词？ | 跳转 S-附录 按需挑选（不必全模板化）+ 你在 B1/2/3 里调到好用的 |
| 维护 | 换项目 / 换语言怎么复用？ | 增量模板化：`[功能]` 槽位通用化 |

**照抄即用的通用追问提示词**：

> 帮我把这段提示词整理成通用模板：把项目相关的硬编码都改成 `[槽位]` 占位符，并加一段"如何复用、何时触发"的说明，输出成一份可直接存放的形式。

> 💡 **关键判断**：提示词库的**灵魂是把"一次性好使"变成"换成 `[槽位]` 就能反复用"**——凡是你在某个分支里用到趁手的，都花 2 分钟模板化收进来。

### 🔴 ② 用脚本 / 模板自动生成骨架

**产出**：一套自动生成**需求文档 / 任务列表 / 测试框架**骨架的脚本或模板。

**可复制的拆分维度**：

| 维度 | 要确认的核心 | 装进「退款」 |
|------|--------------|--------------|
| 生成对象 | 哪些每步都要建的东西值得自动化？ | 需求文档空壳、任务清单表、测试骨架 |
| 实现 | 用脚本还是纯模板？ | 脚本生成 + 模板填充 |
| 接入 | 每次怎么触发？ | 一条命令 / 一个快捷键 |

**照抄即用的通用追问提示词**：

> 请为我写一个脚本，输入一个功能名，自动生成：需求文档脚手架的六要素空模板、任务列表表格、测试目录与文件骨架。要求：可重复运行、参数化"功能名/语言/框架"。

> 💡 **关键判断**：**优先自动生成"结构固定、只换名字"的部分**（六要素模板、任务表头、测试骨架），别为了省手打去硬自动化那些每次都会变的设计内容。

### 🔴 ③ 集成 CI/CD：提交前自动测试 + AI 审查

**产出**：一个**提交前自动跑测试 + Lint + AI 代码审查**的 CI 配置。

**可复制的拆分维度**：

| 维度 | 要确认的核心 | 装进「退款」 |
|------|--------------|--------------|
| 触发时机 | 什么时候自动跑？ | 提交前 hook / PR 阶段 |
| 跑什么 | 自动执行哪些门槛？ | 单测 + 静态检查 + 回归 |
| 审查 | 有没有 AI code review？ | 合 PR 前让 AI 过一遍改动 |

**照抄即用的通用追问提示词**：

> 请为这个项目配置 CI：① 提交/推送前自动运行 [测试命令] 与 [静态检查]；② 加一个 hook 在提交失败红测试时拦截；③ 生成 AI 代码审查的提示词，供 PR 阶段使用。给出配置文件与说明。

> 💡 **关键判断（三分支门槛不同）**：**B1** 守"单测全绿"；**B2** 额外锁"复现 Bug 的用例不许再红"；**B3** 再锁"行为基线测试在全绿才允许合并"——CI 把这三条"人的纪律"变成"机器强制"。

### 🔴 ④ 建立流程规范

**产出**：一份**个人或团队**的流程规范（每个阶段的产出 + 完成标准）。

**可复制的拆分维度**：

| 维度 | 要确认的核心 | 装进「退款」 |
|------|--------------|--------------|
| 对象 | 规范是自己用还是团队用？ | 个人速查 vs 团队 Wiki |
| 阶段产出 | 每步必须交什么？ | 需求文档 → 方案 → ADR → 任务卡 |
| 把关 | 每步"算完成"的标准是什么？ | 验收清单打勾 + 测试通过 |

**照抄即用的通用追问提示词**：

> 把我在 vibeCoding 教程里逐步用到的规范，整理成一份[个人/团队]流程规范：每个阶段列出「必交产出 + 完成标准 + 参考提示词出处（S-附录）」，输出为一份可维护的文档。

> 💡 **关键判断**：**规范按团队规模"从简迭代"**——一个人先在脚本里跑通，再拿去给小团队试点，别一上来写 50 页没人遵守的制度。**够用就行，运转起来再补。**

## 二、沉淀成「工具链清单」（本步的产出物锚定）

你这一章要"交出去"的，是一套**能直接运作的工具链**。它由四块拼成，先看覆盖全不全，再谈优不优：

```markdown
# 我的 vibeCoding 工具链

## 1. 提示词库      来源：跳转 S-附录 按需挑选 + 自定制，放 [载体：Cursor Rules/Projects/模板]
## 2. 生成脚本       自动产出：需求文档骨架 / 任务列表 / 测试框架
## 3. CI/CD         提交前：单测 + 静态检查 + AI 审查；PR 阶段：AI code review
## 4. 流程规范       每阶段必交产出 + 完成标准（可追溯回 S-附录 的提示词）
```

**怎么写？**
- 按 ①–④ 逐个落地，把配置、脚本、规范**全部纳入版本控制**（和 S-C 的要求一致）。
- **整合提示词**（把四块拼成清单）：

> 请汇总成一份「工具链清单」：我已有 [提示词库内容 / 脚本 / CI 配置 / 流程规范]。按 提示词库 / 生成脚本 / CI/CD / 流程规范 四块输出，逐块标 ✅ 已就绪 / ⚠ 需补，并建议下一步优先补哪块。

**检查标准**：按清单跑一遍，能"一条命令 + 一条提示词"复现 S0→S-C 的核心产出，不再靠人肉回忆每一项。

> 📌 工具链把我们在这套教程里一路锚定的"产出物"（需求文档、ADR、任务卡、测试报告、交付物）都改成了**机器可检查的门槛**——这是全教程的落脚点：**流程 -> 产出 -> 工具，层层固化。**

## 三、本步无需固定提示词（教你"怎么定制"）

大纲明确"提示词模板：不固定，鼓励学员按自身需求定制"。所以这一章不给"照抄即用"的固定模板，而给你**三条定制的元规则**：

1. **先沉淀你用过、好使的**——回看你 B1/B2/B3/S0–S-C 里"让 AI 输出最稳"的那几次，把那次提示词抽成模板。
2. **把硬编码改成 `[槽位]`**——凡是会换的（功能名、语言、框架、路径）一律占位，让模板能复用。
3. **测试它、迭代它**——新模板先在本周真实任务上验证一次，不顺手的立刻改；**先求运转，再求完美**。

> 💡 需要填空式例句的话，直接回头翻 **S-附录 · 全量提示词模板库**——你所有工具的"原材料"就在那里。**不必全模板化**：先从你用最勤的 3 条开始，按元规则模板化成 `[槽位]` 即可起步。

## 四、练习：为自己配置一套提示词模板和自动化脚本

**任务**：给自己的工作流配好第一版工具链。

**推荐步骤**：
1. 用「建提示词库」的追问，从 S-附录 挑你用最勤的 3 条 + 你常用的提示词，模板化收进一个载体。
2. 用「生成脚本」的追问，做出"输入功能名 → 一键生成需求/任务/测试骨架"的脚本。
3. 用「集成 CI/CD」的追问，/**或用现有平台**，配好"提交前自动测试 + PR 审查"。
4. 用「建流程规范」的追问，写明"每阶段交什么、算完成的标准"。
5. 用「沉淀工具链清单」的整合提示词，核一遍四块是否就绪，补最薄弱的一块。

**对答案**：照着你的工具链跑一个新功能，能让 需求→方案→任务→测试 的骨架在几分钟内自动就位。
