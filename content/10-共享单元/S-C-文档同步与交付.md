# S-C · 文档同步与交付（三分支共用）

> **轨道**：共享单元（B1 / B2 / B3 都必经，三分支共用）。
> **前置**：需要最终可运行的代码 + S-B 的**测试报告**。
> **目标**：让**文档与最终代码一致**，形成一份**可持续维护的交付物**——代码改动多大，文档就同步多大。
> **预估时长**：40–60 分钟。

代码写完、测试通过，还差最后一件最容易被跳过的：**文档。** 没有它，三个月后的你对着代码也只能一脸茫然，新同事更是无从下手；而且"文档和代码不一致"比"没有文档"更坑人——你以为的接口和实际跑的对不上，比没有更危险。

> 一句话：**交付的不只是代码，而是"代码 + 一致的解释"。** 文档的价值不在写，在"和代码对得上"。

---

## 一、通用方法：四个环节

### 🔴 ① 让 AI 同步代码到文档

**产出**：一份与**最终代码一致**的设计文档 / 接口文档。

**可复制的拆分维度**：

| 维度 | 要确认的核心 | 装进「退款」 |
|------|--------------|--------------|
| 更新对象 | 哪些旧文档已过时？ | 接口文档、数据模型、架构图 |
| 对齐代码 | 文档表述是否和最终实现一致？ | 退货接口是否真叫 `/api/refunds` |
| 校正差异 | 文档与代码冲突时以谁为准？ | 以代码为准，改文档 |

**照抄即用的通用追问提示词**：

> 请对照当前代码实现，更新我项目的[H 设计 / 接口 / 数据模型]文档。
> 文档路径：[各文档路径]
> 要求：① 逐项核对文档与代码是否一致；② 以代码为准修正文档；③ 列出你做过的所有改动。

> 💡 **关键判断**：**文档一般跟着真实实现和契约为准，不是无脑反向。** 当文档和代码打架，先怀疑谁过时——多数是文档写早了、没跟上实现，此时以代码为准改文档；但**如果那条接口是"对外契约"（下游已在用、不能随便破坏），代码反而要以契约为准改回去**。一句话：**文档同步反映真实代码，而"真实"由实现与对外契约共同认定。**

### 🔴 ② 生成 API 参考与使用说明

**产出**：一份 **API 参考 + 使用说明**（怎么调、传什么、返回什么、注意事项）。

**可复制的拆分维度**：

| 维度 | 要覆盖的核心 | 装进「退款」 |
|------|--------------|--------------|
| API 参考 | 每个接口的方法/路径/入参/出参/错误码？ | 退款接口的完整签名 |
| 使用说明 | 别人怎么上手用这个功能？ | "调退款前先查订单状态" |
| 注意事项 | 有哪些坑要提醒？ | 幂等键必传、金额上限 |

**照抄即用的通用追问提示词**：

> 请根据当前代码生成「API 参考」和「使用说明」：
> 代码位置：[文件/模块]
> 输出：① 接口清单（方法/路径/入参/出参/错误码）；② 一段"怎么用"的说明；③ 注意事项清单。

> 💡 **关键判断**：API 参考的**入参/出参必须能从代码断言**（直接抽取签名），不能凭记忆写——记忆最不可靠。

### 🔴 ③ 更新 CHANGELOG、文档入版本控制

**产出**：一份**更新的 CHANGELOG** + 已纳入版本控制的文档。

**可复制的拆分维度**：

| 维度 | 要确认的核心 | 装进「退款」 |
|------|--------------|--------------|
| CHANGELOG | 本次改动用一句"发生了什么变化"记录？ | 新增退款接口、修复部分退问题 |
| 版本控制 | 文档是否和代码一起入库、可回溯？ | docs 目录纳入 git |

**照抄即用的通用追问提示词**：

> 请根据以下改动，更新 CHANGELOG：
> [粘贴：本次提交/改动说明]
> 要求：① 用"新增 / 修复 / 变更 / 移除"归类；② 每类一句话、面向读者而非流水账；③ 输出本次变更清单。

> 💡 **关键判断**：文档**(docs)**和代码**同一次提交、同一仓库**，才算真的可回溯——单独丢在别处等于没存。

### 新手落点：手把手把文档存进版本控制

> 上面说"文档和代码同一次提交、同一仓库"，如果你连"把文件写进 git"都没做过，照下面 4 步走一次就会了（前提：已会 S0"第 0 步"的最小 git：`init/add/commit`）。

**Step 1 · 建目录**：项目根目录下建一个 `docs/`（存所有产出物）。让 AI 建也行：`让 AI 在项目下建 docs 目录`。

**Step 2 · 把产出存成文件**：把你最早的产出（如 B1-① 需求文档）让 AI 写成 `docs/requirements.md`。一句话话术：

> 把我上一步整理的需求文档，按六要素模板写成 `docs/requirements.md`，并直接放进 `docs/` 目录。

**Step 3 · 纳入 git（3 条命令）**
```
git add docs/
git status            # 应看到新增的 docs/requirements.md（绿色 = 已暂存）
git commit -m "docs: 需求文档"
```

**Step 4 · 验证可回溯**
`git log --oneline` → 能看到你这条 `docs:……` 提交，就成功了。以后每改一次代码，就顺手更新 `docs/` 里对应文档、再 commit 一次——**文档和代码从此锁进同一条历史，随时能翻回去看"当初怎么写的"。**

> 💡 **判断成功与否**：`git log --oneline` 里能看到这条 docs 提交 = 完成。看不到（提交失败/没 add）就用 S-对话"喂报错姿势"把错误带给 AI。

### 🔴 ④ 核对交付物清单

**产出**：一份**交付物核对清单**（代码 / 设计文档 / 测试报告 / 部署说明等有无齐备）。

**可复制的拆分维度**：

| 维度 | 要确认的核心 | 装进「退款」 |
|------|--------------|--------------|
| 清单项 | 交付需要哪些东西？ | 见下"沉淀成交付物"四件 |
| 完备性 | 是否有缺项？ | 有设计无测试报告=缺项 |
| 对准 | 交付物是否与代码/需求一致？ | 部署说明和真实启动方式一致 |

**照抄即用的通用追问提示词**：

> 请对照一下，本项目当前交付还缺什么：
> 所需交付物：[代码 / 设计文档 / 接口文档 / 测试报告 / 部署说明 / CHANGELOG]
> 逐项给出：✅ 已有 / ⚠ 过时 / ❌ 缺失，并给缺失项的补齐建议。

> 💡 **关键判断（三分支补哪些文档）**：**B1** 补全设计 + 接口 + README；**B2** 在 CHANGELOG 里记清"修了什么 Bug、复现路径"；**B3** 重写被重构改动的结构 / 接口文档——**三支都把"对得上代码"当标准，不堆没用的长文档。**

## 二、沉淀成「交付物清单」（本步的产出物锚定）

你这一章要"交出去"的，是一套**可持续维护的交付物**。核心是下面这份清单，逐项都有"什么 + 标准"：

```markdown
# 交付物清单：<功能 / Bug 修复 / 重构>

## 交付四项
1. 代码             已提交、通过 S-B 测试、纳入版本控制
2. 设计文档         与最终代码一致（用 ① 校正）
3. 测试报告         四段结构（范围/用例结果/回归结论，来自 S-B）
4. 部署说明         真实的启动/配置方式，与代码一致

## 辅助项
- API 参考 + 使用说明  从代码抽取，可断言
- CHANGELOG           本次变更按 新增/修复/变更/移除 归类
- README              使用方式 + 注意事项
```

**怎么写？**
- **四件主交付物**必须齐、且**一致**；辅助项按分支取舍（B1 全补、B2 至少 CHANGELOG、B3 至少结构/接口文档）。
- **整合提示词**（把各环节产出拼成交付清单）：

> 根据以下素材，整理成一份「交付物清单」：
> [粘贴：代码提交说明] [粘贴：设计/接口文档改动] [粘贴：S-B 测试报告] [粘贴：部署说明与 CHANGELOG]
> 按"交付四项 + 辅助项"输出，逐项标注 ✅ 可用于交付 / ⚠ 需补 / ❌ 缺失。

**检查标准**：照着清单，读者能拿到 "可运行的代码 + 一致的文档 + 可信的测试报告 + 可复现的部署方式"。

> 📌 文档和测试报告共同进入 git，随 **S-D 工具链**固化成"每次改完自动提醒补文档"的闭环，交付物才算真正稳定。

## 三、提示词模板：文档更新提示词（S-C 三轨道通用）

> 请根据当前代码实现，更新相关设计文档、README 和 CHANGELOG。
> 确保文档与代码一致，描述清楚使用方法和注意事项。

**逐字段解析**：

- **"根据当前代码实现"**：锚定"以代码为准"，防止 AI 凭空发挥。
- **"设计文档、README、CHANGELOG"**：三份各管一事——设计管结构、README 管使用、CHANGELOG 管变更史。
- **"确保文档与代码一致"**：这是 S-C 的灵魂；不一致等于误导。
- **"描述清楚使用方法和注意事项"**：把"怎么用"和"有什么坑"讲清，别只写会不改凝结的术语。

> 💡 **递归用法**：更新完先不直接收下，回喂"请把文档里任何与代码不一致的表述逐条列出并全部修正"，能有效拦截"AI 复述了过时描述"。

## 四、练习：同步文档并核交付物

**任务**：把当前改动同步到文档，并核对交付物。

**推荐步骤**：
1. 用「同步代码到文档」提示词，让 AI 对照代码更新过时文档。
2. 用「生成 API 参考与使用说明」提示词补出可断言的接口说明。
3. 用「更新 CHANGELOG」提示词，给本次改动归类记录。
4. 把文档与代码同库提交到版本控制。
5. 用「核交付物清单」提示词，对照四件交付逐项核对，补齐缺项。

**对答案**：你能回答"哪些文档被改过、为何改、README/CHANGELOG 是否同步、四个交付物是否齐且一致"。
