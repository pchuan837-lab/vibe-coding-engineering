# S-B · 测试与回归（三分支共用，各自侧重不同）

> **轨道**：共享单元（B1 / B2 / B3 都必经）。
> **前置**：需要一份"被测对象"，任选其一——B1 的需求文档 + 技术方案、B2 的 Bug 复现结果、B3 的行为基线（S-A）。
> **目标**：用测试**验证正确性**，确保新修改**不破坏已有功能**；三分支复用同一套方法，但各自侧重不同。
> **预估时长**：1–2 小时（B2/B3 视回归范围而定）。

B1 的新功能、B2 的 Bug 修复、B3 的重构——**代码落在"动了就可能有副作用"的世界里**。测试就是那道"我没改坏东西"的保险。不写测试的"改好"，只是"这次碰巧没炸"；有了测试，才算真的敢改。

> 一句话：**让每一行改动都有"证据"说它没把别的弄坏。** 三分支的区别只在"先建什么、守什么"——B1 守需求，B2 先锁 Bug，B3 先锁行为。

---

## 一、通用方法：四个环节

### 🔴 ① 生成测试用例

**产出**：一份按**正常 / 异常 / 边界**组织的测试用例清单。

**可复制的拆分维度**：

| 维度 | 要测的核心问题 | 装进「退款」 |
|------|----------------|--------------|
| 正常 | 数据/流程都对时，预期结果？ | 全款退：库存回滚 + 券退回 + 金额一致 |
| 异常 | 出错/被拒时，行为是否安全？ | 金额超剩余、订单已关闭、支付回调失败 |
| 边界 | 临界值/极限输入是否稳？ | 部分退款到上限、重复提交同一 `refundNo` |

**照抄即用的通用追问提示词**：

> 基于以下需求文档/行为基线，生成测试用例清单：
> [粘贴：需求文档 或 行为基线]
> 请按 正常 / 异常 / 边界 三类组织，逐条给出：
> ① 前置条件；② 操作步骤；③ 预期结果。
> 只给用例，暂不写代码。

> 💡 **关键判断**：用例的"预期结果"必须可断言（对应某个返回值/状态/金额），不能写"应该正常"这种空话——否则它测不出来。

### 🔴 ② 生成测试代码

**产出**：一串**可运行**的测试代码（单元 + 集成 + 端到端）。

**可复制的拆分维度**：

| 类型 | 测什么 | 什么时候最该用 | 装进「退款」 |
|------|--------|----------------|--------------|
| 单元测试 | 单函数/单类的逻辑 | B1 新代码、B3 重构反复跑 | 退款金额计算 |
| 集成测试 | 模块间/系统间协作 | B1 跨服务、B2 联调 | 退款 → 库存回滚的协作 |
| 端到端 | 整条用户流程 | B2 复现路径、B1 流程验收 | 用户点退款 → 款项到账 |

**照抄即用的通用追问提示词**：

> 请把上一步的测试用例写成可运行代码。
> 测试框架：[如 pytest / jest / go test]
> 代码位置：[文件/模块]
> 要求：覆盖用例清单全部条目；每个测试能独立运行；数据用假数据/脱敏。请先列出将创建的测试文件与各自覆盖点，再写代码。

> 💡 **关键判断（三分支怎么选类型）**：**B1** 以单元测试为主、配流程端到端；**B2** 隔着 Bug 复现路径写**端到端/集成**去锁死它；**B3** 以单元测试为主、让重构中测试全程绿的"行为基线"优先。

> 💡 **别把"按 Bug 归属选层"误解成"只测这一层就够"**：三层测的是**不同维度**的契约、是互补关系、不是替代关系——单测过了不代表路由把参数传对了（那是 routes 层的事），routes 层过了不代表数据库事务正确提交了（那是 integration 层的事）。"按归属先补这一层"是在最该守的契约上优先补一条冒烟，其余两层照样要各自验证，三层叠起来才完整。

### 🔴 ③ 运行测试、分析失败、迭代修复

**产出**：一份**测试报告** + 对每个失败用例的**根因分析**。

**可复制的拆分维度**：

| 维度 | 要判断的核心 | 装进「退款」 |
|------|--------------|--------------|
| 怎么跑 | 用什么命令全量/定向跑？ | `go test ./refund/...` |
| 失败定位 | 失败是代码 Bug 还是测试写错？ | 断言错了？还是真的多退了？ |
| 迭代修复 | 改哪边、要不要先让测试变正确？ | 先修测试到"诚实"，再修代码 |

**照抄即用的通用追问提示词**：

> 我运行测试得到以下输出：[粘贴失败输出]
> 请：
> ① 逐条判断是"代码缺陷"还是"测试用例本身写错"；
> ② 对"测试写错"的，给出修正；
> ③ 对"代码缺陷"的，给出最可能的根因与修复建议。
> 输出格式：用例 → 判断 → 处理。

> 💡 **关键判断**：**测试红了自己先别慌着改代码**——先判断是不是测试写错了。测试撒谎（错误断言）比代码 Bug 更隐蔽，会误导你。

### 新手落点：从"用例"到"能跑"到底要几步（全程手把手）

> 如果你**从没写过一次测试**，② 的提示词拿到手里也未必敢用。别慌，最小示范就是下面 5 步，跑通一次你就跨过了"完全不会"这道坎。

**前提**：你已有一个能跑的最小项目（固定：S0"第 0 步"配的装备）。

**Step 1 · 选框架**（就看你项目技术栈）
| 栈 | 测试框架 | 跑的命令 |
|---|---|---|
| Python | pytest | `pytest` |
| JavaScript / TypeScript | Jest（或 Vitest） | `npm test` |
| Go | go test（内建，无需装） | `go test ./...` |

> 拿不准就让 AI 推荐，但**让它只推荐一个、并给你一条能启动的命令**——别一次抛给你三种让你纠结。

**Step 2 · 建一个最小测试文件**（先别全量写）
- Python：建 `tests/test_demo.py`；JS：建 `refund.test.js`；Go：建 `refund_test.go`。
- **只放一个真断言**，目标是"跑起来"，先不当全面测试。

**Step 3 · 写第一个真实断言**（挑最核心那一个用例）
以 Python + pytest 为例（JS 的 `expect(a).toBe(b)` 同理）：

```python
# tests/test_demo.py
def refund_amount(total, refund):
    return min(refund, total)          # 不超过订单总额

def test_refund_not_over_total():
    assert refund_amount(100, 200) == 100   # 超了就给到上限
```

**Step 4 · 跑命令、看绿**
`pytest`（或 `npm test` / `go test ./...`）→ 看到 **1 passed** / **ok** → 你已跑通人生第一次测试。

**Step 5 · 再把其余用例补进去**
把 Step3 里的骨架收好，回到 ② 的提示词，让 AI 按用例清单补齐——这时你就看得懂它生成的代码了。

> 💡 **跑通的标志**：命令无报错 + 至少一个 PASS。看到红（FAIL/panic） → 用 S-对话"喂报错姿势"把它喂准再修。

### 🔴 ④ 回归测试

**产出**：一份"**本次修改未破坏已有功能**"的回归结论。

**可复制的拆分维度**：

| 维度 | 要确认的核心 | 装进「退款」 |
|------|--------------|--------------|
| 回归范围 | 改了什么，连带影响哪些模块？ | 退款接口改了 → 顺带测订单/库存 |
| 基线 | 拿什么当"没改坏"的对照？ | B3 用重构前行为基线 |
| 结论 | 通过率 + 无回归 = 可落地？ | 全部绿灯才敢合并 |

**照抄即用的通用追问提示词**：

> 我已完成「[改动]」，请帮我做回归：
> ① 列出本次改动可能影响的模块/接口；
> ② 建议应回归的现有测试与用例；
> ③ 指出该场景最该盯的失败点。
> 我逐一运行并回报结果，你据实给出"是否可合并"判断。

> 💡 **关键判断（三轨道的回归差别）**：
> - **B1** 守验收——跑**全量用例**确认需求满足；
> - **B2** 先写**失败用例锁 Bug**，修复后确认转绿且不破坏其他（回归优先）；
> - **B3** 先建**行为基线（characterization tests）**，重构中让测试**全程绿**，改完后基线仍在（行为基线优先）。

## 二、沉淀成「测试报告」（本步的产出物锚定）

你这一章要交出去的，是一份**测试报告 + 可复现的测试代码**。测试报告是"凭什么敢说没改坏"的证据，结构如下：

```markdown
# 测试报告：<功能 / Bug / 重构>

## 1. 范围与基线
被测对象 + 这些测试守的是哪份需求/行为基线（B1 需求文档 / B2 复现路径 / B3 基线）

## 2. 用例与代码
用例清单（正常/异常/边界）+ 对应测试文件清单

## 3. 运行结果
通过数 / 失败数 / 覆盖率；失败用例的根因与处置（修代码 or 修测试）

## 4. 回归结论
受影响模块的回归通过情况 → 结论：可合并 / 待修复
```

**怎么写？**
- **代码**：用 ①② 生成的测试代码落盘到项目测试目录，纳入版本控制。
- **报告**：用 ②③④ 的结果汇总成上面四段；覆盖率按分支侧重报（B1 看整体，B2 看复现路径，B3 看关键路径）。
- **集成提示词**（把四个环节的产出拼成报告）：

> 请把以下素材整理成一份「测试报告」：
> [粘贴：用例清单] [粘贴：测试代码路径] [粘贴：运行结果] [粘贴：失败根因]
> 按 范围与基线 / 用例与代码 / 运行结果 / 回归结论 四段输出，回归结论给出明确"可合并 / 待修复"判断。

**检查标准**：读报告的人能回答"守的是哪个基线、跑了多少用例、哪些失败为何失败、改完是否无回归"。

> 📌 这份测试报告直接成为 **S-C** 交付物里的"测试报告"一项，也让 B1-⑤ 的每个"实现与验证记录"能对到这里的最终结论。

## 三、提示词模板：测试用例生成提示词（S-B 三轨道通用）

> 请根据以下需求文档和行为，生成测试用例和测试代码。
> 需求：[简述]
> 代码位置：[文件/模块]
> 覆盖正常场景、异常场景、边界条件。
> 使用 [测试框架] 编写，并确保可运行。

**逐字段解析**：

- **`需求：[简述]`**：B1 贴需求文档；B2/B3 改成贴**行为基线/复现步骤**——目标是同一个：给 AI 一份明确的"被测标准"。
- **`代码位置：[文件/模块]`**：收窄到被测单元，避免测到隔壁模块。
- **"覆盖正常/异常/边界"**：这是最低要求，漏了任何一类都要补。
- **`[测试框架]`**：换成项目现有框架，别让 AI 另起一套。
- **"确保可运行"**：要求给出能真正跑通的测试，不只是描述性的伪代码。

> 💡 **递归用法**：第一版用例若太糙，回喂"请对 ①异常 ②边界 各再补 3 条，并逐条给出可断言的预期值"，即可逼出有杀伤力的用例。

## 四、练习：为一个改动跑通测试并留报告

**任务**：给当前阶段的一次改动写测试、跑通、留报告。

**推荐步骤**：
1. 用「生成测试用例」提示词，从需求/基线挤出正常/异常/边界用例。
2. 用「生成测试代码」提示词落成可运行测试，并选好测试类型比重（按你分支：B1 单测为主 / B2 端到端锁 Bug / B3 行为基线）。
3. 用「运行·分析·修复」提示词，区分"代码缺陷 vs 测试写错"并修复。
4. 用「回归测试」提示词做无回归确认。
5. 用「沉淀测试报告」的整合提示词，把上面结果拼成四段报告。

**对答案**：你能回答"守的是什么基线、几个用例过了几个失败、每个失败为何失败、改动后是否无回归"。

## 五、本章验收清单

- [ ] 我能从 需求文档 / 行为基线 生成覆盖 正常/异常/边界 的测试用例。
- [ ] 我能让 AI 生成可运行的 单元 / 集成 / 端到端 测试代码，并按分支选对比重。
- [ ] 我能区分"测试写错"与"代码缺陷"，并迭代修复而非急着改代码。
- [ ] 我能按分支特点做回归（B1 全量 / B2 先锁 Bug 转绿 / B3 行为基线全程绿）。
- [ ] 我能把结果沉淀成一份四段的测试报告（见二、），含明确的可合并结论。
- [ ] 我能判断"全绿"是否真的代表无回归（须对照受影响模块逐一确认，而非只看通过数）。

> ✅ 通过后，进入 **S-C · 文档同步与交付**——把代码、设计、测试报告等整理成可持续维护的交付物，并保持文档与最终代码一致。
