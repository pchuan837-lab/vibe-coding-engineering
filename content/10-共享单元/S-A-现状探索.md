# S-A · 现状探索：读懂现有代码库（三分支共同前置）

> **轨道**：共享单元（B1 / B2 / B3 动手前的共同前置）。
> **前置**：通读 S0 · 为什么需要流程。
> **目标**：摸清架构、入口、关键依赖，避免"盲人摸象"——拿到需求就往一个文件里塞，却不知道它会炸到别处。
> **产出物**：一份「现状探索产出物」= 代码库地图 + 关键文件速查表（见「沉淀成产出物」），作为 B1 / B2 / B3 各路动手前的导航底图。
> **预估时长**：1–2 小时（新项目可简化到 15–30 分钟）。

> ⚠️ **重要提醒**：这一章讲的是"**在已有代码库上**"的探索。
> - 如果你要开发的**是全新项目**（还没有一行代码）→ 这一步大幅简化，重点变成"和 AI 一起确定目录骨架、技术栈、模块划分"（参照 S-附录 里的技术方案设计提示词）。
> - 其余所有情况（新功能、修 Bug、重构老系统）→ **本步骤必做，别想跳过。**

> **新手免责声明（项目太大？先别吞大象）**：你**不需要**一次性读懂整个系统。如果代码库很大（几万行以上），看到全量地图确实容易懵、AI 也未必一次吐得全。请按**"狙击手模式"**进场（提示词见 S-附录 `S-1-Lite`）：
> - 只做两件事——① 让 AI 找出"`[功能名]` 的入口在哪个文件"；② 从它向下追**最多 2 层**调用，输出这 3–5 个文件的职责。
> - 超出 2 层的先忽略。等眼前这个改动做完、有兴趣了，再回来看第 1 步的全量地图。
> 
> 一句话：**先咬你需要的这一口，别一次吞整头大象。**

## 一、为什么要做现状探索？—— 盲人摸象的代价

先问一个问题：当你把下面这句话丢给 AI 时，AI 到底在"哪一个仓库"里做文章？

> 「帮我优化一下订单查询太慢的问题。」

如果 AI 只盯着 `OrderController` 一处，却没想到慢的根本原因在 `OrderMapper` 里一个失控的 N+1 查询、或者数据库缺了一个关键索引——那你改完 controller 大概率**白忙一场，甚至引入新问题**。

「读懂代码库」是在把所有可能踩雷的地方先标出来：

- **入口在哪**：这个功能从哪个文件被请求进来？
- **数据流怎么走**：请求进来后经过了哪些模块、读写了哪些数据？
- **依赖关系**：我想改的这段代码，被谁依赖、又依赖谁？改它会波及谁？
- **风险点**：哪些地方脆弱、耦合重、缺测试，我最碰不得？

现状探索的产出，是一张"**关键文件速查表 / 代码库地图**"——它是你后续所有操作（加代码、定位 Bug、做重构）的**导航底图**。

> 一句话：**动手前先建模，建模后再动刀。** 不要一上来就在黑暗里摸象。

## 二、通用方法：四步读懂一个代码库

整套方法只需四步，每一步 AI 都能帮你完成大半，但**你来把关方向**。

### 🔴 第 1 步：让 AI 生成「代码库地图」

**产出**：一份「代码库地图」（六板块：整体架构 / 模块职责 / 入口流程 / 核心数据 / 模块依赖 / 风险点），作为后续几步的宏观骨架。

**可复制的拆分维度**（六板块，跨项目直接套用）：

| 维度 | 核心问题 | 装进「贯穿案例·订单退款」 |
|------|---------|--------------------------|
| ① 整体架构与分层 | 这是什么架构、分几层 | 退款逻辑该放应用层还是领域层 |
| ② 各模块职责 | 每个目录/包是干什么的 | 找"退款"要动订单模块还是支付模块 |
| ③ 入口与关键流程 | 从哪进、一次请求怎么走 | 退款从哪个接口进、经过哪些模块 |
| ④ 核心数据模型 | 有哪些实体/表、怎么关联 | 退款牵动订单/库存/优惠券哪些关联 |
| ⑤ 模块间依赖关系 | 谁依赖谁、有没有环、最底层是哪些 | 改订单服务会不会炸到一批依赖方 |
| ⑥ 修改风险点 | 哪些耦合重、缺测试、改动易炸 | 退款要加字段的地方是不是最脆那块 |

**照抄即用的通用追问提示词**：

> 请分析以下代码库，输出一份代码库地图：`[项目根目录 / 关键文件列表]`。
> 按 ①架构与分层 ②模块职责 ③入口与关键流程 ④核心数据模型 ⑤模块间依赖 ⑥修改风险点 六块输出 Markdown。
> 要聚焦时补一句：`请重点描述一次 [某典型请求] 从入口到数据库的完整调用链。`

这是最高效的一步。AI 可以在几秒内扫完整棵树，输出一份宏观地图。**你只需要把项目根目录或关键文件列表丢给它，并告诉它你要什么。**

代码库地图为什么恰好是这六块（缺一块的翻车代价）：

| 地图板块 | 回答的问题 | 没它，你会栽在哪（为什么需要它） |
|----------|-----------|------------------|
| ① 整体架构与分层 | 这是什么架构？（MVC / 微服务 / 分层 / 事件驱动…） | **不懂分层，就把业务逻辑塞错层**——例如把数据访问写进 Controller，后续每加一个功能都难收拾 |
| ② 各模块职责 | 每个目录/包是干什么的？ | **找不到"该动哪"，只能到处猜**——改错模块，或把一个功能拆散到七八个不相关目录 |
| ③ 入口与关键流程 | 程序从哪个文件启动？一次典型请求怎么走？ | **不知道请求从哪里进来**——加功能 / 定位 Bug 时无从下手，只能靠断点瞎试 |
| ④ 核心数据模型 | 有哪些关键实体/表？它们怎么关联？ | **改字段/加字段时踩到关联雷**——不知道一个订单关联库存、支付、优惠券，一改崩一片 |
| ⑤ 模块间依赖关系 | 谁依赖谁？有没有环？谁是最底层不要乱动？ | **动"最底层"没心理准备**——它被几十个模块依赖，你改了它，全链路一起炸，却还以为只是小改动 |
| ⑥ 修改风险点 | 哪些地方耦合重、缺测试、改动易炸？ | **在雷区里还大步走**——没提前标出脆弱处，改一处爆一处，把排雷变成了连环 事故 |

**为什么"正好"是这六块？因为每一块都对应一种"读不懂代码库就必然踩的坑"**，而且它们有内在顺序：

- ①②③ 是**全局观**（这是什么、块怎么分、从哪进）——先让你"知道路怎么走"；
- ④⑤ 是**结构观**（数据怎么存、模块怎么连）——再让你"知道哪根柱子不能碰"；
- ⑥ 是**预警观**（哪里会炸）——最后给你"排雷清单"。

> 一句话：**前五块帮你"看清地图"，第六块帮你"标出雷区"。** 没有这套区分，你拿着需求就冲进代码库，跟没地图没拆弹图地进工地没两样。

> 💡 **小技巧**：地图不需要一次生成得面面俱到。第一版只要"分层 + 模块职责 + 入口"，够你开跑就行；等真正要动某块时，再让 AI 就那一块深挖。

### 🔴 第 2 步：用搜索 + 调用链分析精确定位

**产出**：一份「受影响面清单」——目标函数 / 字段的**全部真实调用点** + 其影响范围。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「贯穿案例·订单退款」 |
|------|---------|--------------------------|
| 定义在哪 | 这枚函数/字段住在哪个文件的哪一行 | 找 `cancelOrder()` 的定义在哪个文件 |
| 直接调用点 | 谁直接调用了它 | 搜 `cancelOrder` 有哪些直接调用 |
| 隐藏调用点 | 有没有被事件/依赖注入/字符串间接调用 | 退款取消是否被 `order.cancel` 事件触发却搜不到 |
| 影响范围 | 改了它，哪些模块要一起回归 | 会影响订单/库存/支付，要回归谁 |

**照抄即用的通用追问提示词**：

> 我要改动 `[函数/字段名]`，请帮我精确评估受影响面：
> ①它在哪个文件定义；②列出全部直接调用点（含文件+行号）；
> ③找出可能存在的隐藏调用点（事件名 / 依赖注入别名 / 字符串 key），逐一贴出调用证据；
> ④给出改它之后需要回归测试的模块清单。

第 1 步的地图是"宏观"。这一步要回答一个**更尖锐的实操问题**：

> 我接下来要动的这个**具体函数 / 字段 / 数据结构**，被哪些地方用到？动了它，谁会受影响？

这一步要区分**两个层次**，别混为一谈：

#### 层次一：找"定义在哪" —— 用文本搜索（Quick & Dirty）

按函数名、类名、报错关键词全局搜一遍，锁定这枚代码"住在哪个文件的哪一行"。工具上：

| 栈 | 常用手段 |
|----|----------|
| 任意 | 编辑器内全局搜索 / `ripgrep`（`rg -n "函数名"`，带行号） |
| Go | IDE（GoLand）的 "Go to Definition" 跳转定位、`rg -n "函数名"` |
| TS/JS | VS Code "Go to Definition"、`tsc --noEmit` 报错回溯 |
| 通用 | IDE 的 "Go to Definition" 跳转定位定义行 |

**这一层能告诉你"定义在哪"，但它不够——因为它默认把"同一个词"都当成"同一件事"。**

#### 层次二：找"全部真正的调用点" —— 用调用链分析

这才是精确定位的关键。文本搜索有个致命盲区：**它只做"字符串匹配"，碰上动态派发就抓瞎。**

我们用贯穿本章的电商例子说明。假设订单模块里有这样一个函数：

```ts
// order/service.ts
export function cancelOrder(orderId: string, reason: string) {
  // ...订单取消主逻辑
}
```

**文本搜 `cancelOrder` 能搜到什么？** 直接手写的调用：

```ts
// admin/controller.ts  —— 后台手动取消
cancelOrder(orderId, "运营手动取消");

// order/controller.ts  —— 用户页面点取消
cancelOrder(orderId, "用户取消");
```

**但文本搜索会漏掉这些"隐藏调用点"：**

```ts
// 1) 通过事件/字符串订阅被触发，搜"函数名"根本找不到：
events.emit("order.cancel");          // 搜 cancelOrder 搜不到这行
// 回调里才执行 cancelOrder，路径藏在字符串里

// 2) 通过依赖注入 / 反射 / 运行时构造被间接调用：
const orderSvc = container.resolve("OrderService");  // 别名是字符串
orderSvc.cancel(orderId, "定时超时取消");             // 方法名还能对得上

// 3) 事件监听器按字符串 key 注册，谁触发它藏在别处：
bus.on("order::cancel::timeout", () => cancelOrderInTimeout());
```

**结果**：你以为只改 2 处调用就行，实际上有 5 处在用 —剩下 3 处被你漏掉了，改完立刻炸在线上。所以第二层用的不再是"搜名字"，而是"**建调用关系图**"。

**怎么建真正的调用链？** 按项目语言选对应的静态分析工具，它能解析代码结构、找出"真实被唤起的所有路径"：

| 栈 | 工具 / 手段 |
|----|------------|
| TS/JS | `ts-morph` 写脚本遍历调用点；`npx madge --extensions ts,js src` 画依赖图 |
| Go | `go list -deps ./...` 看包依赖；`golang.org/x/tools/go/callgraph`（静态调用图）；IDE 的 Find Usages（能跟到动态处） |
| Java | IDE 的 "Find Usages"（IntelliJ 对动态绑定处理较好） |
| 通用兜底 | 在可疑事件名/字符串 key 上反向搜一遍（如 `rg "order.cancel"` 找监听方） |

**先分清工具各自干什么，别混用**（尤其别把"静态检查"当"调用链分析"）：

| 工具 | 用途（它到底在干什么） | 何时用 |
|---|---|---|
| `go vet` | **静态检查**：分析是否用了可疑构造 / 潜在 bug（如多余的赋值、不可达代码），**不是**帮你找定义或建调用链 | 提交前当检验员，抓低级风险 |
| `Find Usages` / 调用图（callgraph） | **调用链分析**：找出某个函数"真实被谁调用、波及哪些路径" | 想知道"改这里会不会炸别处"时 |
| `go list -deps` | 看包级依赖关系 | 梳理模块边界、定位"哪个包拖了大依赖"时 |

> 💡 **务实建议**：先用文本搜索拿到"快而全的候选"，再用调用链工具确认"真实的受影响面"，最后**对事件名 / 依赖注入别名这种字符串**单独反向搜一遍补盲区。三层都过，才算真正"摸清了"。

**一句话总结这一步**：Ctrl+F 能让你"找到定义"，调用链分析才让你"看清影响面"。这两者差的那部分，正是改东坏西的**隐藏引信**。

### 🔴 第 3 步：让 AI 逐模块总结「三件事」

**产出**：一份「模块三句话总结」（是什么 / 干什么 / 被谁依赖），每句带 import / 调用证据可抽查。

**可复制的拆分维度**（三句固定句式，跨模块直接套用）：

| 维度 | 核心问题 | 装进「贯穿案例·订单退款」 |
|------|---------|--------------------------|
| 是什么 | 这个模块本质上是什么（一条角色定义） | 订单模块是业务编排还是纯数据存取 |
| 干什么 | 它暴露哪些主要入口 / 能力（几个动词即可） | 订单模块有哪些对外方法，退款走哪几个 |
| 被谁依赖 | 谁 import 它、它又依赖谁（**最关键**） | 改了支付模块要回归哪几个调用方 |

**照抄即用的通用追问提示词**：

> 请按三句固定句式总结模块 `[模块名]`：
> ①它是做什么的（一条角色定义）；②它暴露哪些主要入口 / 能力；
> ③它被谁依赖、又依赖谁——第 ③ 句务必给出具体文件 + 行号的调用证据，不要泛泛的模块名。

第 2 步把"某个函数"看透了，但你还缺"**这个模块整体**该不该动、怎样下手"的判断。第 3 步就是补这块：**对每个关键模块，逼 AI 用三句固定句式讲清楚**——避免它给你一大段代码复述，你听完还是不知道重点在哪。

三句固定句式，一句都不能少：

1. **是什么** —— 这个模块本质上是什么（一条角色定义）。
2. **干什么** —— 它暴露哪些主要入口 / 能力（几个动词即可）。
3. **被谁依赖** —— 谁 import 了它、它又依赖谁（**这条最关键**）。

**为什么"被谁依赖"是命门？** 因为它直接决定你的"爆炸半径"。我用一个完整的支付模块示例讲透。

假设有个 `pay/gateway.go`，让 AI 这样回答（下面是"示范答案"，你要的是这种颗粒度）：

> **是什么**：对接第三方支付渠道（微信 / 支付宝）的适配层——向上层提供统一的支付接口，屏蔽各渠道差异。
> **干什么**：对外暴露 3 个入口：`CreatePayment()` 发起支付、`VerifyCallback()` 校验支付回调签名、`QueryOrder()` 主动查单。
> **被谁依赖**：被 2 个模块 import —— 订单模块（下单时调 `CreatePayment`）、后台对账模块（调 `QueryOrder`）；它自己则强依赖 HTTPS 客户端库和渠道密钥配置。

这条"被谁依赖 = 2 个模块"的价值立刻显现：**如果你想给支付加一个"渠道切换"，改动会波及订单和对账 2 个模块 → 这 2 个模块的测试都要回归 → 影响面可控。** 但如果有模块用更隐蔽的方式（依赖注入拿别名、事件订阅）在用它，影响面就可能是 20 个模块——**你没摸清"被谁依赖"，就永远不知道这颗雷多大。**

**关键：怎么确保 AI 这三句话是"真话"而不是编的？**

因为 AI 的总结也可能错（尤其是大型代码库里的 import 和动态依赖）。所以第 3 步的实操要带一道"**证据校验**"：

```text
追问模板：
请为你上面的每一条"被谁依赖"，给出证据——具体是哪个文件的哪一行 import / 调用，
把相关代码贴出来，不要给泛泛的模块名。
```

> 💡 这样逼 AI 出示"import 行 / 调用点"作为证据，你抽查 1–2 处即可确认它对这一块的认知是否可靠。**AI 的地图要抽查，这里更要抽查——因为"被谁依赖"判断错了，后面所有影响面评估都会跟着错。**

**实战顺序建议**：一次**只问一个模块**，别一次塞一堆；优先问"新项目要接的 / 新队友写的 / 或看起来就很可疑的大模块"。每问完一个，就把结果填进第 4 步的速查表，避免重复提问、重复统计。

### 🔴 第 4 步：沉淀「关键文件速查表」

**产出**：一张会持续更新的「关键文件速查表」（关键文件 / 是干什么的 / 改这个功能从哪下手 / 影响哪些模块），是本小节的收口交付物。

**可复制的拆分维度**：

| 维度 | 核心问题 | 装进「贯穿案例·订单退款」 |
|------|---------|--------------------------|
| 关键文件 | 哪些是"会反复碰"的，不是全量清单 | 退款涉及 `order/service.go`、`pay/gateway.go` |
| 从哪下手 | 加功能时先看哪个文件 | 加了"退款"→先看 `order/service.go` 的 `cancelOrder()` |
| 影响哪些模块 | 改动后要回归谁 | 改了订单服务→回归库存/支付/优惠券 |
| 何时更新 | 什么时候补一行 | 每改完一个关键文件，立即在那一行补一句"改了啥、影响变没变" |

**照抄即用的通用追问提示词**：

> 请根据前面的探索（代码库地图 + 受影响面清单 + 模块三句话）提炼一张「关键文件速查表」：
> [粘贴：以上探索产出]
> 列：关键文件 / 是干什么的 / 改某个功能从哪下手 / 影响哪些模块；
> 只保留"会反复碰"的关键文件，合并重复项，不要全量罗列。输出 Markdown 表格。

探索的最终产物要落成一张表，而不是停留在脑海里或聊天记录里。这张速查表就是你后续所有工作的**案头参考**：

| 关键文件/模块 | 是干什么的 | 我改这个功能要从哪下手 | 它会影响哪些模块 |
|--------------|-----------|----------------------|-----------------|
| `order/service.go` | 订单业务逻辑 | 加退款时先看这里 | 库存、支付、优惠券 |
| `pay/gateway.go` | 对接支付渠道 | 换支付商时改这里 | 订单、对账 |
| … | | | |

**这一列一列怎么填？（重点：别把它当成"一次性报告"，要当"活档案"）**

速查表的价值不在"写完"，而在"写完还能被后续每个环节持续用上"。所以填的时候记住四个原则：

1. **每一行 = 一个"会反复碰"的关键文件**，不是全量文件清单。一上来就把几百个文件全列上，等于没列。
2. **第三列（从哪下手）要写得"够具体到能直接定位"**——写"加退款时先看这里"，比写"订单逻辑"有用得多。最好是"**要加 X 功能 → 先看这个文件**"式的映射，直接变成你的行动索引。
3. **第四列（影响哪些模块）要来自第 3 步的核验**，别拍脑袋。它直接决定你改完后要回归哪几个模块的测试。
4. **边动手边更新**：你每改完一个关键文件，**立即**在这个文件那一行补一句"改了啥、影响变没变"。**让表永远反映最新现状**，而不是停在探索那天。

**一个完整的填写示例**（从需求到填表看这串思考）：

> 场景：你下一步要给订单加"退款"，于是翻了地图和调用链，得到几个关键文件。填进表时你这样写：
>
> | 关键文件 | 是干什么的 | 改"退款"要从哪下手 | 影响哪些模块 |
> |---|---|---|---|
> | `order/service.go` | 订单业务主逻辑 | 先定位 `cancelOrder()` 与库存回滚分支 | 库存、支付、优惠券，**另有 3 处隐藏调用点（事件/DI）已验证** |
>
> ——第二、三、四列都来自前面的探索，第四列尤其要把第 3 步核验出的"隐藏依赖"写上去，否则你会漏回归。

**这张表什么时候真正"发力"？—— 三个时刻：**

- **做 B1 新功能的方案时**：第三列直接告诉你"这个功能牵涉哪几个文件"，你照着写技术设计就好，不用重新翻。
- **做 B2 修 Bug 时**：第四列告诉你"改了这个文件，要回归哪几个模块的测试"，避免修好一个、打崩三个。
- **做 B3 重构时**：这张表告诉你哪块最底层、最不能乱动——重构顺序和风险等级的天然依据。

**最关键的一步：把它放进版本控制，别只存本地聊天记录。**

> 💡 建议放进 README 或项目里的 `docs` 目录并纳入版本控制（结合 S-C 文档章节），让它变成团队共享的活地图。它同时也正好是 S-附录 所有其他提示词里"请提供相关上下文"时**最省事的上下文来源**——下次让 AI 改代码，直接把这张表贴进去，AI 就少踩一半坑。

**一句话收尾**：第 1 步让 AI 生成地图、第 2 步精确定位函数、第 3 步核验模块依赖，**第 4 步把它们全收进一张你会持续更新的速查表**——四步走完，你手里的不是一堆聊天记录，而是一张能指导后面每一步的作战地图。

### ⚠️ 别忘了校验：AI 的产出可能是错的（防幻觉）

> **为什么必做**：AI 分析**大型代码库**时经常产生幻觉——**编造不存在的文件、依赖、调用关系**。它给你的地图很流畅，但可能是错的地图。新手最容易踩的坑就是"信了错地图，基于幻觉动手"。校验不是不信任，是把 AI 当"初稿生成器"而非"真相源"。

**校验三招**（每跑完一步都过一遍）：

1. **抽查抽真**：用文件管理器 / 文本搜索，**抽查 AI 点名的 2–3 个"关键文件"**，确认真实存在、路径和职责对得上。它声称"××模块依赖 ××"，就去那个文件里找到那行，而不仅仅是信了总结。
2. **要证据，别要结论**：要求 AI 每个断言都附**出处（文件 + 行号）**；给不出出处的，让它明确标注"推测"。**回链 S-2** 的"被谁依赖"证据追问。
3. **机器校验代替肉眼猜**：能跑 `grep` / 编译 / 测试就把结果甩给 AI 对照——用机器的结论去校验 AI 的结论，而不是凭感觉。

**可信度分层**（决定你要花多大力气核验）：

| 最该校验（幻觉高发） | 可暂信（低压） |
|---|---|
| 模块职责 / 依赖关系 / "被谁调用" | 目录结构本身（自己用文件管理器一眼看真） |
| 入口文件与调用链 | 库名 / 框架名等公开常识 |

**追问话术**（直接把下面的丢给 AI）：

> 请把刚才的每一条断言都标出来源（具体文件 + 行号 / 命令结果）。给不出来的就标"推测"，并和"核实到的事实"分开列。我会抽查其中 2–3 处。

> 💡 这一步正好和 S-对话 的"核验三问"对齐——**"证据够不够"是事实问题，该较真；"信不信 AI 的措辞"是判断问题，交给 S-对话**。校验是 S-A 版的"别被 AI 带着跑"。

### 沉淀成「现状探索产出物」（本步的产出物锚定）

你这一章要"交出去"的，是一份 **「现状探索产出物」**——代码库地图 + 关键文件速查表，是所有后续动作（B1 方案、B2 定位、B3 重构）的**导航底图**。前面四步各产出一份碎片，用下面这条**整合提示词**把它们收拢成规范交付文档：

```markdown

## 1. 代码库地图        架构分层 / 模块职责 / 入口流程 / 核心数据（第 1 步）
## 2. 受影响面清单      目标函数/字段的全部真实调用点 + 影响范围（第 2 步）
## 3. 模块三句话        关键模块"是什么 / 干什么 / 被谁依赖"+证据（第 3 步）
## 4. 关键文件速查表    关键文件 / 干什么 / 从哪下手 / 影响哪些模块（第 4 步）
```

**整合提示词**：

> 请把我这次现状探索的产出整理成一份「现状探索产出物」（四段）：
> [粘贴：代码库地图] [粘贴：受影响面清单] [粘贴：模块三句话] [粘贴：速查表草稿]
> 按 1.代码库地图 / 2.受影响面清单 / 3.模块三句话 / 4.关键文件速查表 输出；速查表合并重复文件、只留"要动手"的关键文件。输出 Markdown。

**怎么写？**
- **四份产出不必并列**：地图和速查表是主角；受影响面清单、模块三句话是支撑证据，按需并入对应行即可。
- **它是"活档案"**：边动手边更新，改一个关键文件，就在速查表那行补一句"改了啥、影响变没变"，别停在探索那天。

**检查标准**：读这份产出的任何一位（无论做 B1 方案 / B2 定位 / B3 重构），都能直接说出"要改这个功能从哪下手、会影响哪些模块、哪块最不能动"。

## 三、提示词模板：让 AI 生成代码库地图

这是 S-附录 里的 `代码库探索提示词`（即 **S-附录 S-1**，B1/B2/B3 通用）。直接复制填空即可。

> 你是一名资深架构师。请分析以下代码库，输出一份代码库地图：
> [项目根目录 / 关键文件列表]
>
> 要求包含：
> 1. **整体架构与分层**（这是什么架构、分几层）；
> 2. **各模块职责**（每个目录/包是干什么的）；
> 3. **入口与关键流程**（程序从哪启动、一次典型请求怎么流转）；
> 4. **核心数据模型**（关键实体/表及关联）；
> 5. **模块间依赖关系**（谁依赖谁、有没有环、最底层是哪些）；
> 6. **可能需要修改的风险点**（耦合重、缺测试、易炸的地方）。
>
> 输出 Markdown 格式。

**逐字段解析（方便你按需增删）**：

- **`[项目根目录 / 关键文件列表]`**：不要只给根目录，最好再贴一下你觉得相关的几个关键文件名，AI 会优先分析它们。
- **第 1 & 2 点**：宏观层，帮你建立全局观，一般都能生成好。
- **第 3 点**：最关键——**没有"入口和流程"，你就不知道从哪下手**。如果 AI 没给清楚，就追加一句："请具体描述一次 [某个典型请求] 从入口到数据库的完整调用链。"
- **第 5 点**：决定"能碰哪、不能碰哪"。若 AI 只是罗列没判断，追加："请明确指出哪些模块是最底层、改动成本最高、最不该碰。"
- **第 6 点**：提前排雷，B3 重构时尤其重要。

> 💡 **推荐用法**：第一版先只要求"架构 + 模块职责 + 入口"，快速拿到能上手的底图；等到要真正动某一块代码时，再对那一块单独追问"这一块的完整调用链和风险点"。

## 四、新项目怎么简化？ —— 从"探索旧代码"到"定骨架"

前面强调过：**全新项目没有旧代码可读**。但"现状探索"的精神照样适用——只是对象从"老代码库"换成了"还没定型的目录结构"。这一步推荐一起做两件事：

1. **和技术方案设计一起定骨架**：让 AI 给出推荐的目录结构、模块划分、分层方式（参照 S-附录 的技术方案设计提示词），避免功能还没写，目录就已经乱成一团。
2. **先立一张「承诺速查表」**：把"每个新模块是干什么的、归谁负责"先记下来，边开发边更新。**别等代码写完了才想起来补地图**，那时成本已经是好几倍。

> 一句话：老项目是"读已有地图"，新项目是"先画好地图再动工"。

## 五、练习：给你的项目生成代码库地图

**任务**：用本章方法，分析一个你手头真实的项目，产出它的代码库地图 + 关键文件速查表。

**推荐步骤**：

1. 选一个你能访问到的真实项目（不必是大型项目，哪怕是你自己在做的小项目也行）。
2. 用第 三 节的提示词丢给 AI，生成第一版代码库地图。
3. 对照真实代码抽查 1–2 处，看 AI 有没有说错（**AI 的地图也可能过时/出错，务必抽查**）。
4. 从地图里挑出"你接下来最可能要改的一个功能"，用第 2 步的 AST/搜索法，摸清它的调用链。
5. 把成果填进第 4 步速查表模板，存进项目的 `docs` 目录。

**示例抽查（你自己也可以这么验）**：

> AI 说"`receiveOrder()` 被订单模块调用"。你可以全局搜 `receiveOrder`，数一下真实出现几处、是不是真有订单模块在调。如果 AI 少算了两个调用点，**说明它对这一块的调用链认识不准，你要么追问，要么用依赖工具重查。**

**完成标准**（对答案）：

- [ ] 我拿到了一份包含"架构/模块/入口/数据模型/依赖/风险点"的代码库地图。
- [ ] 我抽查验证了地图里至少一处关键说法为真。
- [ ] 我针对「下一个要改的功能」，摸清了它的完整调用链。
- [ ] 我把成果沉淀成了速查表,并保存到了项目文档里。
